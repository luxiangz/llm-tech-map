1第一部分 · 拉起服务：PCP 初始化

命令形如 vllm serve deepseek-ai/DeepSeek-V3 --prefill-context-parallel-size 2 --tensor-parallel-size 1 ...。启动按下面 5 步初始化 PCP。

启动 ①命令行参数 → 配置对象

文件：vllm/config/parallel.py

--prefill-context-parallel-size 2 落到 ParallelConfig.prefill_context_parallel_size = 2（parallel.py:126-128）。注释原文："PCP expands the process world size but does not increase the KV-cache shard count"——PCP 扩的是进程数，不是 KV 分片数。

启动 ②进程组初始化：构建 PCP 通信组

文件：vllm/distributed/parallel_state.py

initialize_model_parallel（:1746）把 world_size 排成五维点阵（:1821-1827），再对 PCP 维做「transpose → reshape → unbind」投影（:1864-1881）：

all_ranks = torch.arange(world_size).reshape(-1, DP, PP, PCP, TP)   # TP 最内维
group_ranks = (
    all_ranks.transpose(3, 4)          # PCP 换到最内维
    .reshape(-1, prefill_context_model_parallel_size)
    .unbind(0)                         # 每行一个 PCP 组
)
_PCP = init_model_parallel_group(group_ranks, ..., group_name="pcp")

结果：PCP 组 = 每个 TP 组各抽一个同位 rank 组成的横向集合（跨 TP 组、组内共享 (pp,tp) 坐标）。此后全代码库经 get_pcp_group()（:1449-1451）取用。

启动 ③PCP > 1 强制切到 V2 runner

文件：vllm/config/vllm.py:583-585

PCP 是 MRV2（V2 model runner）专属特性。配置校验强制 prefill_context_parallel_size > 1 时启用 V2 runner；V1 runner 里 PCP 只存在于一个兼容性检查（gpu_model_runner.py:7122）。

2第二部分 · 长序列请求的完整流转

假设一个 128K 上下文的 DeepSeek-V3 请求进来（PCP=2、TP=1，2 张卡）。下面按时间顺序走完整个流转。

流转 ①请求到达 → 调度器（对 PCP 透明）

文件：vllm/v1/core/sched/scheduler.py（三处提及 PCP，无任何 PCP 调度逻辑）+ vllm/v1/core/sched/output.py:192-283

①-a "透明"的准确含义：调度器做「这一步跑谁、各算多少 token、KV 写进哪些块」的决策时，全程使用全局口径。scheduler.py 里其实有 3 处 PCP 字样，但没有一处是 PCP 逻辑：

# ① 读配置（只是取值，不决策）—— scheduler.py:174-175
self.dcp_world_size = vllm_config.parallel_config.decode_context_parallel_size
self.pcp_world_size = vllm_config.parallel_config.prefill_context_parallel_size

# ② 建 KV 管理器：PCP 被"故意当成 1"——透明性的核心实现 —— scheduler.py:284-285
self.kv_cache_manager = KVCacheManager(
    ...
    dcp_world_size=self.dcp_world_size,   # DCP：真实值透传（KV 会被交错切分）
    pcp_world_size=1,                      # PCP：硬编码 1（KV 不切分，保持全量副本）
)

# ③ 一个兼容性断言（拒绝组合，不是逻辑）—— scheduler.py:341-345

对照 DCP 就更好懂：DCP 要交错切分 KV cache，所以分配器必须知道 dcp_world_size；PCP 是「部分 query + 全量 KV」（gather 变体），分配器必须被瞒住（=1）。透明不是"无感知"，而是"被强制按 1 处理"——PCP 的存在被刻意从分配路径里抹掉了。

①-b 调度产出：全局 SchedulerOutput（output.py:192-283）——调度器（CPU 单进程）与所有 worker 之间的唯一数据契约，四组字段：

组关键字段含义
A. 本步调度内容scheduled_new_reqs（:197）、scheduled_cached_reqs（:201）、num_scheduled_tokens（:205）、total_num_scheduled_tokens（:208）、scheduled_spec_decode_tokens（:212）、scheduled_encoder_inputs（:216）、num_common_prefix_blocks（:219）首次调度请求的完整数据（prompt、block_ids…）/ 已调度请求的增量 diff / 每请求本步 token 数（全局口径）/ 总和 / 投机 draft token / 多模态编码器输入 / 公共前缀块数
B. KV 块分配new_block_ids_to_zero（:253-256）、kv_cache_block_copies（:258-259）本步新分配的物理块（worker 要先清零防脏数据）/ CoW 块拷贝；块分配本体在 A 的 block_ids / new_block_ids 里，同样是全局口径
C. 生命周期finished_req_ids（:224）、free_encoder_mm_hashes（:227）、preempted_req_ids（:233）上一步与本步之间结束的请求（通知 worker 释放缓存状态）/ 释放编码器缓存 / 被抢占的请求（v2 runner）

①-c 广播：每个 rank 拿到逐字节相同的全局 batch

# vllm/v1/engine/core.py:595-596 —— 调度器只跑一次，产出唯一全局 SchedulerOutput
scheduler_output = self.scheduler.schedule(self._should_throttle_prefills())
future = self.model_executor.execute_model(scheduler_output, non_block=True)

# vllm/v1/executor/abstract.py:224-227 —— collective_rpc 把同一对象广播给所有 worker
def execute_model(self, scheduler_output, non_block=False):
    output = self.collective_rpc("execute_model", args=(scheduler_output,), non_block=non_block)
    return output[0]

PCP rank 0 和 rank 1 拿到的 num_scheduled_tokens、block_ids 完全一致——描述的都是一条完整的 128K 序列、它全部的 KV 块（num_scheduled_tokens 是 128K 而不是 64K）。差异从这之后才开始：每个 rank 用这份相同蓝图各自构建 InputBatch，再在 partition_batch（流转③）里切出自己那 1/P 份。

流转 ③partition_batch：长序列切成 DualChunk 块分到各 rank

文件：vllm/v1/worker/gpu/pcp_manager.py:319-542（门面 maybe_partition_pcp_batch :621-627）

门面只有三行：manager is None 就原样返回（非 PCP 模式零开销），否则进 partition_batch。切分发生在每个 worker 自己本地——每个 rank 拿着同一份全局 batch，各自切出自己那份。分七小步：

③-a 存档全局视图 + 守卫（:327-328, :324-325）：self._global_batch = global_batch——采样前恢复用的「存档」；投机解码直接 NotImplementedError（PCP 不支持 spec decode）。

③-b 布局几何：DualChunkSwap 切法（_get_rank_segments :195-250）：一条长 prefill 切成 num_chunks = 2×W 块，rank r 认领块 r 与块 2W−1−r（镜像双块，覆盖整个 query 恰好一次，每 rank 负载 ≈ query_len/W）：

num_chunks = 2 * self.pcp_world_size
...
if is_prefilling:                                  # prefill
    chunk_indices = (rank, num_chunks - 1 - rank)       # 双块镜像
else:                                              # decode 复制
    chunk_indices = (0,)

decode 每步只有 1 个 token/请求，切成 W 份没有收益且增加延迟，所以全复制——每个 rank 都算这个 token（冗余计算），KV 只由 rank 0 写（见 ③-d 写掩码）。每个片段是一个 RankSegment（:26-34）；同一请求的两块是两个独立本地段——这就是 PCPManager 的本地缓冲区按 2×max_num_reqs 分配的原因（:74）。

③-c 纯 prefill 殿后（_reorder_segments :163-193）：decode/continued prefill 段排前、纯 prefill 段排后——MLA/sparse MLA 的 attention 后端要求 decode 在前、prefill 在后。

③-d 三个索引张量——整套设计的「几何」（_build_batch_layout :252-317，每步重建并拷上 GPU）：

# PCP=2 代码自带例子（:273-280）
global batch:       [A B C D E F G]            # 7 个 token，一个 prefill 请求
rank 0 / rank 1:    [A B G] / [C D E F]
padded gathered:    [A B G _ | C D E F]        # 每 rank 补齐到 max(3,4)=4
hidden_restore_idx: [0, 1, 4, 5, 6, 7, 2]      # 全局 token → gathered 槽位（attention 后还原用）
padded_gather_idx:  [0, 1, 6, 0, 2, 3, 4, 5]   # gathered 槽位 → 全局 token（index_select 用）

外加 gathered_kv_write_mask（:285, :298-306）：prefill 槽全 rank 写真值（写 KV）、decode 槽只有 rank 0 写真值——保证每个 KV 槽恰好被写一次。padding 槽的 gather 索引随意（例子槽 3 的 0 不参与计算）。

③-e 组装局部标量（:341-411）：local_to_global_batch_req_idx（局部段→全局请求）、local_start_pos = num_computed[req] + chunk 在 query 内的偏移（:363-372）——绝对位置，保证 chunk 即使来自序列中间，RoPE 也不坏；num_local_tokens 与 num_local_tokens_padded = max(各 rank token 数)（:386-387）——对齐到所有 rank 的最大值，这是后面 all-gather 能拼成规整矩形的必要条件。

③-f 切 token：index_select 一行（:412-422）——「每个 rank 拿到自己那 1/P 份 token」的实现：

rank_token_start = self.pcp_rank * num_local_tokens_padded
local_gather_idx = self._padded_gather_idx[rank_token_start : rank_token_start + num_local_tokens_padded]
torch.index_select(
    global_batch.input_ids,     # 全局 token 数组（完整 prompt 顺序）
    0,
    local_gather_idx,           # 本 rank 槽位 → 全局 token
    out=input_buffers.input_ids[:num_local_tokens_padded],
)

随后重建局部 query_start_loc（cumsum，:424-432）、positions/seq_lens（prepare_pos_seq_lens，:440-446）、is_padding（:448-450）并抹零 padding 槽的 input_ids/positions（:451-457）。

③-g 组装局部 InputBatch（:459-542）：cu_num_logits = arange(num_local_reqs+1)——PCP 不支持投机，每个局部请求恰好 1 行 logits（对应「这个 chunk 算完能采样的那个 token」）；local_is_prefilling 按局部段重判（min(local_start_pos, prefill_len) < prefill_len，:486-491）；最后 dataclasses.replace（:507-542）浅拷贝 + 覆盖所有 token 相关字段——「切分」的本质：同一份 InputBatch 结构，token 字段换成 rank 局部版本，完全不涉及 KV 数据（KV 在流转④）。

此刻状态：每个 rank 手里是一个「只含自己两块 chunk」的本地 InputBatch（req 数 = 本地段数），全局 batch 被存档在 self._global_batch。恢复路径预览：attention 后 restore_hidden_states（:607-611）做 all_gather(hidden, dim=0) 再按 hidden_restore_idx 排回全局顺序——采样拿到的 hidden 和全局 batch 对齐（流转⑥展开）。
流转 ④prepare_attn：slot mapping 编址重排

文件：pcp_manager.py:544-605（消费方 model_executor/layers/attention/pcp.py:11-45）

④-a 先回顾：slot 怎么算（公式里没有 PCP）——slot = 该 token 的 KV 在物理缓存里的地址。计算 kernel（gpu/block_table.py:299-307，DCP=1 时）：

block_indices = positions // block_size     # 第几个逻辑块
block_offsets = positions % block_size      # 块内偏移
block_numbers = tl.load(block_table[req, block_indices])   # 查页表 → 物理块号
slot_ids = block_numbers * block_size + block_offsets      # 物理块号×块大小+偏移

它只依赖全局 position、请求页表、block_size——跟 PCP 无关（只有 DCP 才改公式）。PCP 只做两件事：把「全局 token 序」的槽数组按 padded_gather_idx 重排成 gathered 布局，再按 gathered_kv_write_mask 把不该写的槽位打上 -1。

④-b prepare_attn 的三件事（pcp_manager.py:544-605）：

block_tables = gather_block_tables(local idx_mapping, out=...)   # ① 页表：按局部行抓取（:550-555）
global_batch_slot_mappings = compute_slot_mappings(global_batch...)  # ② 槽在【全局 batch】上算（:564-570）
torch.index_select(global_batch_slot_mappings, 1, padded_gather_idx, out=...)  # ③a 重排成 gathered 布局
torch.where(gathered_kv_write_mask, gathered_slot, PAD_SLOT_ID, out=...)       # ③b 不该写的槽填 -1

④-c 为什么不能直接在局部 batch 上算：① 页表是全局的（局部 batch 里同一请求出现两次，行序已乱）；② 写掩码是跨 rank 决策（「decode 只有 rank 0 写」）；③ 写路径本来就在 gathered 空间执行（latent 先 all-gather，见 ④-f）；④ 全局一次 kernel + 一次 index_select，比局部重算便宜。

各 rank 写 KV（latent 先 all-gather，写路径按位置对齐）：rank 0 写 P0→40、P1→41、P6→46；rank 1 写 P2→42、P3→43、P4→44、P5→45。40~46 七个槽跨两个 rank 恰好各写一次，之后两个 rank 的本地 KV 副本都是完整的 7 个 token。

④-e 加一个 decode 请求（1 token，position 100，物理块 25 → slot 100）。全局顺序 decode 在前：

global_slot_mappings = [100, 40, 41, 42, 43, 44, 45, 46]
padded_gather_idx   = [0, 1, 2, 7, 0,   0, 3, 4, 5, 6]
                        rank0: D P0 P1 P6 pad ┃ rank1: D P2 P3 P4 P5
gathered_kv_write_mask = [T, T, T, T, F,  F, T, T, T, T]   # D 是 decode：只有 rank0 写！
index_select → [100, 40, 41, 46, 100,   100, 42, 43, 44, 45]
where(mask)  → [100, 40, 41, 46,  -1,    -1, 42, 43, 44, 45]

结果：rank 0 写 D→100（每个 rank 都算了这个 decode token，但只有 rank 0 落盘）；rank 1 的 D 槽 -1 跳过。decode 的 KV 恰好写一次，prefill 的槽也各写一次——这就是写掩码存在的全部意义。

④-f 消费方：写路径为什么吃 gathered 布局（model_executor/layers/attention/pcp.py:11-45）——MLA forward 每层先 gather latent 再写 KV：

gathered_prefills = tuple(
    pcp_group.all_gather(tensor[num_decode_tokens:].contiguous(), dim=0)
    for tensor in tensors)          # 各 rank 的 prefill latent 拼成 [W×local]
gathered_slot_mapping = slot_mapping[: pcp_size * local_num_tokens]   # 槽映射同样截到 W×local

    (rank_slot_mappings[0, :num_decode_tokens],      # decode：只取 rank0（其余已被掩码置 -1）

⑤-a 每层先把 latent gather 齐、写进 KV cache：

_gather_prefill_cache_inputs（model_executor/layers/attention/pcp.py:11-45）的核心：

gathered_prefills = tuple(
    pcp_group.all_gather(tensor[num_decode_tokens:].contiguous(), dim=0)
    for tensor in tensors)   # 把各 rank 的 prefill 块 latent 跨 PCP 组收集

gather 后每个 rank 都拿到全部 2W 块的 latent，各自写进本地副本——所有 rank 的 KV 缓存瞬间收敛成全量（不变量 1）。decode 段用各 rank 自己算的（内容相同的）latent 写，槽位统一取 rank 0 行。

两种 all-gather 别混淆：每层一次的是 latent（kv_c+k_pe，576 维，attention 前，pcp.py:24）；每步一次的是 hidden（7168 维，采样前，pcp_manager.py:610）。hidden 不在层间 gather——层间唯一的跨 token 依赖是 attention，而它的数据（KV）已通过每层 latent gather 全量本地化；MLP/残差/LayerNorm 逐 token 独立。为什么 gather 小 latent 而不是大 hidden：576 vs 7168 维差 12 倍，每层 gather hidden 会到 ~56GB/步，latent 只要 ~4.5GB/步。
前缀命中（APC）× PCP：前缀缓存命中 = 本地块复用，不是"往多个 rank 拉取"。块 hash 去重 + CoW 在调度器（单进程）做，广播全局块号后每个 rank 在自己本地块池执行同样的复用；而 PCP 不变量 1 保证前缀 KV 每个 rank 本地早已有全量副本——命中零跨 rank 移动。本步只算未命中部分：partition 只切 num_scheduled_tokens（未命中段），local_start_pos = num_computed + chunk 偏移（绝对位置，RoPE/槽位正确），all-gather 只 gather 未命中的新 latent，写缓存只碰新槽。注意：带前缀的 prefill 是 continued prefill（extend），不是"纯 prefill"——它的 chunk 排在纯 prefill 之前（流转③-c）。

⑤-b 再做 attention（prefill = chunked context）：

"拷贝了两次"？准确说是"gather 暂存 + scatter 落盘"：gathered 缓冲（all-gather 输出，连续布局）与 KV 缓存（slot 散列布局）不兼容，NCCL 没有"按任意索引的 gather-scatter 融合原语"（它的原语都是每 rank 一个连续段），所以必须两步——先 gather 成连续暂存（通信，占互连带宽），再按 slot scatter 写缓存（本地显存写，不占互连）。暂存缓冲每层复用、用完即弃；真正的"重复存储"是 KV 缓存本身按 rank 复制 W 份（不变量 1，故意的取舍）。decode 段完全不 gather（pcp.py:21-22）。为什么 vLLM 不写定制融合算子：任意索引通信场景不少（MoE 专家路由、稀疏 MLA 的 top-k KV 检索、分布式 KV），但生产实现统一走"本地置换 + 连续集合通信"（MoE 的 moe_align_block_size + all-to-all，PCP 的 all-gather + index_select）；因为 NCCL 对全广播已近带宽下界（ring ~2(W−1)/W），定制省的是"暂存往返"这个常数因子，而正确性/跨平台维护成本很高——定制通信只出现在 NCCL 表达不了的"分片/按需"场景（ring CP 的 p2p、indexer 的按索引抓取）。
流转 ⑥restore + 采样：首 token（TTFT）

文件：pcp_manager.py:607-618 + model_runner.py:1545-1551

def restore_hidden_states(self, hidden_states):
    gathered = get_pcp_group().all_gather(hidden_states, dim=0)   # 各 rank 块输出拼回
    return gathered[self._hidden_restore_idx]                     # 还原全局 token 顺序

# model_runner.py:1545-1551

sampler_output, ... = self.sample(hidden_states, input_batch, ...)  # 用全局 batch 采样

各 rank 的 hidden 宽度已在 partition 时 padding 拉齐，all_gather(dim=0) 直接可行；gathered[hidden_restore_idx] 还原成全局顺序。每个 rank 恢复出的 hidden 完全一致 → 算出相同 logits → 采出相同首 token（同种子）。这就是 TTFT 的终点。

采样前全量 restore 能不能省？采样只需要每请求"最后一行"的 logits（hidden[logits_indices]，model_runner.py:1203），全量 restore 不是正确性必需。prefill 时 last token 在 chunk 2W−1、恒在 rank 0（长 query 时）；decode 时每张卡都有（复制执行）——理论上"单卡算 logits + 广播结果"可行。vLLM 仍全量 restore 的三个理由：① 采样路径保持 PCP 透明——restore 把 hidden 恢复成全局顺序，sample() 与非 PCP 完全一致，不需要"行→rank 映射"特判；② 所有 rank 同种子独立采样 → 免去"谁采样再广播 token"的新同步协议；③ 成本可控——restore 每步一次（decode 步只有 1 token，量可忽略），而每层 latent gather 是 61×74MB ≈ 4.5GB，restore 的 ~917MB 是小头。这是"用通信换实现简单"的取舍，不是必要开销。
流转 ⑦decode 阶段：逐 token 复制执行、零通信

文件：pcp_manager.py:225-227（decode 复制）+ mla_attention.py:880-990

prefill 结束进入 decode：调度器每步只调度 1 个新 token，PCP 的 chunk_indices = (0,) 让这个 decode token 复制到每个 rank。每个 rank 用自己完整的 KV 副本独立算注意力（q_nope 吸收进 latent：bmm(mqa_q_nope, W_UK_T) :888），decode 全程零 PCP 通信。代价是注意力算力按请求复制 W 份——「PCP 不加速 decode」的根源；KV 容量交给 DCP。
