0一句话 + 与静态批处理的对比

Continuous batching = 每一"步"（iteration）都重新组建 batch：完成的请求立刻出队、新请求随时入队、每个请求按当前阶段贡献 token（decode 给 1 个、prefill 给一小块）——batch 从诞生到结束没有任何固定边界。也叫 iteration-level scheduling。三个精确化：
  1. 重组发生在"前向之间"：每步四拍 schedule（重组）→ forward（一次完整前向）→ sample → update（回写）——重组是每步的第一拍，决定"这一步跑谁、各算多少 token"，发生在两次前向之间，不是"前向之后"；
  2. 重组是增量微调，不是推倒重建：新 batch = 上一步未完成的请求（默认续跑）+ 新插入的请求 − 已完成的请求——只动"边界"（进/出），running 成员不重排；
  3. 一步 = 一次完整前向（穿过所有层），不是每层重组；async scheduling（双缓冲）下重组会提前一个身位——前向跑着时已在为下一步重组（core.py:596 的 non_block=True），频率仍是每步一次。
静态批处理（static batching）连续批处理（continuous batching）
batch 组成一批请求凑齐后一起跑，全部结束后才换下一批每步动态进出：完成即走、新到即入
GPU 利用批尾"空泡"：短请求等长请求几乎无空泡：走一个补一个
延迟短请求被同批最长请求拖死（长尾严重）decode 步长毫秒级，交互延迟有界
KV 显存可静态预分配（batch 固定）必须动态分配（batch 每步变）→ PagedAttention
内核形状固定 batch、固定 seq 长每步形状可变 → 需要可变 batch 内核 / CUDA graph 补齐
重组时机整批全部完成才换下一批每步前向之间（增量微调，见上方 callout）

1前世：问题与起源

1.1 静态批处理的问题

  • 利用率：一批请求里长短不一，长的跑完整个 batch 才轮到下一批——GPU 在批尾空转；
  • 长尾延迟：一个 100 token 的短请求要陪一个 128K 的长请求跑完整个 prefill + decode，P99 延迟完全失控；
  • 等待即浪费：请求在"凑批"时排队，batch 没满也要等。

1.2 Orca（OSDI'22）：continuous batching 得名

"Continuous batching" 一词来自 Orca（微软，OSDI 2022，Orca: A Distributed Serving System for Transformer-Based Generative Models）。它的核心贡献就是 iteration-level scheduling：不再以"请求"为调度粒度，而是以"一步"（一次前向）为粒度——每一步重新决定 batch 里放谁。这是与静态批处理（request-level batching，如早期 TGI/FasterTransformer）的根本分野。

1.3 vLLM（SOSP'23）：两根支柱必须同时存在

vLLM（PagedAttention 论文）把 continuous batching 变成主流，但有一个关键洞察：连续批处理离不开 PagedAttention，两者互为前提——

  • batch 每步都在变 → 每个请求的 KV 显存需求每步都在变 → 不能静态预分配；
  • PagedAttention 把 KV 切成固定大小的块、按需分配（页表映射）→ 动态 batch 才有内存基础；
  • 反过来，页表/块复用也只有在"每步重组的动态 batch"里才有意义（前缀缓存、抢占都建立在它上面）。
记忆锚点：连续批处理解决"算什么"（每步谁的 token 进前向）；PagedAttention 解决"存在哪"（动态 batch 的 KV 怎么放）。一个是调度机制，一个是内存机制。

1.4 V1：默认开启，与 chunked prefill 合流

vLLM 从 V0 起 continuous batching 就是默认；V1 把它与 chunked prefill 绑成一套：每步 token 预算（max_num_batched_tokens）同时约束 decode 与 prefill 块，长 prefill 天然切成小块混进 decode 步（见 chunked_prefill_history_flow.html §1.2）。

2机制：完整流程（代码）

2a引擎主循环：一步 = 调度 → 前向 → 采样 → 回写

文件：vllm/v1/engine/core.py:584-614

def step(self):                                   # 无限循环，每步一次
    if not self.scheduler.has_requests():
        return {}, False                          # 没有请求就空转
    scheduler_output = self.scheduler.schedule(...)              # :595 ① 重组本步 batch
    future = self.model_executor.execute_model(scheduler_output, non_block=True)  # :596 ② 前向（异步）
    grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)
    model_output = future.result()                # :602 等前向结果
    if model_output is None:
        model_output = self.model_executor.sample_tokens(grammar_output)   # :604 ③ 采样
    engine_core_outputs = self.scheduler.update_from_output(
        scheduler_output, model_output)           # :609 ④ 回写（出队/推进状态）
    return engine_core_outputs, ...

关键：schedule() 和 update_from_output() 是同一个进程里的两个半场——前向期间新请求可以随时 add_request 进 waiting 队列，下一次 schedule() 就把它们收进来。这就是"连续"：请求在任意时刻加入，不等批凑齐。

每个请求的旅程：add_request → waiting →（被调度）→ running →（完成）→ 移除。running 就是"当前 batch"的抽象——每步 schedule() 都会重排它。注意：重排是增量微调——未完成的 running 成员默认续跑，schedule 只动"进/出"边界（完成即出、新请求补位），不会把整批推倒重来。

三步合起来就是"每步重组 batch"：老成员按需贡献 → 超载就踢最不重要的 → 空位立即被新请求填上。抢占（preemption）是连续批处理能扛过载的关键——KV 不够时不是拒绝新请求，而是把低优先级请求的 KV 块腾出来（请求保留进度，稍后从 waiting 回来续跑）。

2d请求状态机

文件：vllm/v1/request.py:348-389

class RequestStatus(enum.IntEnum):
    WAITING = enum.auto()        # 排队中（不在 batch）
    WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR = ...   # 等语法编译
    WAITING_FOR_REMOTE_KVS = ...  # 等远端 KV
    WAITING_FOR_STREAMING_REQ = ...
    RUNNING = enum.auto()        # 在 batch 里
    PREEMPTED = ...              # 被抢占（等待期间保留进度）
    FINISHED_STOPPED / FINISHED_LENGTH_CAPPED / FINISHED_ABORTED / ...  # 终态

旅程：WAITING → RUNNING →（完成）FINISHED_*，或 RUNNING → PREEMPTED →（重新）WAITING → RUNNING。没有"一批一起结束"的概念——每个请求独立走完自己的状态机，这就是连续批处理与静态批处理在数据模型上的根本差异。

这一步让"batch 永不固定"闭环：完成的请求腾出的位置（KV 块 + 并发槽位）在下一轮 schedule() 立即被新请求占用。

3意义：吞吐、延迟与两根支柱

  1. 吞吐：GPU 几乎无空泡——每个位置都在服务"能立刻产出 token"的请求；
  2. 延迟：单步毫秒级，任何请求都不会被"同批最长请求"拖住（长尾消失）；
  3. 过载有界：抢占机制让 KV 压力下系统优雅降级，而不是拒绝服务；
  4. 一切上层机制的地基：chunked prefill（长 prefill 切块混入 decode 步）、前缀缓存（跨请求复用块）、PCP（调度输出广播给所有 rank）都构建在"每步重组 batch"之上。
代价：每步形状可变 → 内核要支持可变 batch（或 CUDA graph 按捕获尺寸补齐）；调度器本身每步有开销（必须远小于一步的毫秒级）；KV 必须动态分配 → 与 PagedAttention 强绑定。V1 用 async scheduling（调度与前向双缓冲）进一步隐藏调度开销。

4今生：V1 的演进与上下游关系

机制与 continuous batching 的关系
chunked prefill长 prefill 通过每步 token 预算"嵌入"连续 batch：每步 = 若干 decode + 一小块 prefill（详见 companion 文档）
async scheduling调度（CPU）与前向（GPU）双缓冲：前向跑着时调度下一步，隐藏调度开销（core.py:596 的 non_block 就是入口）
PagedAttention / 前缀缓存动态 batch 的内存支柱：块分配、跨请求块复用、CoW
PCP调度输出（每步重组的全局 batch）广播给所有 rank，PCP 在其后切 query（pcp_code_walkthrough.html 流转①-③）
抢占 / swap连续批处理的"安全阀"：KV 压力时踢低优先级请求并保留进度
