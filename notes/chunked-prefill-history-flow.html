0先厘清：三个都叫"chunk"的东西

"分块 prefill"在 vLLM 里其实指三个不同层次的分块，经常被混为一谈。它们正交、可叠加：

分块切什么目的代码位置
调度级分块（时间切片）长 prefill 切成多步步长有界、与 decode 交错（延迟 SLO）scheduler.py:459-523
工作区级分块（chunked context）一步内把大 context 按 workspace 切块内存有界（不物化全量 k_nope/v）mla_attention.py:1595-1773
空间分块（PCP / CP）query 跨卡切并行度（不是时间切片）pcp_manager.py:195-250
本报告的主角是前两个（它们才是"chunk prefill"的字面意思）；PCP 是第三个，本报告最后会讲三者如何叠加，并指出 PCP 的 attention 执行循环原封不动复用了 chunked context 的机制。
chunked prefill 和 PCP 的区别：不是"单卡 vs 多卡"，是"切片维度不同"——

chunked prefill 的主要意义 = 把 O(T²) 的长 prefill 从"一次性的巨石"切成"可控小块"，换两个有界：

  • 延迟有界（调度级切步）：decode 不被长 prefill 饿死，SLO 可保证；
  • 内存有界（工作区级 chunked context）：不物化全量 [Skv, N, P] 的 k_nope/v，长历史不爆显存。

与 PCP 的关系：叠加，不是替代。常见误解是"单卡用 chunked prefill、多卡用 PCP"——错。两者各管一段：

切片维度目标增加卡数吗
chunked prefill（调度级）时间（步）延迟有界（decode 不饿死）否
chunked prefill（工作区级）内存（context 块）不爆显存否
PCP空间（跨卡 query）prefill 墙钟 /W（TTFT）是

PCP 的每个 rank 内部，用的正是 chunked prefill 的同一套执行循环（run_prefill_context_chunk + merge_attn_states）——PCP 把 query 摊到多卡后，每个 rank 面对的 context 依然是长历史（全量 KV 在手），依然要按 workspace 切块。一句话：chunked prefill 管"context 怎么分块读入"，PCP 管"query 在哪张卡算"，前者所有场景都要，后者是额外的并行维度。

1前世：问题与起源

1.1 问题：长 prefill 是"毒药"

128K prompt 的 prefill 是 O(T²) 的巨型计算（attention 的 QK^T 随序列平方增长），一次灌满 GPU 数秒。没有分块时三个问题叠加：

  • decode 饿死：同一批的其他请求等首个 token，被这条长 prefill 堵住几秒 → 交互式 SLO 直接爆表；
  • GPU 利用率差：单条 prefill 的 batch 只有 1 个请求，算力用不满；
  • 内核形状冲突：decode 是"1 query token/请求"（memory-bound，页表 gather），prefill 是"多 query token"（compute-bound）——两种 kernel 形状完全不同，这就是 split_decodes_and_prefills 批序契约（decode 在前、prefill 殿后）的根源。

1.2 时间线：V0 → V1 → MRV2

阶段做了什么关键点
V0（PagedAttention 论文 SOSP'23 同期）enable_chunked_prefill 开关：调度器把长 prefill 切成小 chunk，每步"decode + 一小块 prefill"混合执行attention 后端必须支持混合批；V0 的 ChunkedPrefillMetadataBuilder 就是 split_decodes_and_prefills 的前身
V1（MRV1 / MRV2）continuous batching 成为默认，chunked prefill 不再需要开关调度器每步有 token 预算（max_num_batched_tokens），长 prefill 自然被切成多步，每步与 decode 混合
MRV2 + MLA新增工作区级分块（chunked context）MLA 的 compute-friendly 路径在大 context 下内存爆炸（见 2.2），必须按工作区再切

1.3 背景：MLA 的两种算路径（文件头注释）

mla_attention.py:13-21 定义了选路径的准则——Sq / Skv 的比值：

# mla_attention.py:13-21
MLA 有两条计算路径：
* "compute friendly"：适合 prefill（Sq/Skv 较大，常接近 1）
  —— 把 latent 上采样成 MHA 的 k_nope/v 再算（数据量大、算得省）
* "data-movement friendly"：适合 decode（Sq/Skv 很小，常接近 0）
  —— 把 q 吸收进 latent（bmm(q_nope, W_UK_T)），MQA 语义、数据搬运少

NOTE：什么算"大/小"目前由调度器打的是 prefill 还是 decode 标签决定，
     未来应该按比值动态调。

MLA 的完整矩阵定义（mla_attention.py:34-63）：C=context 长、Lkv=512、P=128、R=64、V=128（DeepSeek-V3 口径）。

128K prefill 在 budget=16K 时被切成 8 步，每步与 decode 混合：

  • 第 1 步：算 token 0~16K，写进 KV 缓存（fresh prefill）；
  • 第 2 步：算 token 16K~32K——此时它是 continued prefill（context = 前 16K，从缓存读），local_start_pos = num_computed + 偏移 是绝对位置，RoPE 不坏；
  • ……直到 prefill 完成才采样首个 token（TTFT 的终点）。

每步的 num_scheduled_tokens、query_start_loc、positions 由 prepare_inputs（gpu_model_runner.py:932-1165）翻译成 InputBatch——这就是"chunk prefill"的第一步。

run_prefill_context_chunk（prefill/flash_attn.py:451-470）用 causal=False——context 全是合法前缀，不需要掩码；返回 LSE 供在线合并。merge_attn_states 是 rank 内的 online-softmax 合并（PCP 下也不跨 rank，因为 KV 已全量本地）。

数学等价性：分块 + LSE 在线合并 = 一次算全 context。这正是 flash-attention 的 online softmax，只是把"内部 tile"放大成"显式 chunk"——分块不改变结果，只约束峰值内存。

3意义（为什么这三层设计是必要的）

  1. 内存有界（工作区级）：不物化 [Skv, N, P] 的 k_nope/v，固定 workspace——128K context 也能跑，这是"能跑长序列"的前提；
  2. 延迟有界（调度级）：长 prefill 不堵死 decode，交互式 SLO 可保证；
  3. 利用率：decode token 填满 prefill 之间的 batch 空隙，GPU 不闲；
  4. 为 PCP 铺路：chunked context 的执行循环（run_prefill_context_chunk + merge_attn_states）正是 PCP 每个 rank 用的同一套——PCP 只是把"query 也切到多卡"（空间分块），context 的处理逻辑原封不动复用。这就是为什么 PCP 流转⑤里能看到一模一样的 chunked context 代码。

4今生：三块拼图如何叠加（128K prefill，PCP=2，budget=16K）

调度级：128K → 8 步，每步 16K（时间切片，与 decode 交错）
  每步内 PCP：16K query → 每 rank 8K（空间切片，DualChunkSwap）
    每 rank 内 chunked context：已算前缀（如第 5 步时 64K）按 workspace 切块
      逐块：gather 缓存 → kv_b_proj → run_prefill_context_chunk(causal=False)
            → merge_attn_states（在线 softmax）
      加上 suffix（本步 8K 新 token，causal=True）→ 合并出本 rank 的输出
层次管什么切分粒度代价/收益
调度级（时间）步长 / 延迟 SLO每步 ≤ budget 个 token多步调度开销 vs decode 不被饿死
工作区级（内存）峰值显存每 chunk ≤ MCC 个 context token多几次 kernel launch vs 不爆显存
PCP（空间）并行度 / TTFT每 rank 1/W 的 querylatent gather vs prefill 墙钟 /W
三者的关系：调度级"切步"决定每步的 query 是什么；PCP 决定 query 在哪张卡；chunked context 决定 context 怎么分块读入。三层各管一件事——时间、空间、内存——缺一不可，且完全正交、可任意组合。
