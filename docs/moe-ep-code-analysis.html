3EPLB：164 行纯 PyTorch 的放置算法

详细报告：src/_analysis/EPLB_code_analysis.md。以下为代码级要点（行号以 src/EPLB/eplb.py 为准）。

3.1 模块结构与入口

  • 自底向上 4 个函数：balanced_packing（:5）→ replicate_experts（:44）→ rebalance_experts_hierarchical（:74）→ 入口 rebalance_experts（:131）；__all__（:164）。
  • 入口把 weight[L,E] 强制 .float().cpu()（:149）——算法整体在 CPU 执行，输出三张 int64 表：
    • phy2log[L, num_replicas]：物理专家 → 逻辑专家（编号约定：节点主序、节点内每 GPU 连续 num_replicas/num_gpus 个槽位）；
    • log2phy[L, E, maxlogcnt]：逻辑专家 → 各副本所在物理专家（-1 填充的矩形表）；
    • logcnt[L, E]：每逻辑专家副本数，行和恒 = num_replicas。

3.2 两种策略其实是“一个函数的两组参数”

if num_groups % num_nodes == 0:            # eplb.py:150
    phy2log, phyrank, logcnt = rebalance_experts_hierarchical(weight, num_replicas, num_groups, num_nodes, num_gpus)
else:                                      # “global”策略没有独立代码：
    phy2log, phyrank, logcnt = rebalance_experts_hierarchical(weight, num_replicas, 1, 1, num_gpus)   # :156

global = 把“1 组、1 节点”喂给同一三层流水线（组=全部专家、节点=单点），层次结构塌缩为“全局复制 + 全 GPU 打包”。分层流水线（:74-129）：

  1. Step 1 组→节点：按组 token 总量 balanced_packing(…, num_nodes)，构造 middle-logical 排列 log2mlog/mlog2log（:103-108）；
  2. Step 2 节点内复制：每 (layer, node) 行独立 replicate_experts(…, num_replicas//num_nodes)（:110-113），副本不跨节点（NVLink 域假设）；
  3. Step 3 副本→GPU：按“均摊后单副本负载”再 balanced_packing(…, num_gpus//num_nodes)，物理槽位号直接把 GPU 分块编进编号（:115-129）。

3.3 两个启发式的代码本质

# 复制（LPT 式）：反复给“单副本负载最大”的专家加副本（eplb.py:66-70）
for i in range(num_log, num_phy):
    redundant_indices = (weight / logcnt).max(-1).indices   # weight/logcnt = 均摊到每个副本的负载
    phy2log[:, i] = redundant_indices;  rank[:, i] = logcnt[…];  logcnt[…] += 1

# 打包（eplb.py:27-40）：按权重降序，逐个放入“未装满且当前最轻”的桶（每桶恰好 n/m 项）
indices = weight.float().sort(-1, descending=True).indices
pack = min((i for i in range(num_packs) if pack_items[i] < groups_per_pack), key=pack_weights.__getitem__)

两点隐含假设值得注意：① 副本间负载按 weight/cnt 均摊（依赖“副本间 round-robin 均分路由”这一引擎约定）；② 每专家副本数无上限，一个极端热专家可吃光全部冗余槽。算法确定性（无随机、平局取最小桶号），同输入必同输出。

3.4 验证与移植结论

  • 仓库无测试文件、无 CI；7 处 assert 全是整除性/结构性检查（:19/36/60/90/92/94/95）。
  • 实测：torch 2.13 CPU 原样运行 README 示例 → phy2log 与官方输出逐元素一致；logcnt 每层和 = 16；global 分支（num_groups=3, num_nodes=2）不变式亦通过。
  • 移植提示：算法是纯 CPU 数值问题，任意语言重写只需三个纯函数；移植验证建议直接用 README 的 2×12 例子作 golden test，并保留“节点主序、GPU 连续槽位”的编号约定（否则 log2phy 的 scatter 重建会错位）。

4UltraEP：配额规划 + RSN 原生通信的全栈 C++/CUDA 运行时

详细报告：src/_analysis/UltraEP_code_analysis.md（UltraEP v1.0.0，约 7k 行 C++/CUDA + 2k 行 Python）。行号指向 src/UltraEP/ 下对应文件。

4.1 四层架构与“状态即对称内存”

  • 分层：ultra_ep/*.py 只做编排（无算法）→ csrc/ultra_ep.hpp/.cpp（Manager 状态/流/事件编排，cpp 1213 行）→ csrc/kernels/*.cu（persistent 求解 + 通信内核）→ NVSHMEM 对称堆（跨卡直达，唯一硬依赖；无 NCCL，仅元数据集体可选 NCCL 后端）。
  • 每 EP group 一个 Manager；每 rank 预留 R=num_local_redundant_experts 个冗余物理槽，副本 weight/grad 缓冲全库只有一个 [R, expert_total_numel] NVSHMEM blob、跨所有层复用（这就是论文“冗余槽显存 9.9GB→108MB”的代码来源）。
  • master 指针池：construct_local_master_ptr_pool(real_layer, fc1/2 权重+梯度) 把本 rank 各主专家独立张量的 data_ptr() 打包成 GPU int64 表（按 real layer 索引）。
  • 虚拟层：PP/VPP 下 allocate_microbatch_slot(real_layer) 返回 virtual = real*max_mb + counter%max_mb；placement/事件按 virtual 层隔离，指针池按 real 层取——一套放置语义复用到多个在飞微批。

4.2 前向四步 + 反向三钩子（不侵入 transformer）

前向（每 MoE 层）：update_placement(vid, routing_map)   # gating 后精确负载 → GPU 全量求解（异步）
                → weight_sync(vid, async=True)          # master 权重分发到副本槽（comm_stream）
                → reroute(vid, probs, routing_map)      # 逻辑路由展开到物理副本（藏在 weight_sync 下）
                → ws_event.current_stream_wait()        # dispatch 前汇合
反向（bwd-only 恒等 autograd.Function，fwd 恒等、bwd 动作）：
   RestoreReplicaWeights.bwd → weight_sync(阻塞)         # 专家 Dgrad 前恢复本层副本权重（槽被跨层复用覆盖过）
   StartGradReduce.bwd      → grad_reduce(async)        # 异步起副本→master 梯度归约
   JoinGradReduce.bwd       → gr_event.wait()           # 藏在 attention backward 后汇合

三个恒等函数使集成方无需改写 transformer 的 backward 图（Megatron 侧只加 3 个开关：--moe-enable-ultraep + 冗余专家数 + 让 token dispatcher 走 HybridEP）。

4.3 规划：阈值二分 × 容量可行性 oracle（placement.cu）

内核 quota_placement_solve_kernel：__launch_bounds__(128)，grid = 每 NVL 域一个 block（域内独立求解），常量 MAX_GPUS_PER_NVL=72, MAX_EXPERTS_PER_NVL=512, QUOTA_MIN_TOKENS_PER_REPLICA=1024, QUOTA_FAST_REPLICA_LIMIT=8。简化伪码：

T_lo = ⌈mean(rank_load)×balance_threshold⌉;  T_hi = max(rank_load)
快速试探：从 T_lo×(1+eps) 起按 (T_hi−T_lo)/100 步进，最多 2 次重试找可行 T
否则：4 warp 并行二分（每 warp 测一个阈值探针，保留最小可行缩界）

feasible(T)（单 warp）:
  excess[r]=max(rank_load[r]−T,0);  slack[r]=max(T−rank_load[r],0)
  if Σexcess==0 → true;  if Σexcess>Σslack → false
  对源 rank（负载降序）: need=excess[r]
    对其专家（负载降序）:
      available = loads[expert] − keep_on_master − 已导出
      while need>0 and available>0:
        min_tokens = max(1, ⌈need/可用目标数⌉)          # 动态下限防碎片
        选 best target r': slack 最大（平手最小 id），槽未满(≤R)、且未放该专家的 master
        q = min(need, slack[r'], available);  if q
  
要点：一次求解同时决定“复制谁、复制几份、每份多少 token（quota）”，把复制与重路由耦合（对照 EPLB 只做放置、reroute 交给引擎的 round-robin）；纯 GPU、无跨 rank 协商（所有 rank 同输入 → 同结果，无需 broadcast）；CPU 版（csrc/kernels/legacy/placement_cpu.cpp）仅兼容/对照。


  
4.4 权重分发：direct / adaptive / force_relay（weight_sync.cu）

  
    
    
  • 决策 should_use_weight_sync_relay：adaptive 需副本数 ≥4 且收益 (C−⌈(C−relay)/relay⌉) ≥ 2；中继数 relay_count = ⌊√C⌋（上限 8）；NVLink 域 ≤8 卡强制 direct。
    • 
    
  • 任务粒度：权重按 shard（fc1/fc2/scale）→ chunk（8×32KB=256KB）→ tile（32KB）切分；stage-1（master→relay）+ stage-2（relay→leaves）两张任务表由单 block×32 内核在 GPU 上构建（中继/叶子选择也贪心在卡上做，按各 rank 累计出口字节摊流量）。
    • 
    
  • 执行：persistent 内核，CTA 数 = SM×multiplier（clamp 到总 tile 数），leader atomicAdd 抢 tile；32KB smem 双缓冲：tile N 的 TMA load 与 tile N−1 的 N 路 TMA store 重叠——本地读一次、多播写给所有副本；每 chunk 的 ready flag 用 epoch 号而非布尔（多步间免清零）；≤8 卡的域退化为整 block 向量化线程拷贝版。
    • 
    
  • 效果：热专家出口流量从 O(C) 降到 O(√C)，chunk 级流式避免全局 barrier（论文/博客的 chunk-streaming relay，对应 §5.3 中的两阶段中继树）。
    • 
  


  
4.5 reroute 与 grad_reduce（reroute.cu / grad_reduce.cu）

  
    
    
  • reroute fwd：两遍（count → scatter）。quota 路径用 upper_bound(rank_quota_prefix, ordinal) 选副本；legacy/round-robin 用 ordinal % C；可选 interleave（先乘与总数互素的步长）把“同一 token 区间打在同一副本”的锯齿热点打散，降低后续 dispatch 拥塞。reroute bwd 用前向保留的 expanded 映射直接 gather（不复算、确定性）。
    • 
    
  • grad_reduce：persistent 内核（默认 42 SM、须偶数 ≤ 设备 SM）。deterministic 版按任务表序做保序累加（每 (master,shard) 组首任务写、依序累加后整体写回）→ bitwise 可复现（e2e 用 bitwise_equal 验证）；atomic 版（deterministic=false）用 atomicAdd 后向量化清零副本槽。归约后副本槽清零、下轮复用。
    • 
    
  • token 搬运本身不在 UltraEP：demo/生产配方里 dispatch/combine 由（Hybrid）DeepEP 提供——UltraEP 只做“专家/副本状态 + 均衡”。

4.7 工程上值得警惕的点（来自代码）

  
    
    
  • NVSHMEM 环境件：NVSHMEM_DISABLE_NVLS=1、CUMEM_GRANULARITY=2^29；构建需 -rdc 且仅 SM90/SM100。

5MoonEP：CuTe DSL 规划内核 + 对称内存通信库

详细报告：src/_analysis/MoonEP_code_analysis.md。行号指向 src/MoonEP/ 下对应文件。

5.1 先回答“用什么实现的”：CUTLASS Python DSL（不是 Triton，也不是手写 .cu）

  • 全部通信/规划内核用 NVIDIA CUTLASS Python DSL（CuTe DSL）编写并 JIT 编译（host 侧 functools.lru_cache 缓存每个 (shape,配置) 的编译产物；shape 全部 constexpr 特化）；关键原语（multimem.st 多播写、cp.async.bulk、match.any.sync、griddepcontrol）用 inline-PTX 嵌入。
  • csrc/ 只有 478 行（bindings.cu + nvl_shared_buffer.cuh）：封装 cuMemCreate/Map/ExportToShareableHandle（VMM 对称内存）与 cuMulticastCreate/AddDevice/BindMem（NVSwitch multicast），经 pybind11 暴露为 moonep._C。
  • 唯一 pip 依赖 nvidia-cutlass-dsl==4.4.2；payload bf16（H%8==0、16B TMA 对齐）、权重/梯度 fp32；H、H' 需 128 的倍数（2D TMA tile）。

5.2 规划内核（moonep/planning.py）：一个 cooperative grid 干完“完美均衡”

入口 launch_planning(ctx, topk_experts_flat, tokens_per_expert, cu_seqlens, plan)，输入是本 rank 真实路由；输出就地写回 dst[N]（规范编码）/ cu_seqlens[E+B] / experts_to_copy[R,B] / zero_fill / remote_stats。单内核分阶段（num_sms×CTA、512 线程/CTA）：

CAP = S×K（每 rank 实 token 容量）
A0  各 rank 用 multimem 多播把 tpe/topk 汇聚到 rank0；rank0 算专家前缀和 tpe_cumsum 与每个 home 组总 token
A1  组间迁移矩阵 z：bal[组]=group_tokens[组]−CAP（Σbal=0）
    贪心：h=argmax bal；u=argmin bal；z[h,u]=−bal[u]；bal[h]+=bal[u]；bal[u]=0（受方一次补满）
    直到 bal[h]≤0  ⇒  构造上保证【每个 rank 恰好收到 S×K 个实 token】且每个 dest 至多从一个远端 home 组接收
A2  专家级过户 alloc[e,d]：每个 home 组把配额按“本地剩余最多的专家”逐块让给 argmax 配额的目标
A3  每个 dest rank 选出 token 最多的 B 个远端专家(experts_to_copy)做预取槽；按组 0..E+B 扫出
    cu_seqlens（pad 到 token_padding 的倍数）与 zero_fill；rank0 用 multimem_st_v4 一次广播整张规划表
C1  各 rank 对本层 topk 做 expert 直方图 + 段前缀和 + warp 内 match_any 计数（排序为 O(1) 定位）
C2  对每条目用 tpe_cumsum 算全局序号，再对 alloc_cumsum 做【固定趟数二分(LOG2_R)】得到目标 rank lo，
    编码 dst = lo*NvS + expert_off[lo,e] + 组内偏移；同一 token 命中同 dest 的后续项编码为 −(raw)−1（负值保留 raw）
D   本地化输出 + cross_rank_barrier 发布（全程设备端，无 host 往返）

“完美均衡”的代码来源很干净：每源 rank 恰输出 S×K 个条目、容量 CAP=S×K、贪心循环终态使每个 dest 恰收 S×K——性质由构造保证（报告 §2.3 伪码）。规划的目标是最小化迁移（受方一次补满 → 迁移专家数少），冗余专家只在“某组溢出、需要远端接盘”时才出现。

5.3 Dispatch/Combine：没有独立 permute 内核（dispatch.py / combine.py / epilogue / prologue）

  • dispatch：消费 warp 用 cp.async.bulk 把 token 行直接写到远端 rank 的 expert-grouped 槽位（drow = dest_rank*NvS_padded + loff，经对称映射即 NVLink 写）；同 token 命中同 dest 的 K 项被规划器合并为 1 次传输（dedup），zero warp 清 padding，builder warps（仅 fresh）用 per-warp atomicAdd 物化 dup_groups/dup_loffs 结构。
  • dispatch_epilogue（本地）：把 primary 行扇出展开到全部重复槽位，供 group GEMM 直接读 [NvS,H]——专家 permute 被“融”进通信本身，而不是先搬回来再 permute。
  • combine_prologue（本地反向规约）：重复行的输出先在 smem 里 fp32 累加回 primary；combine 只拉 primary 行（G2S→S2G）累加到 token-major [S,H]，独立 warp 把路由权重 gather 回 [S,K]。
  • 无 host 同步：自复位 grid/cross-rank barrier（DeepGEMM 血统，写侧 fence.proxy.alias、读侧 fence.proxy.async.global 桥接 multicast/unicast 与 generic/TMA）+ PDL（pdl_trigger_dependents / pdl_wait_predecessor）+ 设备端读 dup_counts + 全静态 shape。
  • zero_copy：dispatch 返回 NVL shard 的视图（combine 端 data_ptr() 断言是同一块），专家 FFN 原地读写；代价是视图有别名生命周期约束（autograd 反向必须 zero_copy=False）。

5.4 对称内存与多播（csrc/nvl_shared_buffer.cuh + moonep/buffer.py）

  • nvl_dist_alloc：cuMemCreate（PINNED/DEVICE/POSIX_FD）→ Map/SetAccess 建本地 keepalive 张量 → ExportToShareableHandle；nvl_dist_map 收齐各 rank 的 fd 后 把 R 个 chunk 按 rank 序 map 进一段连续 VA、全部 RW（注释明说与参考实现不同：dispatch 要写远端区）。
  • nvl_multicast_*：root cuMulticastCreate + 全员 AddDevice + BindMem（注释：BindAddr 对 IPC 导入 VA 非法，故用 BindMem）；multimem.st 写 multicast VA = 硬件扇出到各 rank 同偏移。fd 经 AF_UNIX SOCK_DGRAM + SCM_RIGHTS 传递。
  • 对齐是血泪教训集中地：每个 chunk 字节数必须对齐到 VMM 粒度与 multicast 粒度的 max（注释多处给出驱动报错/挂死的教训）。
  • 预取/越界直读本质都是对称映射上的 NVLink 远端读（内存语义），无需显式 RDMA——与 UltraEP 用 NVSHMEM 对称堆是同一哲学的两套实现。

5.5 B 槽机制：prefetch 与 grad_reduce（prefetch.py / grad_reduce.py）

  • 权重张量 [E+B,H,H']：行 [0,E) 是各 home rank 主专家参数（对称映射）；行 [E,E+B) 是本 rank 预取槽。训练用 B=E/R（规划器保证 group GEMM 只摸本地行），推理推荐 B=3–4，槽不够时按 cu_seqlens 直读 home 行（稍慢、正确）。
  • prefetch：persistent 2 warp、2D TMA（128×128 bf16、stages 2–6 按 smem 预算选），把 experts_to_copy 指向的远端专家行拷入预取槽；槽物理内存在进程全局池（跨层共享）。
  • grad_reduce：[E+B] 梯度行的 [E,E+B) 不是参数梯度，而是独立 [R,B,H,H'] fp32 reduce buffer（复制专家梯度是临时值，不能污染框架自身梯度归约）；160 线程 persistent kernel（1 TMA warp + 4 ACC warp）把远端槽读到本地 fp32 参数梯度累加，cross_rank_barrier 后只清自己消费的槽（注释：曾试远端清零被否——同向 NVLink 读写共享带宽，本地清更快）。

5.6 测试与基准（怎么证明“对”和“快”）

  • 正确性 = 与参考实现逐元素比对：tests/planning_reference.py 是纯 torch CPU 参考（模拟 A1 贪心/A2 过户/C2 searchsorted/去重）；test_planning 对 dst/cu_seqlens/zero_fill/experts_to_copy 跨 rank all_gather 后逐元素相等，并断言守恒（alloc 行和=expert_count）、容量（列和≤CAP）、padding 倍数、dst 解码界；dedup 结构因生产 atomicAdd 前缀顺序不稳定，只比“group 集合”语义。
  • 路由生成器 tests/generate_topk_routing.py：lognormal 热门度 + multinomial 不放回采样造可控 maxvio（seed 共享热门度、rank 控逐 token 采样），另有 solve_sigma_for_maxvio 二分 σ 精确命中目标 maxvio。
  • 性能 = 与 DeepEP v2 elastic 对齐对拍（benchmarks/bench_vs_deepep.py）：同路由矩阵（seed 1234）、同 hidden/权重、同计时框架（warmup20/iters50）、同 SM=32、同 alignment/padding=128；逐 op 报 plan / d_f / d_b / c_f / c_b / pf；带宽公式 S·K·H·2/t 两侧一致。grad_reduce 不计入（可被后续计算重叠）。
  • 编码契约严谨：RANK_BITS=7（R≤128）、KIDX_BITS=7（K≤127）、跨 2^31 地址运算显式 i64。

5.7 局限（代码级可见）

  • 单节点 NVLink（EP = world size，bench 即如此跑）；依赖 NVSwitch multicast 硬件能力；bf16 + H/H′ 对齐约束；rank0 承担全局规划（汇聚 + 广播 + 单 warp 贪心）是串行热点；atomicAdd 前缀使 dedup 结构跨次顺序不稳定（测试只比语义）。

维度EPLB（eplb.py）UltraEP（csrc + ultra_ep/）MoonEP（moonep/ + csrc/）

⑤ 与框架集成面import 调用返回 3 张映射表（phy2log/log2phy/logcnt）；零侵入每层 3 个恒等 autograd 钩子 + Manager；Megatron 3 开关；token 搬运仍由 DeepEP/HybridEP 提供Buffer API 取代 dispatch/combine；要求权重为连续 [E+B,H,H'] 对称张量 + cu_seqlens 寻址（与现有框架布局深度耦合，vLLM 集成走 backend PoC）
⑥ 测试完备度无测试文件（README 示例经实测与代码一致，可作 golden）单卡求解合法性断言 + 分布式 e2e（weight_sync 逐位比对、grad_reduce bitwise、失衡/下界报告）；合成 Zipf 精确命中目标失衡CPU 参考实现逐元素比对 + 守恒/容量/padding 不变量 + 全链路 e2e；dedup 语义化比较；与 DeepEP v2 对齐基准

一句话总结差异本质：EPLB 把“均衡”当放置期的一次性数值优化；UltraEP 把“均衡”当每个 microbatch×层的控制面问题（GPU 求解 + 数据面原生通信）；MoonEP 把“均衡”当通信层的结构性保证（布局直接让每 rank 恒载 S×K）——三者的“均衡强度”和“工程代价”正是沿这个方向递增的。

7规划算法本质对比（伪代码级）

三者求解的是同一个“最小化最大 rank 负载”问题，但建模与求解路径完全不同：

EPLBUltraEPMoonEP
输入负载估计值 weight[L,E]（外部预测，如滑动平均）gating 后精确 loads[G,L]（fcollect 汇聚）本步真实 tokens_per_expert + topk（多播汇聚）
决策变量副本份数 + 副本→(节点,GPU) 放置阈值 T（隐式）+ 每个 (expert,target) 的 quota q组间迁移量 z + 专家级 alloc + 预取专家集合(B)
求解方法贪心：每步加副本给 argmax(weight/logcnt)；打包用最轻可行桶二分 T × 可行性 oracle（excess≤slack、动态 min-tokens、occ 防重复）；4 warp 并行探针贪心互填（argmax 超载 → argmin 空余）→ 过户 → 前缀和二分落位
输出phy2log / log2phy / logcnt（放置 + 反查 + 计数）p2l / l2p / lcnts / quota / quota_prefix / rank_quota_prefix（含 reroute 分片信息）dst / cu_seqlens / experts_to_copy / zero_fill（含布局与预取清单）
与 token 执行关系解耦（引擎按表 round-robin 分发）耦合：quota_prefix 直接驱动 reroute（upper_bound 选实例）耦合：dst 编码直接驱动 dispatch 直写
复杂度量级O(冗余数 × 行 × 专家) 向量化 + O(L·E·桶) Python 循环域内一个 block 并行；<100µs（EP64 求解，博客）单 cooperative grid + 固定趟数二分（LOG2_R），开销“可忽略”
副本负载假设weight/cnt 均摊（round-robin）按 quota 精确分片（不再依赖均摊）由 alloc 精确过户（不依赖均摊）

可以这样记忆三者的进化关系：EPLB 是“先定放置、分发靠引擎”；UltraEP 是“放置与分发一次性联合解出（quota）”；MoonEP 是“连 token 槽位都预先排布好，分发即直写”——控制粒度从“专家级”下沉到“token 槽位级”。

8从代码看三种设计哲学与选型启示

8.1 三种哲学

  • EPLB：策略即参数、贪心 × 分层、纯函数交付。把“全局均衡”实现为“层次均衡的退化输入”（同一函数两组参数）；复制与打包都用最朴素 LPT/贪心，靠“组→节点→GPU”的拓扑分层逼近均衡；对外只交三张映射表，算法内部只吃一个 fp32 负载向量——是可移植参考实现的教科书写法。
  • UltraEP：全设备决策、状态即对称内存、控制/数据面分离。求解、任务构建、通信全在 GPU（host 只 launch）；跨卡访问一律 NVSHMEM 对称内存普通读写 + TMA，免 IPC 管理；placement/quota（<100µs 控制面）与 weight/grad 传输（数据面）由各自的 persistent 内核承担、SM 预算可调——是为“每步都要重算”而生的工业运行时。
  • MoonEP：均衡进入数据布局、零拷贝是融合终点、全套设施服务“无 host 同步”。不提供 permute_in/out，而是把 permute 融进通信（直写 expert-grouped 槽位）、把 unpermute 融进 combine（prologue 预规约 + 只拉 primary）；对称内存 + 多播 + PDL + 设备端 barrier 全部为“每层零 host 往返”服务——是把系统性能细节做到极致的通信库（也因此与引擎的内存布局深度耦合）。
