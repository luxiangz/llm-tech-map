0. 摘要：十条核心结论（TL;DR）

  1. 这条技术主线讲的是"优化边界的逐层扩大"，而不是"LLM 学会了写 CUDA"。优化对象从单 Kernel（Tile/布局/流水）→ Megakernel（设备端任务图）→ Whole Model（整模图编译+并行+量化）→ Inference System（调度/KV/Server/数据链），反馈闭环同步扩大；四层是嵌套包含关系，不是替代关系。
  2. Megakernel 是整套叙事的地基：把整张计算图编译成"一份 PTX、一次 launch、一个 grid"，用 Persistent Grid、每 SM 指令流、依赖计数器与共享内存池把原属 Host/Runtime 的调度同步搬进设备端。Hazy Research 实测 H100 上 Llama-1B 前向 <1ms、用到 78% 显存带宽，比 vLLM 快近 2.5×、比 SGLang 快超 1.5×（batch=1、32 prompt+128 生成 token）。
  3. 甜点区在低时延小 batch：batch 越小、kernel 密度越低，launch/同步/气泡占比越高——megakernel 收益越大（多组实测 1.47×–1.51×，batch=1）；batch 增大后收益递减。这与"低时延"业务方向高度契合。
  4. Kernel Agent 的瓶颈不是写代码能力，而是目标函数："单 kernel 编译成功 ≠ 系统能用"。局部最快不等于模型最快，更不等于服务最快；正确性验收必须从"最终输出对齐"升级为"执行轨迹/中间状态等价 + 真实 serving 回归"。
  5. 约束先于生成：AutoMegaKernel 用"故意不完备"的受约束 Schedule-IR 把 Agent 的编辑面限制在 tiling / fusion_grouping / sm_assignment / pipelining_depth / page_allocation 等安全旋钮上，7,160 个对抗 Schedule（6,091 不安全）零错误接受；ForgeMegakernel 用十个渐进 milestone + 中间状态 Oracle 在 8 个模型家族 0.6B–13B 上拿到 50.5%–85.9% MBU、几何平均较 SGLang 1.21×。
  6. 整模层是系统工程问题：算子级优化仍有 10–15% 局部收益但对端到端贡献常 <2%；Agent 的增量价值在"跨图、跨层、跨回合"的编排与审计，把数周人工迭代压缩为数小时机器回合（迭代效率 3×–10×，不是直接 e2e 加速）。
  7. 系统层的正确方向是"Agent 驾驶、人类监督、确定性护栏兜底"：统一全自治推理运维截至 2026-09 尚不成熟；可落地形态是分层控制系统——LLM 提假设/读代码/生成候选，确定性程序负责测量/审批/执行/回滚，人保留高爆炸半径动作的最终授权。
  8. 评测与测量本身就是主战场：InferenceBench 显示 15 种前沿 agent（最高 8.08× vs 朴素 PyTorch）仍输给同等时间预算的简单超参搜索（11.53×）；AutoTuneBench 证明同一 kernel 对稻草人基线 10.6×、对诚实基线仅 2.03×。奖励函数不干净，Agent 会"合法地"学到假优化。
  9. "用 Agent 优化系统"与"为 Agent 优化系统"正在双向汇流：Autellix 把 Agent 程序（而非单次请求）作为一等调度对象，相同延迟下程序吞吐较 vLLM 提升 4–15×——系统级目标正从 request latency 升级为 program completion time。
  10. 可信度四问：目标是否真实、Oracle 是否独立、测量是否同条件、失败是否可回退。所有性能数字必须带硬件/模型/精度/基线/workload 口径，"最高值"不可跨组件相乘、不可跨论文排名。本报告对外部核验做了逐项标注（已核验 / 部分核验 / 未能核验）。

一句话总结：Agent 的真正增量不是替代编译器或 Autotuner，而是连接过去彼此割裂的优化空间与证据；而系统是否可信，最终取决于四件朴素的事——目标真实、Oracle 独立、测量同条件、失败可回退。

1.1 四层嵌套边界：扩大的是优化对象与反馈闭环

  • 第①层：传统 GPU 优化把一个算子视为单位——固定语义后搜索 Tile、Warp、流水和布局，指标是局部延迟。
  • 第②层：Megakernel 把单位扩大到异构任务图——指令流依赖、片上资源，指标是 Forward/Decode 延迟。
  • 第③层：Whole Model 纳入算子间数据流与 Host 配置，指标是模型端到端延迟。
  • 第④层：Inference System 把 Batch、KV Cache、并行、Server 与特征处理一起放进目标函数，指标是 TTFT、TPOT、吞吐、P99、成本。

四层并非替代关系：系统 Agent 仍依赖编译器生成代码、搜索器分配试验预算、Profiler 提供信号；上层优化必须回到底层 Kernel 才能兑现。真正新增的是：Agent 可以在证据不足时改变假设、编辑不同语言和层级的代码，并决定下一步调用哪种工具。

2. 第一篇：《从 Kernel 到推理系统：Agentic 优化全景》（总纲）

2.1 Megakernel：先把边界搬进 GPU

工程化定义：一次 Launch 覆盖较大范围的异构计算图，并在设备端承担原由 Host launch、Kernel boundary 或 Runtime 负责的部分调度、同步与流水。典型实现要素：Persistent Grid、每 SM 指令流、依赖计数器（Counter/Semaphore）、Shared Memory 池。注意："Persistent"或"大型 fused kernel"本身并不自动等于 Megakernel。

已实现案例（Hazy Research）已核验（官方博客）

  • ThunderMLA：用设备端解释器融合 MLA partial attention 与 reduction。H100 四组公开测试相对当时 FlashMLA 分别提升 23.6% / 19.0% / 36.3% / 7.6%；CPU Schedule 生成约 1–2ms，可复用或异步摊销。（博客核实：ThunderKittens 实现、统一 prefill+decode MLA kernel、变长调度器）
  • 完整 Llama-3.2-1B Megakernel：BF16、Batch 1、32-token prompt、生成 128 token、关闭 speculation 条件下，H100 上相对 vLLM 基线（已启用 CUDA Graph 与 Torch Compilation）接近 2.5×，相对 SGLang 超过 1.5×。（博客核实：模型实为 1.24B 参数，H100 前向 <1ms、78% 显存带宽；B200 上 <680μs、较 vLLM >3.5×）边界：不能外推到 70B、大 Batch 或动态 LoRA。

2.2 Agent for Megakernel：难点从写代码变成守住全局不变量

普通 Kernel Agent 可以在一个清晰函数边界内"生成—编译—校验—计时"；Megakernel 的候选则可能改变任务切分、每 SM 指令顺序、同步边和 Buffer 生命周期。只做最终输出比对，既难定位错误，也可能在罕见调度下暴露 race 或 deadlock。因此 Agent 必须被结构化中间表示（IR）和独立 Oracle 约束。闭环形态：

  • AutoMegaKernel 已核验（arXiv:2606.09682）：将 HuggingFace Llama-family 完整 Forward 生成为单个 persistent cooperative CUDA kernel；冻结的 Schedule-IR Validator 通过静态图检查拒绝不安全计划（作者明确说明不是机械化形式证明）；7,160 个对抗 Schedule（6,091 不安全）零错误接受，接受 360 个真实 lowering；自动研究环相对自身基线提升 1.25–1.72×；W8A16、Batch-1 相对 CUDA-graphed cuBLAS BF16：L4 最高 1.33×、L40S 1.25–1.27×、A10G 最高 1.08×、RTX5090 1.19–1.23×；在 A100/H100 上落后，比较精度不对称，最大真实 checkpoint 为 TinyLlama-1.1B。
  • ForgeMegakernel 已核验（arXiv:2609.12379）：十个渐进 milestone、每 SM 细粒度指令流、依赖计数器、Shared Memory Buffer Pool，引导 Coding Agent 生成每模型 Decode Megakernel；独立 mid-state Oracle 检查误差/精度/性能；8 个模型家族 0.6B–13B、14 个代表性 Decode 操作上 50.5%–85.9% MBU；同配置相对 SGLang 0.5.18 几何平均 1.21×、相对一套 Megakernel Compiler 1.54×；集成 SGLang 后在 GSM8K ragged prompt 上 14 个实现均更快且答案精度相当。

边界小结（原文）：Agent 负责提出跨阶段结构与修订路径，Validator、Compiler、Oracle 和 Benchmark 负责定义什么候选可以被相信。没有后者，Agent 只是在更危险的空间里生成代码。

2.3 Agent for Whole Model：局部最快不等于模型最快

KernelBench 把问题分为单算子、简单融合和完整模型等层级，以 fast_p 统计"正确且超过指定加速阈值"的任务比例。其 2025 年初始实验中，前沿推理模型开箱即用时能达到 PyTorch 基线速度的案例少于 20%；执行与 Profiling 反馈可改善结果——说明一次生成不是稳定优化器，Whole Model 不能简化为把所有热点逐个替换。

  • StitchCUDA 已核验（arXiv:2603.02637）：Planner/Coder/Verifier 三角色，Verifier 调用 Nsight Systems/Compute 做正确性与性能反馈；用规则与 Rubric 抑制复制 PyTorch、硬编码输出等 reward hacking；KernelBench 端到端任务接近 100% 成功率；速度收益相对多 Agent 基线 1.72×、相对 RL 模型基线 2.73×。限定：论文设定内的相对结果，不是通用模型加速倍数。
  • LLM4LLM 已核验（arXiv:2608.21836）：从目标推理脚本出发抽取分阶段任务，经验引导的 episodic Agent 搜索，只通过模型内验证接纳 Patch；10 个语言模型推理 workload 在 A100/H100 上均端到端改善，几何平均 3.91×（A100）/ 6.98×（H100）；KernelBench Level 2 辅助证据最高 2.745×。限定：依赖论文选定脚本、模型和基线。

Whole Model 验收原则：关键验收对象应是完整输出与 workload，而不只是单次 Kernel 时间——融合可能减少 launch 却因寄存器压力拖慢主 GEMM；一个更快算子也可能引入 Layout conversion；固定 Shape 胜出不代表 ragged batch 胜出。

2.4 Agent for Inference Systems：优化对象成为异构软件栈

再往上一层，瓶颈可能根本不在模型代码：请求排队、continuous batching、KV 分配、并行策略、模型 Server、Python 特征变换乃至数据搬运都能决定端到端结果。Agent 需要统一不同 Profiler 和代码库的证据，并把 SLO 与正确性设为硬约束。

  • FlashVector 已核验（arXiv:2609.17391）：把单 Kernel Agent 范式扩到 GPU Kernel、ML Framework Graph、NVIDIA Triton C++ Model Server 和 Python 特征服务；已部署于 Unity Vector 广告平台；Model Server 最高 2× 吞吐 / 1.98× 延迟加速，Feature Store 最高 1.6× 吞吐。限定：不同组件各自的最高值，不可相乘成全链路收益。
  • Autellix（NSDI'26，版本名 Agentix） 已核验（arXiv:2502.13965）：属于"为 Agent 优化推理系统"而非"用 Agent 优化推理系统"——Serving Scheduler 把 Agent 程序作为一等对象，利用跨 LLM 调用依赖和已完成调用数进行抢占与优先级控制；多种模型与 agentic workload 下相同延迟相对 vLLM 获得 4–15× 程序吞吐。提示系统级目标应从 request latency 升为 program completion time。

2.5 编译器、搜索器与 Agent 的边界（总纲核心表）

组件主要职责擅长不应被宣传成
编译器把合法程序/IR Lower 到目标代码，做可证明或规则化变换类型、依赖、代码生成、确定性检查会自主定义跨栈目标的 Agent
Autotuner / 搜索器在预定义参数或变换空间内试验并选择大规模、可复现、数值搜索理解任意日志并发明新修复路径
Agent读取代码、文档、Trace 和失败，选择工具并修改搜索空间或程序跨语言诊断、假设生成、长程迭代正确性 Oracle、编译器或性能真值

判断标准不是"是否使用神经网络"，而是是否理解开放式证据并改变优化计划。最可靠的架构：把创造性放在 Agent，把穷举效率放在搜索器，把语义约束放在 IR/Validator，把真值放在真实执行。

AlphaEvolve 已核验（DeepMind 官方）：Google 公开报告——一个 Gemini 矩阵乘 Kernel 提升 23%、使 Gemini 训练时间整体下降约 1%；FlashAttention 实现最高提升 32.5%（该 kernel 平均快 32%）；另在数据中心调度回收约 0.7% 全球算力。限定：Google 特定基础设施中的项目结果。

2.6 三条推断（原文对未来的判断）

  1. 性能证据会成为 Agent 的中间语言。Argus（arXiv:2609.12299，已核验）已尝试以 semantic region 统一编译器、硬件和系统测量——未来 Agent 不会只消费一段 NCU 文本，而会操作带来源、执行上下文和归因歧义的证据图；但统一标准尚未形成。（核验补充：Argus 实测让 AlphaEvolve 的平均加速从 5.4% 提升到 8.9%，TinyLlama 解码 1.65 vs 4.92 ms/token。）
  2. 生产形态更可能是"Agent 设计、确定性系统执行"。Agent 可离线改 Kernel、Schedule、Server 策略；线上路径仍由经过验证的 Dispatcher、规则和回滚控制。直接让通用 LLM 在每个请求上改执行计划，成本、抖动与安全性目前都不合算。
  3. 目标函数将从速度变为约束下的多目标 Pareto。TTFT、TPOT、吞吐、P99、任务质量、显存、功耗、编译成本和维护成本互相冲突；RoofLang（arXiv:2609.12551，已核验）提出实现无关表示、可验证 Mutation Space 与 Evaluator，其 Persistent Optimizer Agent 在 NVIDIA B300 上为 DeepSeek V4 Pro 搜索到吞吐和交互性改善 6.23%–50.1% 的架构（2026-09 新论文，尚不能当作成熟通用产品）。

结语（原文）：Agent 的真正增量不是替代 CUDA Compiler 或 Autotuner，而是连接过去彼此割裂的优化空间与证据。越往系统上层走，候选空间越大，单点"最高加速"越不重要，端到端、可复现和可上线越重要。

3. 第二篇：《Megakernel：从算子融合到设备端 Runtime》（主线一·地基）

本篇是整个系列的原理地基：先建立 GPU 执行模型与 launch 开销的量化认知，再讲 Megakernel 的编译与调度机制，最后给出实测数字与适用边界。

3.1 预备知识：执行模型与 launch 开销

  • 一个 CUDA kernel 被 Host 发射后，GPU 以 CTA（Cooperative Thread Array）为单位调度；每个 CTA 内是固定数量的 warp（每 warp 32 线程）；多个 CTA 分配到不同 SM；Grid 是一次 launch 中所有 CTA 的集合；SM 调度器以 warp 为最小单位，经取指、译码、发射、执行、写回。
  • 常规推理框架（PyTorch/TensorRT）中，一个模型是一串 kernel 序列：Host 逐个发射，kernel 之间通过全局内存（HBM）交换数据。
  • 开销数字：单次 launch 的 CPU 侧开销约 5–10 μs；kernel 间隙（gap）通常 1–2 μs（涉及同步更长）；一次 LLM 推理可能发射几十到上百个 kernel——假设 100 个 kernel、每个间隙 5 μs，累计 500 μs 纯开销；kernel 间经 HBM（1–2 TB/s HBM3）来回读写中间结果进一步耗时。batch 越小、计算密度越低、间隙占比越高——这正是低时延场景（交互式 Agent、实时对话）的痛点。
  • （Hazy 博客补充核验 已核验：H100 上 dummy kernel 每次启动约 2.1 μs，CUDA Graphs 也只降到约 1.3 μs；16 层 × 每层 7 次启动 × 5 μs 停顿，即可把理论 ~1350 次/秒的前向拉低到 ~770 次/秒——H100 只用到约 50% 显存带宽。）

同一实现可以既 fused、又 persistent、又用 CUDA Graph 组织 launch；Megakernel 则是"一份 PTX、一次 launch、一个 grid"，图里所有 op 以软件调度执行，CPU 只需把入口参数写进 command buffer。这既是极限的算子融合，也是把"运行时"从 Host 搬到设备端。

3.4 设备端调度：TACO、Taplink 与软件栅栏 机制名未能在公开来源核验

  • TACO（原文展开为 Topologically Anchored Causal Ommission）：基于拓扑序的 tile 就绪跟踪——计数器记录每个 subkernel 尚未完成的依赖数，计数归零即进入就绪队列，可被任意 CTA 领取。
  • Taplink：跨 subkernel 的 work stealing 通道。异构 kernel 大小差异大（GEMM 要占满整个 Grid 才到峰值，LayerNorm 只需 1 个 CTA）——按最大 kernel 配 CTA 则小 kernel 时空转，按平均配则大 kernel 拿不到峰值。解法是 CTA 常驻 + work stealing：大 kernel 全员参与；小 kernel 执行时，空闲 CTA 经 Taplink 提前偷做后续 subkernel 的 tile，实现大小 kernel 流水重叠。
  • 全局同步：硬件 grid.sync()（Cooperative Groups）受严格限制——必须 cooperative launch 且 Grid 不能超过 GPU 可同时驻留的 CTA 数。Megakernel 的 CTA 按"常驻"配置，满足前提；但实际实现用软件栅栏：CTA 完成后原子递增到达计数器，其他 CTA 自旋读取直到达标——更灵活，代价是自旋等待占用 SM。
  • 思想先驱 Henson（CMU，2016）：GPU 上的任务运行时——任务队列放全局内存，CTA worker 用 atomicAdd 领任务号（天然无锁），支持 work stealing，工作循环为 fetch → execute → commit。Megakernel 把这套机制收进单个 CUDA kernel 并把调度开销压到指令级。

3.5 设备端 Runtime 三大件与动态性

  • 任务管理：subkernel/task 生成、依赖跟踪（计数器）、就绪队列。
  • 同步：软件栅栏（到达/等待计数）。
  • 通信：通信协程（communication coroutines）——把发送/接收写成协程，等待 NVLink/网络数据时挂起并让出 CTA 执行权给计算 tile，数据到达后恢复，实现通信-计算重叠。
  • 动态 shape 与动态控制流（Mamba selective scan、agentic 工具调用分支、early exit、speculative decoding 分支）：把决策搬到设备端就地分支，避免 Host 观察输出→决定下一步→重新 launch 的往返，也避免静态图路线的重编译/回退解释执行。

3.7 代价与适用边界

  1. 寄存器压力：所有 subkernel 打包进一个 kernel，寄存器按最差情况（最大 kernel）分配，限制常驻 CTA 数。
  2. 编译时间：整图编译成单份 PTX，图越大越慢；tile/subkernel 划分调参会成倍放大编译次数。
  3. 调试困难：kernel 内 software 调度使 printf、Nsight 分析变难，内部可观测性差。
  4. 通用性：主要面向 Transformer 推理；对训练、完全动态图支持有限。

甜点区：低时延、小 batch（尤其 batch=1 交互式）推理收益最大；batch 增大、计算密度上升后 gap 占比下降、收益递减。

4.1 第一节：单 Kernel Agent 已经解决了什么（第一阶段成果）

"LLM 学会了 CUDA"只说对了一半：KernelBench、TritonBench 把问题变成可执行评测；Kernel Agent、CUDA Agent、KernelGYM 把一次生成变成编译—测试—Profile—修复的长程交互。KernelBench 提供 250 个 PyTorch 工作负载，用 fast_p 统计"正确且快于基线 p 倍"的任务比例，仓库已覆盖 CUDA、Triton、CuTe、TileLang、ThunderKittens 等后端；Level 1 单算子、Level 2 简单融合、Level 3/4 模型结构。TritonBench 给出 184 个真实 GitHub 算子——DSL 降低语法门槛，却没有消除布局、分块、访存和硬件映射的搜索难度。

  • CUDA Agent（arXiv:2602.24286）：数据合成 + 带技能 CUDA 开发环境 + 自动验证/Profile + 大规模 Agentic RL；论文声称 KernelBench 三个级别相对 torch.compile 的 faster rate 分别为 100% / 100% / 92%。

4.2 第二节：抽象跃迁——Agent 开始搜索一个微型 Runtime

单 Kernel 范式默认三个便利条件：任务边界明确、Kernel 退出后天然形成全局同步、最终输出可被 Host 读取——这三个条件在 Persistent Megakernel 中同时弱化。候选的形态从：

单 Kernel:  program = code + launch_config
Megakernel: program = task DAG + per-SM queues + instruction ABI
                  + memory plan + synchronization protocol + kernel knobs

传统的每算子 launch 序列把依赖、故障边界和全局 happens-before "免费"交给 CUDA Runtime；Megakernel 只启动一次、每个常驻 CTA 按指令流取任务，因而必须在设备内重建这些机制。搜索维度随之爆炸：从 tile size、warp 数、向量宽度，扩展到融合分组、任务粒度、SM 归属、依赖阈值、预取距离、共享内存页生命周期。反例：一个局部更快的 GEMV 可能因寄存器占用降低整核驻留数；一次看似合理的重排可能让 SM0 等待只能由 SM0 后续任务产生的计数（自锁）；过度融合会放大指令缓存与尾部负载不均。

4.3 第三节：受约束 IR——别让 Agent 直接改所有东西

最危险的方案是让 Agent 自由重写数千行 CUDA，同时还允许它修改测试和计时器——搜索空间巨大，错误候选还能"优化"验收标准。更可控的方案：冻结可信基座，只允许 Agent 改一个类型化、资源显式的 Schedule IR。AutoMegaKernel（MIT 开源 VM、指令、Schedule、验证器、评测与 Agent harness）即此思路：Agent 的主要编辑面是 tiling、fusion_grouping、sm_assignment、pipelining_depth、page_allocation、线程数与共享内存预算，而不是任意同步代码；固定 ABI 限定输入、输出、wait 和参数容量；单条指令不得私自碰 counter 或启动子任务。

这类 IR 的意义不是比 CUDA "更高级"，而是故意不完备：牺牲任意表达力，换来可枚举、可验证、可归因的搜索空间——Agent 可以探索性能策略，却不能创造未声明的通信边。CAKE（arXiv:2608.12629）同方向：把 warp role、数据移动、同步和 pipeline 暴露为硬件显式、可诊断的 IR。边界：AMK 的"正确性 by construction"是对冻结可信基座的静态图检查，不是机械化形式证明。

4.5 第五节：中间状态 Oracle——最终 logits 正确还不够

融合抹掉了算子边界，也抹掉了天然观测点。只比较最终 logits 有三类盲区：误差可在后续运算中抵消；等长测试无法发现 ragged batch 的位置广播；固定输入容易诱发硬编码和跳算。KernelBench-Verified（arXiv:2607.16241）进一步提醒：测试分布和 TF32 基线一改变，原本显眼的速度优势可能消失。

ForgeMegakernel 的答案：独立 mid-state test oracle——从配置预先派生字节数、精度契约和容差；Agent 只能修改 kernel 源码和 notes，不能修改 evaluator。由于 KV cache 本就必须落全局内存，Oracle 可逐层读取 K/V 行定位第一次分歧，无需物化每个寄存器值。三个无容差功能测试：① logits 必须有限；② 在 KV 写游标后注入噪声，输出必须 bit-identical（暴露越界读）；③ ragged batch 每个 lane 必须使用自己的 position。数值层面以 FP64 forward 定标，比较逐层 KV 与 top-64 log-softmax；性能层面由 Host 按模型配置核算实际应读字节与 MBU，拒绝 Agent 自报。边界：Forge 未开源，其完整 Oracle 实现只能视为论文主张。

4.6 第六节：Profile 闭环——从总时长到可行动证据

单 Kernel 慢时，ncu 能指出 occupancy、访存合并、stall reason；Megakernel 在 Nsight Systems 中可能只是一条长横条——总延迟或 MBU 只能说"慢"，不能说是哪个 opcode、哪条依赖、哪个 SM 尾巴造成的。Profile 必须以语义 region 而非 kernel launch 为主键。Argus（arXiv:2609.12299）正面处理：用户标记语义 region 与所需信号，系统保持 region identity 穿过编译、执行和测量变体，编排互不干扰的多次采样，再关联 compiler / hardware / system 三路证据并记录来源与归因歧义。论文数字：44 个 persistent GEMM/attention 配置中改善 39 个；使 AlphaEvolve 几何平均提升从 5.4% 增至 8.9%；TinyLlama-1.1B persistent decode 上带 Argus 的 Agent 达 1.65 ms/token（无 Argus 为 4.92）。可靠闭环不应把几百个原始 counter 塞回提示词，而应先形成语义诊断（read amplification 为何偏高、哪些 SM 在等 counter、哪个阶段扩大 tail spread、寄存器增长是否减少 resident CTA），测量系统保留 run id、环境、diff 与证据，正确性、稳定性与统计显著性共同通过才晋级。

4.7 第七、八节：AMK 与 Forge 互补；验证是一组分层契约

AMK 强调"先把 Agent 限制在可静态检查的 Schedule IR 内"，解决无人值守搜索最危险的死锁/race 面；Forge 强调"用十个渐进 milestone（M0–M9：单算子/层/整栈功能正确 → 单次 Persistent Launch → 每 SM 细粒度指令流 → Counter 依赖替代 Grid Barrier → Shared-memory Buffer Pool → 长序列稳定性）教 Agent 长成高性能 Megakernel，并用独立中间态 Oracle 验证融合过程"。两者共同说明：Megakernel Agent 不是更大的代码生成器，而是三个系统的组合——受约束合成器、独立验证器、硬件测量控制器。

4.9 第十节：结论——下一代优化 Agent 搜索的是执行制度

第一阶段（KernelBench/TritonBench → CUDA Agent/KernelGYM）让模型能在真实 GPU 上反复生成、编译、验证和优化单个 Kernel；第二阶段（AutoMegaKernel、ForgeMegakernel、Argus）把动作空间上升到设备端任务图，验证从最终输出扩展到静态并发性质和中间状态，Profile 从 launch 名称扩展到语义 region。真正的抽象跃迁：单 Kernel Agent 搜索"怎样计算一个函数"，Megakernel Agent 搜索"整张图在设备上如何生存和推进"——必须同时回答工作分配、依赖协议、存储生命周期、可观测性和故障隔离。LLM 负责提出高假设；受约束 IR 压缩危险自由度；静态 Validator 阻止死锁与 race；独立 Oracle 守住语义；Argus 式 Profile 把硬件证据送回搜索。缺少任何一环，都很难把漂亮的 demo 变成可无人值守运行的优化系统。可信 Agent 的标志不是"永远生成成功"，而是能明确区分 SUPPORTED / REJECTED / ABSTAIN / FALLBACK，并为每个结论留下可重放证据——动态 LoRA、未支持算子、硬件代际变化出现时，回退到 CUDA Graph + 成熟算子库，而不是强行进入 Megakernel。

5.3 优化生命周期：回合、触发条件与四道门

  • 触发条件：编译指标（图断裂率、guard 失效重编译率、缓存命中率下降）；Kernel 指标（算子耗时占比 roofline、显存峰值、bank conflict）；并行指标（TP all-reduce / EP all-to-all 通信占比、PP bubble、EP expert 负载不均）；服务指标（P99、吞吐/卡、TTFT、KV cache 命中率）。
  • 动作分级（低风险先行）：低风险=LayerNorm/RoPE 融合、GQA KV 布局、重计算策略、编译 pass 顺序；中风险=W8A8/AWQ 量化、TP/PP/EP 度数调整、tile 重调；高风险=W4A16、自定义 kernel 替换核心算子、MoE expert 重分片。

5.4 决策数字（并行/量化/Kernel/服务，全部带口径）

并行通信量公式

  • TP 每层通信量（前向+反向）：\( \approx 8\,b\,s\,h\,\dfrac{p-1}{p} \) bytes（b=batch, s=seq, h=hidden, p=TP 度）——TP=2/4 时通信占比经验值 30–40%（千卡 NVLink/NVSwitch 集群）。
  • EP 每 token all-to-all：\( \approx 2\,E\cdot\mathrm{topk}\cdot h \) bytes（E=专家数，topk=路由数）；大 batch 下与 GEMM 的重叠度决定收益。
  • SP 每层 all-gather + reduce-scatter：\( \approx 4\,b\,s\,h \) bytes（与 TP 联用降低 LayerNorm/Dropout 通信）。
  • PP bubble：\( \approx \dfrac{p-1}{m+p-1} \)（m=micro-batch 数；m=8、p=4 时约 5–10%）。
  • 每卡显存 = 权重 \( \dfrac{2N\ \text{bytes（FP16/BF16）}}{\text{并行度}} \) + KV cache \( 2\,L\,H_{kv}\,d_{head}\,s\,b \) bytes + 激活与临时缓冲。

6. 第五篇：《Agent for Inference Systems：从自动调参到安全自治运维》（主线四）

结论先行（原文）：Agent 已能优化局部闭环，但还不能接管生产。研究重心已从"替工程师改参数"扩展到"造系统"；统一全自治截至 2026-09 仍未成熟，可落地形态是受策略约束的分层控制系统。

6.1 问题：为何比传统 AutoML 更难

  • 多目标强耦合：TTFT、TPOT/ITL、端到端延迟、吞吐、每百万 token 成本、能耗、模型质量、公平性；约束来自显存、GPU 拓扑、SLO、租户优先级、上下文长度、突发流量。增大 batch 提吞吐却恶化尾延迟；提高 KV cache 占比扩大并发却压缩 CUDA graph 与 workspace；更激进量化提速也可能破坏任务质量。
  • Agent 不能只读 dashboard"猜参数"：需建立因果假设，区分排队、tokenization、prefill、decode、通信、KV 分配与外部工具时间，用干预实验排除伪相关。Agent 应用的端到端等待可能根本不在 GPU。

6.5 Autellix：目标函数修正 已核验（arXiv:2502.13965，NSDI'26）

把 Agent 程序而非孤立 LLM request 作为一等调度对象：拦截程序提交的 LLM 调用、注入程序级上下文，按程序历史调用做抢占与优先级（解决请求级和程序级队头阻塞）。相同延迟下相对 vLLM 等基线程序吞吐 4–15×。含义：

  • 控制面应优化"任务完成时间"与"有效程序吞吐"，而不只是 token throughput——一个占用 GPU 很少但卡住整条 DAG 的短调用，可能比长批处理更应优先。
  • 容量规划随之改变：Agent session 在工具执行期间空闲数分钟甚至数小时却仍持有状态；最优策略可能是卸载状态、缓存工具结果、将 CPU sandbox 靠近数据，而非继续堆 GPU。
  • 统一控制面必须覆盖 LLM 与非 LLM 资源，但每类资源需要独立 actuator 和故障域。

6.6 安全：把 Agent 当作高能力内部攻击者

  • 推理运维 Agent 天然跨越数据面、供应链与控制面；prompt injection 可能藏在用户输入、日志、模型卡甚至 issue 中；本地媒体路径、任意远程 URL、插件和自定义 kernel 都扩大执行面（SGLang 文档明确建议对不可信多模态请求设媒体域名 allowlist；vLLM 文档将本地媒体路径标为安全风险）。默认Agent 的自然语言上下文不可信。
  • 权限分级：L0 仅解释 → L1 只读诊断 → L2 沙箱实验 → L3 预批准参数有限 canary → L4 双人审批执行拓扑/权重/代码变更。凭证必须短时、任务绑定、最小权限。
  • Agent 无权修改：验证器、指标定义、基线、审批策略、审计日志。生产网络 egress allowlist；构建环境无生产 secret；制品以 digest 部署并生成 SBOM；紧急 kill switch、最大 GPU/费用预算、最大流量比例、最大并发变更数都由 Agent 外部执行。

条件可用受限自动调参：固定引擎版本 + 参数白名单内，AutoTuneBench 式协议做离线/影子优化，自动 canary 与回滚可试点
研究前沿代码与策略生成（VibeServe、RoofLang、Simthesizer、Autopoiesis）需沙箱、形式/属性验证与人工批准

务实路线四步：① 统一 telemetry schema 与实验账本 → ② 只读诊断 Agent → ③ 开放测试集群与参数白名单 → ④ 小流量在线动作。度量用 MTTR、错误预算消耗、错误诊断率、回滚成功率、"单位有效收益所需实验成本"，而不是"Agent 对话是否像专家"。

三类基础设施（本篇核心论点）：① 可验证的世界模型（RoofLang/Simthesizer）；② 可信的测量制度（AutoTuneBench/InferenceBench）；③ 可约束的执行控制面（引擎 adapter、canary、rollback、RBAC）。VibeSys 式专用系统生成与 Autopoiesis 式在线演化只有嵌入这三层，才可能从精彩 demo 走向可靠运维。终态判断："Agent 驾驶、人类监督、确定性护栏兜底"，而非删除 SRE 值班表。

7. 第六篇：《评测、验证与生成门禁：如何证明 Agent 优化真的有效》（支柱）

核心命题："跑出一个更快数字"不等于优化成立。错误的 TF32 设置会制造弱基线；公开 shape 无法泛化到内部 shape；单次测速无法区分信号与噪声；有 paper、有 dataset、有 timing 但没消除混淆变量，依然可能"假优化"。信任 = 流程 × 证据。

7.1 四级基线体系

基线类别含义要求
弱基线 weak手写朴素实现 / 供应商默认配置必须替换，避免虚高加速比
强基线 strongcuBLAS/cuDNN/cuBLASLt、CUTLASS、Triton autotune、TVM、vendor 库（CANN 等）、已发表方法最优配置；部署形态对齐（GPTQ vs GGUF 精度对齐、agent 优化图 vs 原图）作为对照上限
生产基线 production与线上真实负载一致（internal shapes、真实 batch 分布、真实 KV 压力）最终验收标准
未调参基线 untuned不改算法只调环境变量/编译选项/权重布局隔离环境收益与算法收益

先决条件（版本与温度）：锁定软件版本（CUDA/cuDNN/PyTorch、编译选项 AVX2/AVX512/TF32）、硬件（GPU 型号、MIG、时钟频率/功耗墙/散热）、随机性（种子、dropout、GEMM 算法选择）、竞争负载（GPU 利用率、SM occupancy、NCCL 通信与其他 kernel 抢占）。稳定性定义：相同 shape 与精度下相对固定基线的加速比波动 < 5%。

7.2 测量方法三要素与统计纪律

  • 预热 warmup（排除 JIT 编译、缓存填充瞬态）；缓存控制（L2 cache flush，固定 buffer 状态）；同步（cudaDeviceSynchronize / torch.cuda.synchronize()——异步 launch 后必须同步再计时）。以 Triton do_bench 为范式。
  • 统计：多次运行取中位数或截尾均值（trim 0.2）；报告 bootstrap 95% CI；Tukey 1.5×IQR 剔除异常值；报告 GPU/驱动/CUDA/PyTorch/时钟环境。
  • 公平性：同一 GPU 同一时隙或分时复用、同一编译选项、同一测量脚本、同一 shape 集合。

有效性检验：从单点数字到统计证据

reps = 100
for i in range(reps):
    t_new = time(f_new)   # 新实现
    t_old = time(f_old)   # 基线
# 配对样本：同一迭代内 new 与 old 背靠背，减少环境漂移
statistic, p_value = wilcoxon(samples_new, samples_old)   # 非参数成对检验
if p_value < 0.05: print("显著快于基线")
speedup = median(t_old) / median(t_new)                   # 效应量
report(speedup, ci_95)

两类错误：Type I（把无效优化判为有效）/ Type II（把有效判为无效）。单次测量 → 单点数字，无法区分信号与噪声；正确做法：多次运行 → 分布。

7.3 生成门禁：数值正确性与精度守恒

  • 正确性判定：torch.equal（逐位一致，理想）或 allclose 容差判定，公式 \( |a-b| \leq \mathrm{atol} + \mathrm{rtol}\cdot|b| \)。
  • 容差参考：fp16 rtol=1e-3 / atol=1e-5；bf16 rtol=3e-2 / atol=2e-3；tf32 rtol=1e-2 / atol=1e-2。
  • 量化类验收：perplexity 回归（ΔPPL ≤ 0.1 或 ≤1% 相对）、下游任务 accuracy 回归（MMLU、GSM8K 等）、KV cache 量化用同文本对比（ROUGE-L / 编辑距离）、权重与激活量化用单层 MSE。
  • 合成基线警示：合成数据上自测自评的加速比，不能直接外推到真实负载。

7.4 稳定性、泛化性与端到端

shape 矩阵：公开 shape（HuggingFace、Triton benchmark suite）× 内部真实 shape（业务真实 batch/seq 组合）的 B×S×H 全矩阵测试，要求无形状退化（原文示例矩阵全部 speedup ≥ 1.5×，如 8×4096×4096：3.2→2.1ms=1.52×；32×4096×4096：6.8→4.1ms=1.66×；16×8192×4096：8.9→5.6ms=1.59×）。

7.5 报告规范：最小可复现 checklist（8 项）

  1. 环境锁定：nvidia-smi、CUDA、驱动、PyTorch 版本日志
  2. 基线说明：类型（弱/强/生产/未调参）+ 配置细节
  3. 测量规范：预热、缓存控制、同步、统计方法
  4. 正确性验证：allclose 容差 + 精度回归结果
  5. 稳定性：多轮 shape 矩阵重复实验
  6. 泛化性：公开 shape → 内部 shape 外推验证
  7. 端到端：L1→L2→L3 全链路指标
  8. 结论与限制：适用边界、失败案例（结果报告须含失败/退化案例与 speedup 区间而非单点）

总结（原文）：优化声明 = 基线 × 测量 × 统计 × 正确性 × 端到端，五项俱到才能宣布"有效"。单点数字会骗人，分布与矩阵不会。谁能证明，谁就能复现；谁能复现，谁就能信任。对 Agent 的根本启示：外部奖励（"数字变快"）必须约束在可信评测流程之内，否则 Agent 会在有缺陷的评测中"合法地"学到假优化。

10. 综合洞察与趋势判断

以下判断综合系列原文（含其三条推断）与本报告的外部核验证据：

  1. 优化单位扩大的本质是"把系统软件搬进设备、把 Agent 搬进系统软件"。Megakernel 把 Host/Runtime 搬进 GPU；Agent for X 把工程师的判断搬进闭环。两条线在"设备端任务图搜索"处汇合——这正是 2026 年新工作（Event Tensor、Weave、Ada-MK）密集涌现的位置。
  2. 低时延是 megakernel 路线的第一战场，也是当前商业价值最清晰的位置。所有实测高收益都出现在 batch=1 / 小 batch / decode / 交互式场景（H100 78% 带宽、1.5× 级加速、AGI 交互时延直接受益）；吞吐型大 batch 场景收益递减。对低时延业务的启示：优先级排序应该是 decode 路径 > prefill > 吞吐。
  3. Agent 的能力边界已经从"生成代码"移到"定义与守住验证制度"。单 Kernel Agent 搜索"怎样计算一个函数"；Megakernel Agent 搜索"整张图在设备上如何生存和推进"（工作分配、依赖协议、存储生命周期、可观测性、故障隔离）。下一代优化 Agent 搜索的对象是"执行制度"，而不是代码文本。
  4. "故意不完备"的 IR 是让 Agent 安全探索的关键设计。AutoMegaKernel 把 Agent 的编辑面限制在枚举旋钮（tiling、fusion_grouping、sm_assignment、pipelining_depth、page_allocation、线程数、共享内存预算），换取可枚举、可验证、可归因的搜索空间——Agent 可以探索性能策略，却不能创造未声明的通信边。这是"约束先于生成"范式最有说服力的实证（7,160 对抗 Schedule 零错误接受）。
  5. 验证正在分层化、契约化。从"最终输出 allclose + 单次计时"扩展为：静态并发性质（死锁/race 图检查）→ 中间状态 Oracle → 执行轨迹等价 → 语义 Region 归因（Argus）→ 真实 serving 回归。任何单一验证器都无法覆盖全部故障层；可信验证是一组分层契约，而非一个工具。
  6. 测量可信度是被低估的主战场。InferenceBench（Agent 输给简单超参搜索）与 AutoTuneBench（10.6× vs 2.03× 的基线把戏）共同指向：当前最大缺口不是 Agent 的知识，而是实验纪律、多样化搜索、best-so-far 管理与反作弊测量协议。这决定了 agent 优化能否产出可信收益。
  7. 目标函数正在从"快"变成"约束下的多目标 Pareto"。延迟/显存/能耗/编译成本/泛化范围/交互性（RoofLang 的吞吐×交互性双目标）；decode 必须分短/长上下文、小/ragged batch、kernel-only/step-no-sampling/e2e 分别报告——否则 Agent 只优化最有利的一个 cell。
  8. "用 Agent 优化系统"与"为 Agent 优化系统"双向汇流。Autellix（程序级调度 4–15×）与 AgentSysBench（5/10 应用非 LLM 主导、工具结果缓存省 19.3% 搜索延迟）说明：agentic workload 改变了推理系统的正确设计目标——program completion time、状态卸载、工具缓存、DAG 感知调度。低时延系统的下一轮收益很可能来自这里，而不只来自 kernel。
  9. 生产终态是"Agent 驾驶、人类监督、确定性护栏兜底"。三件基础设施决定落地速度：可验证的世界模型、可信的测量制度、可约束的执行控制面。在线自演化（Autopoiesis 式）必须嵌入不可变 artifact + 独立 safety controller + 慢速审批轨，否则不可上线。
  10. 失败处理能力（SUPPORTED / REJECTED / ABSTAIN / FALLBACK）是可信 Agent 的标志。保留退化路径（回退 CUDA Graph + 成熟算子库）比强行进入 Megakernel 更重要；可信 Agent 不是"永远生成成功"，而是能为每个结论留下可重放证据。

11. 风险清单与反模式

技术风险

  • 数字外推陷阱：把 batch=1 的 2.5× 宣传为通用加速；跨组件"最高值"相乘；跨论文排名。
  • 弱基线假优化：TF32 设置错误、naive PyTorch 基线、合成数据自测自评。
  • reward hacking：Agent 复制基线、硬编码输出、少算部分计算来"变快"——安全检查与 Oracle 必须在 Agent 不可写的边界之外；失败也要进 ledger，避免幸存者偏差。
  • 正确性盲区：只验最终输出不验执行轨迹——罕见调度下的 race/deadlock 会在生产爆发（megakernel 最昂贵的错误是"永不返回"）。
  • 经验池过拟合：旧经验在新硬件/新版本失效。

工程与管理风险

  • 寄存器压力/编译时间/调试困难（megakernel 三大代价）被低估。
  • 供应链风险：Agent 生成代码 = 不可信制品（SAST、依赖锁定、SBOM、沙箱构建缺一不可）。
  • prompt injection 经由日志/模型卡/issue 进入运维 Agent 上下文。
  • 回滚设计缺位：KV 格式/并行拓扑/engine 变更无法原地撤销，需双集群切流与 warm capacity。
  • 把"对话像专家"当验收标准，而不是 MTTR/回滚成功率/单位收益实验成本。

12. 行动建议（面向低时延推理团队）

结合本系列的证据与"低时延"业务方向，按投入产出排序：

  1. 先建测量制度，再谈 Agent 优化。落地 F 篇框架：四级基线（弱/强/生产/未调参）、warmup+L2 flush+同步三要素、100 次配对采样 + Wilcoxon 检验 + speedup 中位数与 95% CI、shape 矩阵（含内部真实 shape）。这是所有后续工作的地基，且能立刻消除现有评测里的水分。
  2. 把 batch=1 decode 路径列为 megakernel/融合优化的第一目标。评估 SGLang/vLLM 当前 decode step 的 kernel 数与 launch 开销占比（用 Nsight Systems 拉时间轴），对照 1–2 μs gap × 上百 kernel 的量化模型，确定收益上限；关注 Hazy Megakernels、ForgeMegakernel（已集成 SGLang）、Ada-MK 等开源进展。
  3. 用"受约束 IR + 独立 Oracle"的模式引入 Agent。不要让 Agent 直接改任意代码：把优化面收敛到枚举旋钮（tile/并行度/量化档/调度参数），静态检查前置（拒绝死锁/race/非法配置），数值门（atol/rtol + PPL/任务回归）一票否决，四道门（build→correctness→benchmark→serving）全部过后才进灰度；所有候选可回退。
  4. 对 agentic 应用做一次"非 LLM 瓶颈体检"。参照 AgentSysBench 方法拉 request-level critical path：统计工具调用等待、sandbox 状态、tokenization、排队占比；优先做工具结果缓存、状态卸载、P/D 分离——这些收益（2–3× 级）可能比改 kernel 更快到手。
  5. 建立实验账本与经验池。每条实验记录模型/checkpoint 哈希、GPU/驱动/编译器、IR 与二进制哈希、种子、shape 分布、精度契约、验证结果、计时范围、原始 profile、基线版本与 diff；失败候选连同原因入库。这是 Agent 跨回合学习的唯一可靠载体，也是防止"区分不了代码变快/输入变简单/少算/机器漂移"的唯一手段。
  6. 权限分级先行：从 L0 只读诊断 Agent 起步（自动归因、配置 lint、trace replay、容量三态分析），验证器/指标/基线/审计日志永远放在 Agent 可写边界之外；kill switch 与预算由外部执行。
