TEMPO 深度阅读笔记 —— 相图、Makespan 调度与「代理失配」

对象：TEMPO: Makespan-Aware Expert-Parallel Load Balancing Across Memory- and Compute-Bound Regimes（arXiv:2608.13057，v2，2026-08-14）——KlingAI Research（快手可灵）的服务侧 EP 调度器。它是本目录 UltraEP 笔记 §13 里那条标 U 的「TEMPO 批评」的正主。本文与 UltraEP 笔记同体例：Part I（§0–§8）按「问题 → 实测发现 → 形式化 → 方案总览 → 对照关系 → 实验 → 局限」单线精读；Part II 收录阅读中产生的问题逐题详解。证据标注：V 一手核对（论文 v2 HTML 全文 / arXiv 版本页）R 合理推断U 待核实。整理：2026-09-17。

1. 问题：两个「代理」都会失配

1.1 EP 同步结构与可回收时间

每个 MoE 层：router → dispatch all-to-all → grouped expert GEMM → combine all-to-all，层末同步。decode 服务跑在 CUDA graph 下，负载相关项就是 grouped GEMM；层时间 = $\max_g t_g$，再乘以几十层。实测每 batch 的瓶颈 GPU 常态性跑到均值的 1.5–2×——「平均均衡」（placement 的职责）与「本 batch 均衡」（dispatch 的职责）之间的差，就是可回收时间V。

1.2 两类现有调度器与它们的隐含假设

家族代表均衡的量隐含假设
token 代理EPLB（放置）/ LPLB / UltraEP每 GPU token 数专家耗时 ∝ token 数
激活代理METRO每 GPU 激活专家数专家耗时 ∝ 激活副本数
权重移动MoonEP搬权重换取完美 token 均衡权重搬运可被摊薄/重叠

TEMPO 的核心实测发现：两个假设在真实硬件上都不成立，而且失效方向随 batch 规模翻转。同一 batch 上四种代理调度的时间差中位 1.4–1.6×（p95 至 1.7×）V：

1.3 混合 regime 是常态而非角落

用校准出的 $n^*$ 当分类器统计四个真实负载 trace：decode 档（128–512 token/GPU）下 92–100% 的 batch 同时包含 ≥20% 的平坦区专家和 ≥20% 的线性区 token；$B$=512 时平坦区专家占激活的 47%、线性区专家承载 91% 的 token。转接带不是角落案例，而是 decode 的常态工作区V。

2. 实测根基：两段 max-affine 代价模型

2.1 两个 regime 的物理机制

对 SGLang/DeepEP decode 实际使用的 DeepGEMM fp8 masked grouped GEMM 做 $(G, \text{tokens-per-expert})$ 网格微基准（CUDA graph 计时、权重拷贝轮换防 L2 复用、固定 expected_m 冻结 JIT）V：

  • 平坦区（$n_e < n^* \approx 156$）：耗时几乎不随 token 数变化，只随激活副本数 $G$ 线性——每多激活一个专家就要把它的权重从 HBM 流一遍。地板 $b$ 的物理验证：专家 FFN 参数量 $3 d_{\text{model}} d_{\text{ff}}$（DSv3 fp8 = 44.0 MB）÷ HBM 峰值带宽 = roofline 下限 13.1 µs，实测拟合 $b$=14.8 µs，恰在 roofline 的 1.13–1.24×（即 80–88% 峰值带宽）——地板就是权重流V。
  • 线性区（$n_e > n^*$）：grouped GEMM 按 128-token M-tile 处理，代价是 token 数的阶梯函数（[1,128] 内平坦、129 跳一阶）；细粒度实测显示后续台阶是亚线性的（同一专家的额外 tile 从 L2 复用权重，每边界 +11–24%），于是用一个参数 $b_2 \approx b/3$ 捕捉，得到 tile 感知模型V：
$$ t = \max\bigl(\underbrace{a + bG + b_2(T-G)}_{\text{激活/权重流}},\; \underbrace{c + \beta N}_{\text{token 计算}}\bigr), \qquad T = \sum_e \left\lceil \frac{n_e}{128} \right\rceil $$

tile 项把多 tile 区的模型误差从 ~10%（最差 25%）降到 2.0%；decode 区（$n_e \le 128$）不受影响。两种模型的适用分界：decode 关掉 $b_2$，prefill 研究打开（4096–8192 token/GPU 的 recorded 路由上，tile 感知改变 97–99% batch 的解、中位省 4.5–6.0%）。

2.2 误价的不对称性

iso-token 集合（同 N 不同 G）真实时间差最高 2.5×（Qwen3）/ 7.6×（DSv3）；iso-activation 集合 18× / 24×。方向上的不对称：METRO 深入计算区最高错到 2.8×；token-LP 落进内存区错 5–17%——这解释了为什么生产界先注意到 METRO 方向的失败V。碎片化被硬件双倍计费：碎片让专家权重被重复加载（$b$ 收费）、又各自向上取整到 tile（tile padding 收费）。

3. 形式化与相图：每个代理「在家乡都好」的数学镜像

3.1 Fixed-charge makespan 问题

$$ \min \; \max_g \; \max\Bigl(a + b \textstyle\sum_e z_{e,g},\;\; c + \beta \textstyle\sum_e x_{e,g}\Bigr) $$

约束：$\sum_g x_{e,g} = n_e$，$x$ 只能落在 $R(e)$ 上。这是一个带固定费用的 makespan 问题：激活一个副本要付固定费 $b$，token 按线性费 $\beta$ 计价。

  • Theorem 1（NP-complete）：仅 2 个 GPU、全复制、$a=c=0$ 时已 NP-complete——归约自 Balanced PARTITION：max 结构把单一预算 $T$ 变成「激活基数上限 K=m/2」与「token 容量上限 C=W」两个同时成立的背包约束V。
  • Lemma 1：$a=b=0$ 时目标退化为 $\min\max_g N_g$——正是 token-LP，即 LPLB/UltraEP 的调度目标；Lemma 2：$c=\beta=0$ 时退化为 $\min\max_g G_g$——半匹配问题。问题在每个纯 regime 内是多项式的，只在 regime 相互作用时 NP-hard——这正是「各代理在家乡都好、转接带需要新算法」的系统观察的数学镜像V。
  • Theorem 2（加性近似保证）：全复制下，按 token 降序轮转放置的整专家算法 $A_3$ 满足 $M(A_3) \le \mathrm{OPT} + \max(b, \beta n_{\max})$；换算成相对下界的乘性误差：recorded decode batch 上中位 4.1%、最大 7.7%（4× token 规模时 31%）。

4. 完整方案：从淳朴 dispatcher 到 TEMPO

4.1 淳朴方案与它的失血点

如果只讲逻辑，TEMPO 的淳朴形态是四拍：量（每窗口收集各专家 token 计数）→ 解（在代价模型下解 makespan 最优的 token 分配）→ 发（生成逻辑→物理的 dispatch 表）→ 跑（decode 图内按表把 token 概率性地分到副本）。直接实现会死在三处：① 求解嵌在 decode 图内——每层每步付内核与集合通信代价；② 代价值是拍脑袋的——模型错一格，解就错一格；③ 表的更新与图的重放竞争——GIL 与竞态。下面的组件逐一止血。

图 1 · TEMPO 端到端（2026-09-23 更新：由 Mermaid 时序图升级为 drawio）：关键路径（红：图内唯一融合 kernel）与离路径的计数→求解→表发布（绿），校准（黄）喂代价模型。求解在关键路径外（对照 UltraEP：求解在每层关键路径上）。drawio 源文件：assets/tempo-deep-reading.drawio（TEMPO 端到端数据流 sheet）。

4.2 改进 A：黑盒校准——代价表是「拟合」出来的，不是推导的

在部署管线上跑 $(G, N)$ 网格、记录 $(G, N, t)$、交替_assignment_ 拟合两段 max-affine，每种（kernel, dtype, 硬件）组合约 10 分钟。这一步是承重墙而非仪式：整管 refit 一次迭代即收敛（β 0.358→0.356），而错校准（GEMM-only 参数用在带未融合逐 token kernel 的管线上）在 B=128 时让 TEMPO 亏 16%V。对比 UltraEP：UltraEP 的输入是精确整数计数（门控后天然确定），TEMPO 的输入是带参数的时间模型——两条路线的「地基」性质完全不同。

4.3 改进 B：tempo_fast 四阶段求解器

  1. 代价感知贪心播种：专家按 token 降序，整只放到边际代价最低的副本上——整只放置很关键：切碎冷专家正是 token-LP 的错误；
  2. 增广链再平衡：平坦区瓶颈是 $\max_g G_g$，单步移动会「按下葫芦浮起瓢」，用 1–2 步增广链（半匹配增广路径的截断版，即 $\beta\to 0$ 极限的最优算法）；
  3. 瓶颈局部搜索 + 部分迁移：线性区把 token 从瓶颈 GPU 挪走——整专家迁移与三分搜索的部分切分（固定切点数时目标分段线性单峰），迭代 ≤300 次；
  4. 带 1% 切换容差的集成：token-LP 与（复制允许时的）轮转证书 $A_3$ 都是可行点，按模型打分，只有好 >1% 才切换——「不比 token-LP 差 1% 以内」由构造保证，且把 Theorem 2 的加性保证传递给部署求解器。

质量与代价：对 10 秒 HiGHS MILP 的 makespan 比值均值 1.005 / p95 1.024 / max 1.033；相图网格上 ≤1.0102。求解时间 1.9 ms（B≤256，纯 Python）——比 MILP 快约 550×，大 B 时 LP 分支 ~20 ms，全部在关键路径之外。消融证明每个阶段守一个不同 region、无可删V：去掉部分迁移最高劣化 16.3%（EP32 转接带）、去掉增广链 2.7%（中 B 平坦区）、去掉集成 4.5%（EP64 深计算区）。累积消融更有趣：两个非平凡阶段互为对方的 regime 守卫——地板区（B=128）增广链贡献全部 −9.8%，流量区里链单独反而把 0.883 恶化到 0.940（流量绑定后再均衡激活数是错的）、由局部搜索修复。

4.4 改进 C：通信与拓扑感知

把模型从 GEMM 扩到整个 MoE 块：all-to-all 随 rank 收到的 token 数扩展，代价加第三段 max-affine：$t_g = \max(a+bG_g,\; c+\beta N_g,\; c_2+\gamma N_g)$。逐项消融证明各项不是单调叠加：去掉流量项在 B=512–1024 损失过半收益；去掉地板项与裸 token 均衡完全等价（激活项没了，剩下的项都随 token 单调）——地板项是唯一让目标函数不可被 token 归约的项。多节点上，flat 表在 all-to-all 瓶颈点比 static 还差 3.5%；两段式改造（先解 makespan、再按「同节点优先」做源→副本配对，每 GPU 负载可证不变、只改配对）翻正为 +4%（Qwen3 端到端 +7.2%），且每源节点一张表、图内 kernel 不变。

4.5 改进 D：SGLang 集成——图内零边际成本

  • 图内只有一个融合 kernel：概率分发（经持久化逻辑→物理表）与计数收集融合，累积计数器免掉清零/拷贝内核；CUDA graph padding 行被掩码（否则退化路由会伪造幻影热专家——这个 bug 在 LPLB 已发布路径里同样存在，TEMPO 顺手修了）V；
  • 求解走独立进程而非线程：refresher 线程侧流快照计数器 → 专用 gloo 组跨 rank 聚合窗口差分 → numpy-only worker 进程求解。进程内版本因 GIL 争用端到端损 8–10%，离进程消除；
  • 无双缓冲的竞态安全：空闲专家行不动、无效副本列两张表里都是零、kernel 用时逐行重归一化——读到新旧混合的行仍是合法分布；单行撕裂最坏和为零，此时回退到「在持有该专家的副本上均匀分布」（每行一次比较）。代价是 ≤200 ms 陈旧度换关键路径零成本；
  • 集成只触碰 7 个 patch 点，在 EPLB 重平衡下存活V。

5. 与 UltraEP / MoonEP / METRO 的对照关系

5.1 对我们第一篇笔记最重要的三条

  1. UltraEP 被「括号」住了，而非被推翻：Lemma 1 说明 UltraEP 的 quota 目标在 dispatch 粒度上与 token-LP 重合，论文原话是 Table 4 "brackets" 它——在计算区，TEMPO 的解与 token-LP 重合（即 UltraEP 的目标是对的）；在 decode 地板区，token 计数完全失配（激活盲），UltraEP 式的逐层权重物化在 95–107 µs 的整层预算下没有落点。这给了 UltraEP 笔记 §13「为什么只覆盖 prefill 不覆盖 decode」一个定量版本的答案R。
  2. 之前标 U 的批评获得准确语义：v2 的 Related Work 不再说 UltraEP「cannot be reproduced」这类含混措辞，而是精确到目标函数层面——quota ≡ token-LP，属 token 代理家族；家族性缺陷（decode 激活盲）与工程可用性是两回事V。
  3. MoonEP 是「另一个半球」：MoonEP 搬权重换完美 token 均衡；附录 H 实测 decode 规模下仅权重预取就 283–502 µs，超过整层预算（DeepEP dispatch+combine 95–107 µs）——「内存区里搬一个专家的权重约等于使用它的代价」；计费口径下更是 +277–320%。但在 prefill 规模 + 极端偏斜（MaxVio ≳ 20）时 MoonEP 反超 DeepEP（2.55 ms 平坦 vs DeepEP 2.23→2.85 ms 恶化）——两个机制恰好划分了相图V。

7. 相图哲学与局限（论文自陈 L1–L6）

  • L1 头条数字在模型空间：相图/规模图来自校准模拟器，两端用墙钟锚定，中段迁移误差 2–6pp——所以 Testbed A/B 的墙钟闭环是论文的方法论支柱；
  • L2 规模：serving 证据止步 8 GPU 与 2×8（EP16）；DSv3 全尺度（EP32+、58 层深乘）仍是外推；
  • L3 赢区是有条件的，且已被画出来：小专家 bf16 无增益（实测）；赢区条件——放置陈旧度落在预测的 batch 带内（B=64–256，夹住 $B^*_{\mathrm{a2a}}$≈300）、复制预算紧、图内 token-LP 在位、多节点 EP 且专家计算占比足；v1 重映射税 9–20% 在 v2 缩到 2–11%，由数据路径而非求解器支付；
  • L4 静态校准：kernel/驱动更新要重跑 10 分钟校准（流程已自动化、一次收敛）；
  • L5 (G,N) 模型的地板：DeepGEMM 在均匀 per-slot 负载下更快——模型外的第三维决定近平局，这正是集成用 1% 带的原因；作者拒绝为单个 kernel 的怪癖过拟合，标记为未来工作；
  • L6 部署系统有意不追理论最优：NP-hard 所以 tempo_fast 是有界启发式；异步解上一窗口计数（定价 ~2pp 端到端）；whole-slot 粒度、继承 EPLB 放置而不联合优化。作者的原话值得整段记住：「这些权衡绑定之处，对我们数字的诚实解读是零税平局而非胜利——这正是相图的处方。」

全文的真正主张（摘要原文）：「A phase diagram, not a universal win, is the claim: it predicts both outcomes before deployment.」——主张的不是「TEMPO 全面更快」，而是一张部署前就能预言「谁在哪赢、赢多少、什么时候零收益」的相图。

Part II 问题详解

本篇的问答来自对 TEMPO 的阅读过程，以及它与 UltraEP 笔记的互文。符号在公式下或 §0.2 定义。

对照与互文组

Q1 「token 数」和「激活副本数」两个代理为什么都会失配？

因为专家耗时对两者的依赖关系随 $n_e$ 换段（§2）：$n_e < n^*$ 时 grouped GEMM 的耗时被权重流地板锁死——把 8 个 token 分给一个专家和把 120 个 token 分给它耗时几乎一样（Testbed B 实测 $n$=1 与 $n$=64 的曲线重合），此时决定耗时的是激活了几个副本（每个副本付一次 $b$ 的权重流费），token 均衡是盲的；$n_e > n^*$ 后 GEMM 进入线性区，耗时由 token 数（精确到 128-tile）决定，此时激活计数是盲的——把一个 512-token 的热专家整只放在某 GPU 上，激活计数再好看，那块卡也跑成 straggler。更糟的是混合是常态（§1.3）：同一个 batch 里冷专家在地板区、热专家在线性区，任何单一代理都只顾得上一半。TEMPO 的目标函数（两个 max 嵌套）让每一项「只在它自己的 regime 里说话」，这就是它与所有单一代理的分野。

Q2 TEMPO 是怎么「批评」UltraEP 的？这对我们第一篇笔记的 U 标注意味着什么？

v2 的批评精确且克制，分三层：① 归类：UltraEP 属 token 代理家族——它的 quota 目标在 dispatch 粒度上与 token-LP 重合（Lemma 1），因此 Table 1/4 的 token-LP 列就是它的行为上界与下界的「括号」；② 家族缺陷：token 计数在内存区（decode）是激活盲的——这解释了 UltraEP 为什么只覆盖训练与 prefill（那里 token 数与耗时的线性假设成立）；③ 不否认工程价值：v2 没有延续 v1 时期「training-side balancers cannot be reproduced end-to-end on a serving stack」的宽泛措辞（我们 UltraEP 笔记 §13 标 U 的那句），而是收敛为目标函数层面的归类。对第一篇笔记的修正：那条批评的准确含义是「目标函数在 decode 失配」，而非「工程上无法落地」——U 标注解除，两个系统在相图上各据一个半球。

Q3 问题被证明 NP-complete，为什么 1.9 ms 就能解到 MILP 的 1.005 倍？

三个原因叠加：① 最优性只在转接带值钱：Lemma 1/2 表明纯 regime 内问题退化为多项式可解的 token-LP / 半匹配——NP-complete 只出现在 regime 相互作用处，而实际 batch 里「需要真正组合搜索的专家」只是一小部分，其余贪心即近优；② 四阶段各守一个失败模式（§4.3），消融证明它们在各自 region 里不可删，且互为对方的 regime 守卫；③ 1% 切换容差把「模型无法分辨的近平局」交给模型外的第三维（DeepGEMM 偏好均匀 per-slot 负载，L5）裁决，避免为模型噪声支付真实的切换开销。加上求解在关键路径外（毫秒预算宽松 550 倍），「NP-hard」与「毫秒可用」并不矛盾。

Q4 为什么「搬 token」在 decode 免费、「搬权重」不免费？（与 UltraEP 扇出问题的对照）

decode 的整层 MoE 预算只有 95–107 µs（DeepEP dispatch+combine，8 GPU 实测），而地板区里「使用一个专家」的成本 ≈ 把它的权重流一遍（$b$ = 权重字节 ÷ HBM 带宽 ≈ 使用成本的 80–88%）。所以 搬这个专家的权重 ≈ 再付一次使用费——MoonEP 的权重预取单独就 283–502 µs，超预算 3–5 倍；且副本收到的是 decode 的零星 token，永远攒不回搬运成本（计费口径 +277–320%）。而搬 token 的边际成本是几字节的路由表更新，且 TEMPO 把它进一步压成图内查表。这与 UltraEP 笔记 Q10A 的扇出讨论同构：权重移动的成本结构决定了它只在「每层计算足够长、能摊薄搬运」的 prefill/训练区划算——UltraEP 的 300 µs 预算在 prefill 的数千 token 下成立，MoonEP 的预取在 MaxVio≳20 的极端偏斜 prefill 下成立（此时 DeepEP 自己都会恶化到 2.85 ms），decode 则是 token-moving 的独占领地。

Q5 相图怎么读？

相图的横轴是 batch 规模 $B$（每 GPU token 数），纵轴是路由偏斜 $s$（或复制倍数/EP 度/模型形状作面板），每个格子里标注：① 字母 = 该格最优的固定策略（M = METRO 式激活均衡，L = token-LP，E = EPLB 式均匀）；② 底纹/数字 = TEMPO 相对该最优固定策略的增益。读法三条：字母翻转的边界就是代理失配带，且边界位置可由 $B^*=\min(B^*_{\text{avg}}, B^*_{\text{hot}})$ 解析预测（偏斜大时热专家机制让边界左弯）；TEMPO 的增益集中在边界带（混合区），纯 regime 内归零；底纹为负（TEMPO 更差）的格子不超过 −0.3%（1% 集成带内）。部署意义：上线前用校准模型算一遍相图，就知道自己的工作点落在哪个区、值不值得上自适应调度。

Q6 dispatch 表更新为什么不加锁/双缓冲也是安全的？

因为表被设计成「任何时刻、任何中间状态都是合法分布」：① 空闲专家的行不被更新（新旧一致）；② 无效副本列在旧表和新表里都是零；③ in-graph kernel 在使用时逐行重归一化——读到旧行、新行、或新旧混合的行，都是一个合法的概率分布；④ 唯一的危险是单行撕裂后恰好和为零，此时 kernel 回退为「在持有该专家的副本上均匀分布」（每行一次比较）。最坏后果是一个 batch 用了陈旧或均匀的切分——绝不会路由到没有该专家副本的 GPU，也不会除零。这是用「≤200 ms 陈旧度」换「关键路径零同步」的明码标价，与 UltraEP 的 epoch ready-flag（§8.3）同属「放宽一致性换零 barrier」的家族，只是一致性窗口从微秒级放大到毫秒级——因为 dispatch 决策本来就容忍窗口级陈旧（流行度漂移远慢于 200 ms，§5.8 的敏感性扫描验证了这一点）。

Q7 这篇与 UltraEP 笔记怎么互文？两篇合起来看的世界观是什么？

三个层次：① 时间尺度互补——UltraEP 在每层关键路径上花 ≤300 µs 做精确均衡（训练/prefill 的步时以秒计，付得起）；TEMPO 把求解挪到关键路径外、以 ≤200 ms 陈旧度换取 decode 图内零成本（decode 步时百微秒级，付不起任何图内代价）；② 目标函数互补——UltraEP 的 quota≡token-LP 在计算区恰是最优（Lemma 1），TEMPO 的 max-affine makespan 在混合区接管；相图把「谁对」变成了 $B$ 与 $n^*$ 的比较，不再需要站队；③ 方法论互补——UltraEP 的输入是门控后的精确整数（零模型误差），TEMPO 的输入是十分钟校准的时间模型（4–8% 误差、墙钟闭环验证）：能拿到精确计数时用精确计数，拿不到（或代价不成比例）时用校准模型。合起来读：负载均衡的完整地图 = placement 层（EPLB，平均）× dispatch 层（LPLB/UltraEP/TEMPO/METRO，本 batch）× 移动对象选择（token vs 权重），而相图是这张地图的图例。
