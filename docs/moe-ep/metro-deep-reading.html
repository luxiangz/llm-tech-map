METRO 深度阅读笔记 —— memory-bound decode 下「均衡激活专家，而非 token」

阅读对象：METRO（Minimum Expert Token ROuting），论文《Efficient MoE Serving in the Memory-Bound Regime: Balance Activated Experts, Not Tokens》（Yale × Princeton × CMU × NVIDIA，2025-12，arXiv:2512.09277）。一句话：decode 是访存受限的，每步耗时由「这张卡加载几份专家权重」决定——那么路由该均衡的是激活专家数，不是 token 数；METRO 让每个专家的 token 全部走单一副本，贪心最小化每 GPU 激活副本数，固定 SLO 下 decode 吞吐最高达 EPLB 的 4.11×。

证据标注：V = 一手核对（论文原文，2026-09-23 抓取 arXiv HTML 版）；R = 合理推断。注意：2025 年末预印本，尚待同行评审，结论以正式版与复现为准。

系列定位：与 EPLB（放置/复制）、TEMPO（makespan 感知调度）同谱系；METRO 被 TEMPO 引用为「memory-bound 方向的互补工作」。

1. 一页结论

  • 洞察：MoE decode 的操作强度比 H100/B200 的算力/带宽比低最多两个数量级——运行时由专家权重的加载量决定。即使 batch 达 11K token，激活值的内存流量也不到专家权重流量的 0.6%。所以一张卡上 MoE 层的耗时 ≈ 该卡被激活的专家副本数 × 单份加载时间，token 数几乎不影响。V
  • EPLB 在 decode 上的反作用：token 均衡把每个热专家的 token 均摊到所有副本 → 每张卡都被迫激活副本。实测 1.5× 复制下 EPLB 使每 batch 激活专家数 +30%、decode 延迟 +14%、吞吐 −10%；复制率越高越糟。V
  • 方案：min-exp-routing——为每个有 token 的专家选一个副本（Lemma 1 证明整路由不劣），使每 GPU 激活副本数最小化。贪心实现（锁 + 选计数最小的卡）在单 SM 上微秒级完成，比最优解（二分 + 二部图匹配，116–290 µs，太贵）最多差 10.9%，但比 EPLB 路由最多低 42.3%。V
  • 工程闭环：top-k 前用 all-gather 替代 all-to-all 让每卡看到全局 token（NVLink 上 2MB ≈ 3 µs，可忽略）→ 全量 top-k → 贪心选副本 → dispatch。集成进 vLLM 的 decode CUDA Graph，零额外 kernel launch；不改 top-k、不改放置/复制、不改权重、无需重训。V
  • 效果：真实 vLLM 8×A100：decode 延迟 −1.9%～−21.8%、吞吐 +0.7%～+21%；固定 SLO 下（batch 可放大至 4×）吞吐 1.98×–4.11× EPLB；PD 分离下仍比无复制好 4.3–5.0%。V
  • 边界：只对 decode 换路由（prefill 仍走 EPLB 均分）；batch ≤ 64 的极低延迟场景网络延迟主导、全 TP 反而最优，EP 均衡失去意义。V

2. 背景：decode 为什么是 memory-bound，以及这意味着什么

论文的证据链（全部一手核对）：V

  1. batch < 64 时 MoE decode 的可达操作强度比 H100/B200 的机器平衡点低两个数量级；batch 1024 时仍低 47%～3 倍。三个趋势叠加：MoE 稀疏化让权重跨 token 复用变少、长上下文压缩 batch、新 GPU 算力/带宽比继续上升。
  2. 解析模型：decode batch 即使 11K token，激活值流量 < 专家权重流量的 0.6%——「计算多少 token」几乎免费，「加载多少份权重」才是时间主体。
  3. 推论：$\text{耗时}(\text{GPU}_g) \approx \sum_{i \in \text{激活}} \text{加载时间}(E_i)$，均衡目标应是激活副本数 $\lambda_g = \sum_i y_{i,g}$，而非 token 数。

3. 核心洞察：token 均衡在 decode 下是「负优化」

图 2 · 玩具例子：6 个 token 去有 2 副本的 E2。EPLB 均分（3+3）token 完美均衡但两卡都激活 E2；METRO 全走一份（6+0）token 不均衡但只有一卡加载权重——memory-bound 下后者更快。drawio 源文件：assets/metro-deep-reading.drawio。

4. 形式化：min-exp-routing 与 Lemma 1

\[ \min\ \lambda \quad \text{s.t.}\ \ \sum_i y_{i,g} \le \lambda\ \forall g;\quad \sum_g x_{i,g} = T[i]\ \forall i;\quad A_{i,g}=0 \Rightarrow x_{i,g} = y_{i,g} = 0;\quad x_{i,g} \le T[i]\, y_{i,g} \]

$A \in \{0,1\}^{N \times G}$ 是放置矩阵（EPLB 决定，METRO 不改），$x_{i,g}$ 是专家 $i$ 发到卡 $g$ 的 token 数，$y_{i,g}$ 指示是否激活。Lemma 1：任何可行解都能转成「每专家 token 全走单一副本」且 $\lambda$ 不增——所以整数问题安全地退化为「每专家选一个副本」。这正好是 LPLB 那个 LP 的 0/1 端点解：LPLB 允许比例分流（训练期 token 数就是目标），METRO 证明在 memory-bound 下端点解才是对的。R

最优算法为什么不用：归约为带资格约束的 identical-machine 调度后，可二分 $\lambda$ + 二部图匹配求精确解。实测 CPU Dinic 116–129 µs（相对单层 FFN 时间 31–43%）、GPU push-relabel 290 µs（86–104%，问题太小喂不饱 GPU）——每层每 batch 一次的频率下完全不可接受。V

5. Algorithm 1：锁保护的并行贪心

初始化：每 GPU 计数器 L[g] = 0，锁 ℓ_g；y[i,g] = 0
for 每个有 token 的专家 i（并行）:
    G_i = { g : A[i,g] = 1 }              // i 的候选卡（放置矩阵决定）
    按全序获取 G_i 中所有锁                // 保证原子性、避免死锁
    g* = argmin_{g ∈ G_i} L[g]            // 贪心：去激活数最少的卡
    y[i,g*] = 1；L[g*] += 1
    释放所有锁
  • 复杂度 $O(|A|)$，计数器与锁全在 shared memory（test-and-set）；并行度 = 专家数（Qwen 128、V3 256），单 SM 一个线程块足够；
  • 质量：激活数 ≤ 最优 × 1.109，且 ≤ EPLB 路由 −42.3%（上界刻画见论文 §4.4）；
  • 与 LPLB 的对称性很有意思：LPLB 求比例、精确、100 µs（训练）；METRO 求整数、近似、微秒（decode）——两个预算约束下的两种答案。

5.1 通信改造：all-gather 替代 all-to-all

贪心需要全局 $T[1..N]$，而传统 EP 在 top-k 后 all-to-all、各卡只见本地 token。METRO 把顺序换成：先 all-gather 全量隐状态（decode batch 小：32 token/GPU × fp16 也才 2MB，600 GB/s NVLink 上 ~3 µs，远低于 NCCL 集合通信几十到上百 µs 的固定开销），每卡对全量 token 跑 top-k（冗余计算 <1%），本地即可执行 Algorithm 1，再按结果 dispatch。V

图 1 · METRO 端到端（decode 路径）：all-gather → 全局 top-k → 单 SM 贪心 → 单一副本路由；prefill 路径不动（仍 EPLB）。drawio 源文件：assets/metro-deep-reading.drawio。

6. 与 EPLB 的组合方式

  • 放置与复制完全复用 EPLB（含冗余专家机制），METRO 只替换 decode 阶段的「逻辑专家 → 物理副本」选择；
  • prefill 是 compute-bound，token 均衡仍是对的——prefill 保留 EPLB 路由；PD 分离部署天然让两边各用各的路由；
  • 复制率越高，EPLB 的激活膨胀越重、METRO 相对收益越大；METRO 下激活数随复制率持平甚至下降——复制从「decode 负担」变回「纯红利」。V

8. 边界与局限

  • 极低延迟 SLO（batch ≤ 64）：网络延迟主导、不再 memory-bound，全 TP（而非 EP）最优——EP 负载均衡整个问题消失；论文也未观察到 Pareto 最优的流水线并行配置；V
  • 贪心非最优：激活数最多超最优 10.9%（论文给出刻画）；上界仍随复制率非降；V
  • 非均衡耗时尚未建模：不同专家 GEMM 时间不同（与 LPLB 的局限同源），TEMPO（2026）用 max-affine 时间模型继续推进这一方向——见 TEMPO 深读；V

10. 快问快答

Q1：METRO 会改变模型输出吗？

不会。top-k 选哪些专家、专家权重都不动；变的只是同一逻辑专家的多副本里 token 走哪份——副本数学等价。无重训、无精度影响。V

Q2：token 不均衡了，compute-bound 的场合怎么办？

所以 METRO 只换 decode 路由，prefill 保留 EPLB 均分——两个 regime 各用各的正确目标。这也是「PD 分离」不只是资源隔离、更是路由策略分离的论据。R

Q3：为什么不像 LPLB 那样按比例分流？

比例分流会同时激活两份权重（0.6 那份也要加载整个专家）——在 memory-bound 下比例就是浪费。Lemma 1 证明了端点解（全走一份）不会更差，这是 LPLB 与 METRO 最深的分歧点：token 数目标 → 内点最优在比例；权重加载目标 → 最优在端点。V

Q4：贪心的锁会不会成为瓶颈？

锁只在同候选卡集的专家之间竞争，粒度是卡级计数器；专家数（128–256）远小于 token 数，单 SM 足够。论文未报告锁争用成为瓶颈。R

Q5：与 TEMPO 什么关系？

正交互补：METRO 均衡「激活专家个数」（每份耗时同质假设）；TEMPO 建模「每份耗时不齐」（HBM streaming vs grouped GEMM 两种 regime）做 makespan 感知调度，并在论文中把 METRO 作为相关正交工作引用。V
