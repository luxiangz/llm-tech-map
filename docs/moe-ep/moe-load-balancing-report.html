MoE 基础、演进、问题与负载均衡前沿

从稠密 FFN 到稀疏 Mixture-of-Experts，梳理基础细节、完整问题清单，并按“训练期路由 / 系统调度 / 推理期”三条主线整理前沿负载均衡论文、关键技术方案与原文链接。

一页结论

  • MoE 的本质：用可学习路由器在每层动态选择少量专家，使总参数量大幅增加，但单 token 激活参数量与计算量近似不变。
  • 最大矛盾：“专家专业化”天然希望路由集中，而“硬件效率”天然希望负载均衡，两者存在张力。
  • 负载均衡演进：辅助损失（GShard/Switch）→ 更细粒度/全局批次损失（DeepSeekMoE、Qwen3）→ 无辅助损失偏置（DeepSeek-V3 Loss-Free）→ 组合优化与凸对偶框架（BIP、φ-balancing、ALF-LB 理论）→ 系统级实时调度（LLEP、UltraEP、TEMPO）。
  • 落地建议：训练期优先采用 global-batch LBL + sequence-level balance + device-level balance 作为稳健基线；追求性能上限再用 Loss-Free bias 或 $\phi$-balancing；推理/后训练阶段单独处理 EP 负载，使用容量感知、复制量化、动态重路由或实时精度调节。

1. MoE 基础与演进

稠密 Transformer 的每一层 FFN 对所有 token 使用同一套权重。MoE 将 FFN 替换为一组专家 $E_1,\ldots,E_N$，由路由器 $G(x)$ 为每个 token 选择少量专家。这样模型总参数可以很大，但每个 token 只激活 $K \ll N$ 个专家，因此计算量远小于参数量的增长。

\[ y = x + \sum_{i} g_i(x) \cdot E_i(x) \]

2. MoE 基础细节

2.1 标准稀疏 MoE 层

设隐藏维度为 $d$，专家数为 $N$，每 token 激活 $K$ 个专家。第 $l$ 层 MoE 输出为：

\[ y = \sum_{i \in \mathrm{TopK}} g_i(x) \cdot E_i(x), \qquad g_i(x) = \operatorname{softmax}_i\left(W_r x + b_r\right) \]

其中 $W_r$ 是路由器参数，$E_i$ 通常是一个与稠密 FFN 同结构的 MLP（常见 SwiGLU/GeLU FFN）。为了保证稀疏性和可训练性，实践中有：

  • Noisy gating：在 logits 上加可训练噪声，帮助探索；
  • Top-K 硬选择：只保留分数最高的 K 个专家，其余置 0；
  • Expert capacity：每个专家在一个 batch 内最多处理 $C = \mathrm{capacity\_factor} \times \mathrm{tokens\_per\_batch} \times K / N$ 个 token（训练期机制，推理默认不设，详见 2.6 第 5 层）；
  • Token drop：超出 capacity 的 token 被丢弃或仅走残差连接。

2.3 经典负载均衡损失

第 1 步：它要防什么——路由坍缩的正反馈

训练初期路由器接近随机，某个专家可能分数略占优势，随后进入“富者愈富”的循环：分到更多 token → 训练更充分、拟合更好 → 主损失更倾向把 token 路由给它 → 分数更高 → 分到更多 token。不干预的话，$N$ 个专家会退化成一两个专家干活：参数大量闲置、过载专家触发 token drop。Switch Transformer 的辅助负载损失就是在主损失之外加一个“均衡惩罚”，把这个正反馈掰成负反馈。

第 2 步：两个统计量——$f_i$ 是传感器，$P_i$ 是执行器

设一个 batch 内有 $T$ 个 token，路由器对每个 token 输出全部 $N$ 个专家的 softmax 概率 $p(t,i)$：

\[ f_i = \frac{1}{T}\sum_{t=1}^{T} \mathbf{1}\!\left[\arg\max_j\, p(t,j) = i\right], \qquad P_i = \frac{1}{T}\sum_{t=1}^{T} p(t,i) \]
  • $f_i$（被选中频率）＝“实际发生了什么”：统计专家 $i$ 真正收到多大比例的 token。它本质是数数，不可导，只能当传感器用；
  • $P_i$（平均路由概率）＝“路由器的软偏好”：全部 token 给专家 $i$ 的概率均值，可导，梯度能顺着 softmax 传回路由器权重，是执行器。

Switch Transformer 的辅助损失把两者乘起来（$\alpha$ 为权重，论文取 $10^{-2}$）：

\[ L_{\mathrm{aux}} = \alpha \cdot N \cdot \sum_{i=1}^{N} f_i \cdot P_i \]

第 3 步：为什么是乘积 $f_i \cdot P_i$

单用哪一个都不行。只用 $f_i$：它是离散计数，梯度为零，无法训练。只用 $P_i$：概率均衡 ≠ 负载均衡——例如 8 个 token 各以 0.5 的概率给专家 A（总权重 4、负载 8），4 个 token 各以 1.0 给专家 B（总权重 4、负载 4），两个专家在概率面上完全均衡，实际负载却差一倍。这正是 Shazeer 2017 只约束 importance 的损失留下的坑，Switch 用 $f$ 来补。

乘起来之后，对 $P_i$ 的梯度为：

\[ \frac{\partial L_{\mathrm{aux}}}{\partial P_i} = \alpha \cdot N \cdot f_i \]

读法是：“把专家 $i$ 的概率再推高一点要罚多少，取决于它实际被挤爆的程度。”热专家 $f_i$ 大 → 梯度大而正 → 路由器被强力压低它的 logit；冷专家 $f_i \approx 0$ → 梯度几乎为零 → 完全不惩罚它涨概率。再叠加 softmax 归一化（每个 token 的概率和为 1）：热专家 logit 被压下去的瞬间，同 token 上冷专家的概率自动抬升 → 部分 token 的 Top-1 翻转到冷专家 → 下一个 batch 的 $f$ 更均匀 → 梯度惩罚随之减弱，直到接近均匀时稳定。$f$ 提供真实负载信息，$P$ 提供可导把手，构成完整的负反馈回路（见上图）。

第 4 步：为什么乘 $N$——归一化

完美均匀时 $f_i = P_i = 1/N$，代入得 $\alpha \cdot N \cdot N \cdot \frac{1}{N^2} = \alpha$：无论专家数是 8 还是 256，均匀时的损失恒为 $\alpha$，取值范围固定为 $[\alpha,\ \alpha N]$（全坍缩到单个专家时取最大 $\alpha N$），因此权重 $\alpha$ 不必随模型规模重调。

另一视角：路由器“果断”时 $f \approx P$，此时 $N\sum_i f_i P_i \approx N\sum_i f_i^2$，即 $N$ 倍的“两个随机 token 撞进同一专家”的概率——最小化它就是在最小化负载集中度（与 2.5 节的 Gini 系数同族），最小值在均匀分布处取得。

第 6 步：实践细节与两个缺陷（引出后续演进）

  • 每个 MoE 层各有一个路由器、各算一份，总损失 = 交叉熵 $+\ \alpha \sum_l L_{\mathrm{aux}}^{(l)}$；
  • $f$、$P$ 按当前 micro-batch 统计（这一点是后续被改进的把柄）；
  • Top-2 场景公式照用，只是每个 token 贡献 2 次选择，$\sum_i f_i = K$，最小值变为 $\alpha K$，仅影响刻度不影响机制。

缺陷一：梯度干扰。aux 损失与语言建模损失共享路由器参数，为均衡可能强行把 token 推给不擅长它的专家，伤主任务质量 → 引出 DeepSeek Loss-Free Bias（5.2 方案 B）：不动损失，直接在 Top-K 前给过载专家的路由分数加偏置。

缺陷二：统计粒度太细。micro-batch 内强制均匀过于苛刻——一个全是代码的 batch 也会被要求把 token 摊给“医学专家”，压制专业化 → 引出 global-batch LBL（5.2 方案 A）与 DeepSeek 三层均衡目标：只在全局批次尺度要求总量均匀，允许局部批次偏科。

DeepSeek 系列进一步拆成三层目标：

  • Expert-level balance：专家间 token/概率均衡；
  • Device-level balance：同一设备内专家负载均衡；
  • Communication balance：设备间 token 通信量均衡。

2.4 并行与系统基础

  • Expert Parallelism（EP）：不同专家分布在不同 GPU，路由器选出专家后进行 all-to-all dispatch/combine；
  • Tensor Parallelism：专家内部按矩阵切分；
  • Capacity factor：控制每专家最大 token 数，是训练吞吐和掉 token 率之间的旋钮；
  • Inference 阶段：prefill 大 batch 下路由偏移更显著；decode 阶段专家权重访问、KV cache、内存带宽成为瓶颈。

2.5 常用评估指标

总览：两个家族 + 一个统一算例

负载均衡的评估指标分两个家族：分布均衡度指标（Gini、min-max ratio、utilization、imbalance ratio、CV——从经济学与运筹学借来的统计量，"家族通用、细节各家自定义"）与系统侧指标（throughput、makespan、p99、峰值显存——来自调度理论与服务运维，跨行业无歧义）。前者衡量"专家/设备间分得多匀"，后者衡量"最终快不快、省不省"。

本节统一用一个算例：$N = 4$ 个专家，某统计窗口内的 token 负载 $L = (40, 30, 20, 10)$，总量 100，份额 $s = (0.4, 0.3, 0.2, 0.1)$。另外注意"负载"本身的计量口径：按 token 数、按门控权重还是按实际计算毫秒计，不同论文可能不同。

Gini coefficient（基尼系数）

出身：经济学里衡量收入不平等的标准量（1912 年），MoE 论文借来量"专家间 token 分配的不平等度"。

\[ G = \frac{\sum_{i=1}^{N} (2i - N - 1)\, x_{(i)}}{N \sum_i x_i}, \qquad x_{(1)} \le \cdots \le x_{(N)} \text{ 为升序负载} \]

几何意义：负载累积曲线（Lorenz 曲线）与完美均匀对角线之间的面积占比。取值 0 为完全均匀，越大越集中；注意有限 $N$ 时全坍缩（单专家拿走全部）的 Gini 上限是 $\frac{N-1}{N}$ 而非 1，$N$ 越大才越接近 1。

算例：升序 $(10, 20, 30, 40)$，分子 $= (-3)(10) + (-1)(20) + (1)(30) + (3)(40) = 100$，分母 $= 4 \times 100 = 400$，$G = 0.25$。对照：均匀 $(25,25,25,25) \to 0$；全坍缩 $(100,0,0,0) \to 0.75$。4.1 节 LPR 的"Gini 从 0.70 降至 0.035"，即从高度偏斜调到近乎完美均匀。

min-max load ratio（最轻/最重比）

\[ \text{min-max ratio} = \frac{\min_i L_i}{\max_i L_i} \in (0, 1], \qquad \text{或其倒数形式} \ \frac{\max_i L_i}{\min_i L_i} \ge 1 \]

算例：$10 / 40 = 0.25$（倒数形式 $4.0$）。

最大的坑是方向不统一。本报告 4.1 节 LPR 的"min-max load ratio 提升至 0.70"是 $\le 1$ 形式（越大越好），4.2 节 UltraEP 的"imbalance 从 1.30–4.01 降至 1.01–1.04"是 $\ge 1$ 形式（越小越好）——两处口径互为倒数、优劣方向相反，对比任何两个方案的数字前必须先确认方向。

特点：直观，但只看两个极端点，中间 $N-2$ 个专家被忽略；某专家偶然收到 0 个 token 时比值直接归零，对噪声敏感。可视为 Gini 的"廉价替代"。

expert utilization（专家利用率）——最不标准化的一个

没有统一定义，常见三种口径：

  • 阈值法：负载超过公平份额 $1/N$ 的某个百分比（如 50%）的专家数 / $N$；
  • 非零法：收到过 token 的专家数 / $N$（最宽松）；
  • 熵法：把份额 $s_i$ 当概率分布，用 $\exp(H(s)) / N$ 作利用率，其中 $H(s) = -\sum_i s_i \ln s_i$，含义是"有效专家个数"占名义专家数的比例。

算例：阈值法（阈值取 $1/N$ 的一半即 12.5%）：$4/4 = 100\%$；熵法：$H \approx 1.28$，$\exp(H) \approx 3.6$ 个有效专家，利用率 $\approx 90\%$。同一负载两种口径给出不同数字——论文里看到 utilization 必须查它的定义。

imbalance ratio（不均衡比）——概念通用，公式半标准化

名字在 HPC/并行计算里用了几十年，见到即懂，但至少三种口径并存：

口径公式取值出处习惯
max / mean$L_{\max} / \bar{L}$$\ge 1$，1 为完美HPC 最经典，具理论含义
max / min$L_{\max} / L_{\min}$$\ge 1$，1 为完美MoE 系统论文常用
归一化损失$1 - \bar{L} / L_{\max}$$[0, 1)$，0 为完美HPC，表示浪费掉的并行效率比例

max/mean 的理论含义：并行调度中 makespan 由最重设备决定，理想情况每台设备分到 $\bar{L}$，因此并行效率的上界就是 $\bar{L} / L_{\max} = 1/\lambda$。$\lambda = 1.5$ 不只是"偏斜"——它直接说明这一层最多只能用到 $2/3$ 算力，其余 $1/3$ 在空等 straggler。按此读 UltraEP 的"从 1.30–4.01 降到 1.01–1.04"：从"浪费 23%–75% 算力"修到"浪费 1%–4%"。

算例：$\bar{L} = 25$，max/mean $= 40/25 = 1.6$（并行效率上界 62.5%）；max/min $= 4.0$；归一化损失 $= 0.375$——同一集群状态三个数，看起来像三个结论。

与 Gini/CV 的分工：imbalance ratio 只盯最重的那个点，对"中间分布长什么样"无感；Gini/CV 看全局形状但对单个 straggler 不够尖锐。系统论文常两个一起报：一个讲效率上界，一个讲分布健康度。

系统侧指标：throughput / makespan / p99 / peak memory

  • throughput（吞吐）：单位时间处理量。训练期通常 tokens/s（或 tokens/s/GPU、MFU）；推理期 requests/s 或输出 tokens/s；取稳态测量；
  • makespan（完工时间）：调度理论的经典目标 $C_{\max}$——所有设备中最后完成的时刻。EP 一层里就是"最重设备做完它的专家 GEMM"的时刻：均衡好则所有设备同时收工，makespan = 总工作量/总算力；偏斜时由 straggler 决定，其余设备空等；
  • p99 latency：时间窗内所有请求延迟的第 99 百分位（SRE 标准实践）。均值会掩盖长尾，而负载偏斜制造的恰恰是长尾——撞上热专家的那部分请求特别慢；服务 SLA 通常写在 p99/p999 上；
  • peak memory（峰值显存）：各设备显存占用的最大值。MoE 推理的特殊性在于热专家复制与副本缓存会撑爆显存（4.3 节 LLEP 的"4× 峰值内存下降"即此指标），所以单看吞吐不够。

这组指标定义唯一、跨行业无歧义，属于完全通用的工程指标。

2.6 从浅入深：MoE 架构内部原理

第 1 层：为什么需要 MoE

稠密 Transformer 的所有层、所有 token 都使用同一套 FFN。要提升容量，通常需要同步增加宽度和深度，计算量也随之线性/超线性增长。MoE 的思路是“把容量和计算解耦”：准备很多专家，但每个 token 只使用其中少数几个，因此总参数很大、单 token 计算基本可控。

第 2 层：MoE 层的基本数学形式

假设一个 Transformer 层原本有 FFN，MoE 版本把 FFN 替换为 $N$ 个专家和一个路由器。对输入 token 的隐藏向量 $x$：

\[ h = x + \operatorname{MoE}\left(\operatorname{RMSNorm}(x)\right), \qquad \operatorname{MoE}(z) = \sum_i g_i(z) \cdot E_i(z) \]

其中 $E_i$ 是第 $i$ 个专家，$g_i$ 是路由权重。稀疏 MoE 的关键是只对少量专家求和：

\[ g = \operatorname{softmax}\left(\operatorname{TopK}\left(W_r z\right)\right), \qquad \text{非 } \mathrm{TopK} \text{ 的 } g_i \text{ 被置为 } 0 \]

常见设置：$N=8, K=2$（Mixtral），$N=256, K=8$（DeepSeek-V3）。$K/N$ 越小，稀疏度越高，参数规模放大能力越强，但路由质量要求也越高。

第 3 层：专家内部长什么样

绝大多数 LLM MoE 的“专家”就是一个小型 FFN，而不是一个完整 Transformer 层。以 SwiGLU 为例，专家可写为：

\[ E_i(z) = W_{\mathrm{down},i}\left( \operatorname{Swish}\left(W_{\mathrm{gate},i} z\right) \odot \left(W_{\mathrm{up},i} z\right) \right) \]

其参数量约为 $3 \times d \times d_{\mathrm{ff}}$。这解释了为什么 MoE 能轻松把总参数做大：每个专家都拥有独立的三块矩阵，而每 token 只激活少数专家。

第 4 层：路由器与 Top-K 的细节

  • 路由 logits：通常由一层无 bias 的线性映射 $W_r z$ 产生；
  • Top-K：保留分数最高的 K 个专家，其余直接截断；
  • Softmax 归一化：对保留的 K 个分数做 softmax，得到可导的融合权重；
  • Noisy gating：训练初期可加入可学习噪声，帮助路由探索不同专家；
  • Expert bias / Loss-Free bias：在 Top-K 前给每个专家加偏置，用以在线调节负载。

为什么稀疏路由训练困难？因为 Top-K 是一个离散操作，普通反向传播只能把梯度传回被选中的专家；同时路由器和专家互相依赖，容易出现“一开始强的专家越来越强”的坍塌。

第 5 层：Capacity、Token Drop 与负载均衡

为了在 GPU 上做定长批量计算，通常给每个专家设置最大 token 容量：

\[ \mathrm{expert\_capacity} = \mathrm{capacity\_factor} \times \frac{\mathrm{batch\_tokens} \times K}{N} \]

当某专家收到的 token 超过容量时，多余 token 被丢弃或只走残差连接。容量太小会掉 token，容量太大则会浪费算力。为了减少偏斜，通常还要加负载均衡损失：

\[ L_{\mathrm{aux}} = \alpha \cdot N \cdot \sum_i f_i \cdot P_i \]

$f_i$ 是实际路由频率，$P_i$ 是平均路由概率。它推动二者都接近均匀。后来的 Loss-Free 方法则不把它放入损失，而是通过 bias 直接改变 Top-K 结果。

容量是训练期机制，推理默认不设。EP 训练需要预分配定长的 dispatch/combine 缓冲和规整的分组 GEMM，超容量的 token 被丢掉走残差，是预训练阶段可接受的“吞吐换质量”取舍；主流推理引擎默认 dropless——不设容量阈值，每个 token 的 Top-K 专家必然执行，因为推理掉 token 会直接损伤生成质量，且 decode 阶段每步 token 很少、天然不挤（prefill 大 batch 下才可能出现偏斜）。容量感知丢弃在推理期只是少数引擎与研究系统（见 4.3 节 Capacity-Aware Inference）的可选加速旋钮；EP 推理遇到过载更常用重路由与专家复制（LLEP、R&Q）而非丢弃。

第 6 层：从 GShard 到 DeepSeekMoE 的架构演进

GShard / Switch：把原 FFN 换成 $N$ 个等大小专家，Top-1/2 路由。优点是简单，缺点是专家之间冗余较大、专业化和均衡互相拉扯。

Mixtral：8 个专家、Top-2，总参数 46.7B，激活参数约 12.9B。它是开源生态中非常重要的工业参考。

DeepSeekMoE：两个关键改造：

\[ \text{细粒度切分：} N \rightarrow mN \text{ 个更小专家，每 token 激活 } mK \text{ 个} \]
\[ \text{共享专家：额外保留 } K_s \text{ 个所有 token 都经过的共享专家} \]

细粒度专家提高组合灵活性，共享专家吸收公共知识、减少 routed experts 的冗余。DeepSeekMoE 还引入 expert-level、device-level、communication-level 三层均衡目标。

DeepSeek-V3：每层 256 个 routed experts + 1 个 shared expert，每 token 激活 8 个 routed + 1 个 shared；路由采用 sigmoid affinity，再归一化，并用 Loss-Free bias 做负载均衡。总参数 671B，激活参数 37B。

第 7 层：训练时的并行数据流

训练大 MoE 通常同时使用数据并行、张量并行、专家并行、流水线并行。专家并行的一条 token 路径大致是：

  1. 每个设备计算注意力输出；
  2. 路由器产生每个 token 的目标专家；
  3. 执行 dispatch all-to-all，把 token 发送到对应专家所在设备；
  4. 各设备对本地专家做 grouped GEMM；
  5. 执行 combine all-to-all，把专家输出送回原 token；
  6. 残差相加，继续后续层。

负载不均衡时，某些设备的 dispatch 队列更长、专家 GEMM 更重，从而形成 straggler。因此训练期负载均衡既是模型质量问题，也是系统吞吐问题。

第 8 层：推理时的差异

  • Prefill：大批量并行处理 prompt，路由偏移和多模态 token 偏斜会被放大；
  • Decode：每步 token 较少，但所有专家权重都可能被访问，热专家/冷专家带来的显存和带宽不均衡明显；
  • 部署侧：常采用专家 offloading、专家复制、容量感知丢弃/重路由、动态精度、专家 re-layout 等方式。

5. 关键技术方案总结

5.1 负载均衡的四个层次

  1. 算法层：改损失或路由决策，让专家分布更均匀，同时保留专业化。
  2. 架构层：细粒度专家、共享专家、特征对齐/原型/eigenbasis 路由。
  3. 训练系统层：token 调度、专家 re-layout、设备间重平衡，降低真实 GPU 负载差异。
  4. 推理系统层：容量感知丢弃/重路由、专家复制与量化、动态精度，降低 straggler 与内存峰值。

5.2 代表性技术方案拆解

方案 A：全局批次负载损失（工程基线）

把 $f_i$ 从 micro-batch 改为 global-batch 同步统计。优点是保留传统 Switch LBL 的稳定性，又避免“每条序列都强制均匀”伤害专业化。适合作为新 MoE 项目的默认起点。

\[ L_{\mathrm{aux}} = \alpha \cdot N \cdot \sum_i f_i^{\mathrm{global}} \cdot P_i^{\mathrm{global}} \]

方案 B：DeepSeek Loss-Free Bias（性能优先）

不给主损失增加辅助项，而是在 Top-K 前对每个专家的路由分数加一个 bias，并依据近期负载指数移动平均在线更新。它不产生干扰梯度，兼顾质量与均衡。

\[ s_i \leftarrow s_i + b_i, \qquad b_i \leftarrow b_i - \gamma \cdot \left(\mathrm{load}_i - \mathrm{target}_i\right) \]

方案 C：组合优化/凸对偶（精确均衡）

BIP 用小规模 0-1 整数规划修正 Top-K；LPLB 用线性规划做 micro-batch token 调度；φ-balancing 则对全局路由分布最小化凸势函数，用 mirror descent 得到 EMA 形式的在线更新。适合对均衡度有硬指标要求的场景。

方案 D：结构稳定路由（可解释、免损失）

StableMoE 用两阶段蒸馏冻结路由；ERMoE 用正交 eigenbasis 重参数化专家，并以特征-基对齐分数替代自由 logits；LPR 用 latent prototypes 聚类路由。共同点是把“路由稳定性”从训练正则项升级为结构性质。

方案 E：系统级动态重平衡（训练与推理通用）

LLEP 动态把过载 rank 的 token/专家参数搬到欠载 rank；UltraEP 在 rack-scale 上每层实时重平衡；TEMPO 同时建模 HBM streaming 与 grouped GEMM，最小化 makespan。它们不改变模型权重，适合推理、后训练以及非平稳负载。

方案 F：推理期容量与资源重分配

Capacity-Aware Inference 用 token drop / expanded drop 处理过载专家；R&Q 复制热专家并对冷专家量化；ReaLB 按 rank 动态调整 FP4/FP8 精度。三者都能在不重训模型的前提下显著降低推理延迟。

5.3 落地选择建议

场景推荐方案理由
新 MoE 预训练，追求稳健global-batch LBL + sequence/device/communication balance工程成熟，专业化与均衡兼顾
大规模预训练，追求性能上限Loss-Free bias 或 φ-balancing减少 aux loss 干扰，提升质量
需要极强负载均衡保证BIP / LPLB / LPR每 micro-batch 或每层可近精确均衡
路由不稳定、可解释性要求高StableMoE / ERMoE / prototype routing结构级稳定，避免反复抖动
已有 MoE 训练吞吐低FineMoE/LPLB、UltraEP、LAER-MoE系统调度直接降低 GPU 空闲与通信等待
已有 MoE 推理慢、显存高Capacity-Aware Inference、LLEP、R&Q、ReaLB无需重训，直接处理实际路由偏斜
