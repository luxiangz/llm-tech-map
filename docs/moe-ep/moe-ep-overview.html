2背景与动机：为什么 MoE 大模型离不开专家并行

2.1 MoE 架构的“稀疏”本质

混合专家（MoE）把 Transformer FFN 层替换为「一个门控 router + 一组专家 FFN」：每个 token 经 router 打分后只激活其中少数专家。以 DeepSeek-V3 为例（技术报告 arXiv:2412.19437）：总参数 671B、每 token 激活约 37B；每 MoE 层 1 个共享专家 + 256 个路由专家、每 token 激活其中 top-8 路由专家。V（UltraEP 论文也确认其训练采样为 “DeepSeek-V3 (top-8 activated of 256 experts)”）

“稀疏”带来两个天然后果：权重体量大、激活量小（数百 B 参数基本都在各层专家 FFN 上）；路由分布不均匀（真实负载下少量“热专家”承接大量 token）。

2.2 并行选择：TP / DP / EP

  • TP：切分单个算子，通信随专家数爆炸，不适合大 MoE；DP/流水：各放一份完整权重，显存翻倍。
  • EP：把专家本身打散到多卡，每卡只持部分专家；token 选中异卡专家时须跨卡搬运（每 MoE 层一次 All-to-All dispatch/combine）。EP 暴露并行度大、算术强度高，是百 B 级 MoE 训练与服务的必然选择——UltraEP 论文的原话：large-EP（32/64 路）已成为训练与服务数百 B MoE 模型的必备手段。V

DeepSeek 官方《DeepSeek-V3/R1 推理系统概览》：大规模跨节点专家并行（EP）用于增大 batch size、隐藏传输耗时（open-infra-index 原文）。V

2.3 为什么 EP 高效却又“难”：三个痛点

痛点 A：专家负载不均衡 → “短板卡”拖慢整层

UltraEP 论文（§1）对失衡的三种显式表述：失衡放大为 ① 专家计算 straggler、② token All-to-All 瓶颈、③ 过载设备的激活显存尖峰；且“EP 度数越大，效应越复合，实际与理想吞吐的差距越大”。V TEMPO 论文则概括为“EP 服务中每一层都以最慢 GPU 同步”（arXiv:2608.13057 摘要）。V

失衡为什么在推理/服务中无法靠训练解决：DeepSeek-V3/R1 采用 aux-loss-free 训练（去掉辅助均衡损失，改为路由 bias + 序列级互补损失的 DeepSeek 配方，见 V3 报告）——训练时的均衡手段不保证推理流量均衡；且 prefill 阶段专家热度随「语义域 × 层 × 步」剧烈漂移（UltraEP §3 的实测观察），静态放置必然滞后。V

痛点 B：跨节点 All-to-All 与专家状态搬运的通信成本

EP 每层 dispatch/combine，且热专家复制/权重分发本身就是大流量（详见 §5 的 relay 设计背景）；跨节点只有慢速 scale-out 网络（UltraEP 论文：标准 RDMA 集群里高速 scale-up 仅限单台 4/8-GPU 服务器内）。V 因此 DeepSeek 先开源 DeepEP（低延迟 All-to-All 通信库），vLLM 亦把 DeepEP/NIXL 等作为可插拔 EP 通信后端。V

痛点 C：机柜级（rack-scale）整柜系统改变了设计空间

NVL72 / Atlas SuperPoD 一类的机柜级系统把 scale-up 高速域从“单台 4/8 GPU”扩到“整柜 64+ GPU”，使“整组 EP 待在一个高带宽域内”成为可能——这是 UltraEP 论文点明的范式转变：hot-path 实时均衡在物理上第一次可行（§5 详述）。机器之心报道概括为“互连够快之后，算力空转成为整柜系统新的浪费重灾区”。V

3问题形式化与解决空间总览

3.1 统一问题模型

把三个系统放进同一张“图纸”上：

  • E：某层逻辑专家数（如 V3 的 256 路由专家 + 共享专家）；M：EP 世界大小；S：每 rank 输入 token 数；K：每 token 路由的 top-k 数（MoonEP 记号）；
  • 物理实例：逻辑专家 e 可被复制到多个 rank（宿主集 ℋ(e)，UltraEP 记号），副本数 |ℋ(e)| 由“冗余/复制”决定；
  • 负载：某步中专家 e 承接的 token 数（S×K 摊到各专家）；
  • reroute 量：把源 rank 上属于 e 的 token 分给 e 的某个物理实例 t∈ℋ(e)——UltraEP 的 quota qe,t 即“实例 t 的最终 token 负载配额”。
目标：min  maxt Load(t)；约束：Σt∈ℋ(e) qe,t = 供给e、副本数 ≤ 冗余预算 R、q 可为切分粒度

三方案差异化为：

  • EPLB：负载取预测/历史值，离线求解“复制哪些专家 + 副本放哪”，reroute 交给引擎侧独立启发式（如 round-robin）；周期性重算。V（UltraEP 论文对 EPLB 的这一描述）
  • UltraEP：取gating 后的精确负载，在每个 microbatch × 每层实时求解 quota（复制与 reroute 联合优化），再用 RSN 原生通信执行复制与 token 重定向。V
  • MoonEP：先按真实路由做在线规划决定把各专家的 S×K 流量发给哪些动态冗余副本，保证每 rank 恰好 S×K token，然后零拷贝执行。V

3.2 两个贯穿性权衡

  • 冗余 vs 显存/带宽：副本提供调度自由度，但占显存（UltraEP 用跨层复用把单副本槽位压到 MB 级，§5.4）；EPLB 时代对副本显存的粗放管理正是 UltraEP 的改进点之一。V
  • 预测/周期 vs 精确/实时：EPLB 靠“历史滑动平均 + 周期重算”摊薄开销，但负载非平稳时滞后（UltraEP §3 实测：专家热度在 microbatch/层/数据域间剧烈漂移，DeepSeek 式路由补偿只削整体失衡、反而放大短期摆动）；精确实时方案把开销压进 hot path（UltraEP <300µs、MoonEP “negligible overhead”）。V

4方案一：DeepSeek EPLB —— 静态专家放置负载均衡器

4.1 身份与时间线

  • 仓库：deepseek-ai/EPLB（Expert Parallelism Load Balancer），核心实现单文件 eplb.py，MIT 许可。V（README 与 LICENSE 原文）
  • 发布：2025-02-27（DeepSeek 开源周第 4 天），与 DualPipe 同日，多数复盘同日第三项为 DeepSeek-Infra Profile-data；梁文锋参与开发见媒体报道（techweb 等）。V
  • 定位：DeepSeek V3/R1 服务技术栈的「放置/均衡层」，与 DeepEP（通信层）互补；DeepEP 官网设 EPLB 页面。V
  • README 自述（原文要点）：“As described in the DeepSeek-V3 paper, we adopt a redundant experts strategy that duplicates heavy-loaded experts. Then, we heuristically pack the duplicated experts to GPUs … thanks to the group-limited expert routing used in DeepSeek-V3, we also attempt to place the experts of the same group to the same node to reduce inter-node data traffic, whenever possible.”V

4.2 动机：推理期专家负载倾斜 + 负载预测的“尽力而为”

EPLB 面对的问题：EP 下不同专家热度不同（与当前 workload 相关），若 GPU 间负载失衡，最忙 GPU 决定整层步长。其解法不修改模型与 router，而是在服务部署期按“估计的专家负载”计算一个均衡的专家复制与放置方案。README 明确两点边界：V

  1. “the exact method to predict the loads of experts is out of this repo's scope. A common method is to use moving average of historical statistics”；
  2. 因此 EPLB 是对负载估计器 agnostic 的（UltraEP 论文亦评述：常见部署用近期路由历史 + 周期性 rebalance 来摊薄规划与重排开销）。V

这条“预测 + 周期”路线的软肋正是 UltraEP §3 的批判点：真实流量下专家热度非平稳漂移，预测过期 → 放置不准 → 残差失衡（§5.2）。

4.3 方案设计：两种策略（Hierarchical / Global）

注意一个重要更正：v1.0 版把“two types of strategies”理解为「复制算法 + 打包算法」，读到 README 原文后确认它指的是两种适用场景不同的放置策略：V

策略适用条件 / 场景做法（README 原文要点）
Hierarchical Load Balancing（分层）服务器节点数能整除专家组数时；可用于 prefill（专家并行度较小）① 先把专家组均匀打包到节点（利用 group-limited routing，均衡各节点负载）→ ② 在节点内复制专家 → ③ 把副本打包到各 GPU（均衡卡间负载）
Global Load Balancing（全局）其他情况；可用于 decode（专家并行度较大）无视专家组、全局复制热专家，再把副本打包到各 GPU

接口与示例（README 原文）

主入口 eplb.rebalance_experts，输入为逐层负载矩阵与放置规模参数，输出 phy2log / log2phy / logcnt（物理↔逻辑专家映射与副本计数）：

import torch, eplb
weight = torch.tensor([[90,132,40,61,104,165,39,4,73,56,183,86],   # 每行=一层，每列=该层 12 个专家
                       [20,107,104,64,19,197,187,157,172,86,16,27]])
num_replicas = 16; num_groups = 4; num_nodes = 2; num_gpus = 8
phy2log, log2phy, logcnt = eplb.rebalance_experts(weight, num_replicas, num_groups, num_nodes, num_gpus)
# 示例：2 层 MoE × 每层 12 专家，每层引入 4 个冗余专家，16 个副本放 2 节点 × 每节点 4 GPU

该接口与映射术语在生态中广泛沿用：SGLang 移植版逐行复制该文件并注释“not a pypi package”V；GitHub issue #22 讨论 phy2log 中出现同一 rank 重复热专家 id；issue #14 讨论 decode 阶段副本语义（与 Global 策略对应）。V

4.4 特性与代价

  • 离线、非关键路径：在负载估计上计算，运行时零开销；负载画像变化时才重算（各引擎通常周期性/按需触发，如 vLLM-Ascend 曾为其重算耗时加 profiling）。V
  • 无需辅助损失：作用在已训练模型上（V3/R1 本就用 bias/序列级损失的 DeepSeek 配方而非辅助均衡损失）。V
  • 代价 1——副本显存：热专家副本额外占显存（“256 逻辑 + 32 冗余 = 288 物理”这类形态见社区 H20 部署笔记）。V
  • 代价 2——与 reroute 解耦：UltraEP 论文指出 EPLB 只做放置，副本间的 token 分发（reroute）由独立启发式（如 round-robin）处理，未与放置联合优化；其效果取决于负载的平稳性。V
  • 工程成本低：纯 Python 数值计算，无 NCCL/GPU 依赖；任何引擎可复制算法自行适配。V

4.6 如何验证（一手状态）

  • EPLB 自带无官方 benchmark（README 无性能表）V；其“验证”来自生产实战与第三方测评。
  • 最强第三方测评其实藏在 UltraEP 论文里（EPLB 作为基线）：训练（3 模型平均）EPLB 相对 Megatron-LM 提升 +20%（同期 LPLB +12%、EPLB++ +29%、UltraEP +42%）；服务 prefill 场景 UltraEP 相对 EPLB 高 1.29×；DeepSeek-V3 训练场景 EPLB/LPLB 甚至与 Megatron-LM 相当或更差（负载短期摆动大，静态方案滞后）。V（2606.04101 §8.2）
  • SGLang PR #5295 基准：可见 “Total token throughput (tok/s): 33320.48” 一行，上下文对照值需开 PR 看全表。V
  • 规模级采用：华为 CloudMatrix384 论文（2508.02520）把 EPLB 写为正式服务阶段。V

4.7 局限与后续

  • 依赖平稳性：预测过期 → 残差失衡（UltraEP §3/§8 的实证：DeepSeek-V3 上 EPLB 输给不均衡基线 Megatron-LM 的对照组）。V
  • 显存开销 + 次优启发式：副本占显存；打包贪心；reroute 与放置解耦。后续工作：DeepSeek LPLB（线性规划，repo）、社区 IPLB（整数规划）、SGLang Waterfill（在线分发，LMSYS 博客）。V
  • 学术界对“按 token 数均衡”的批判（TEMPO：decode 内存受限域应按被激活的副本数而非 token 数建模，详见 §9）。V

本节一手来源：EPLB README 全文（67 行，建议直接读）；运行示例见 §8.2。

5方案二：UltraEP —— 机柜级精确负载实时均衡（训练 + 服务 Prefill）

5.1 身份与产物

  • 论文：arXiv:2606.04101；作者 Xinming Wei, Chao Jin, Tuo Dai, Yinmin Zhong, Shan Yu, Chengxu Yang, Bingyang Wu, Zili Zhang, Jing Mai, Qianchao Zhu, Zhouyang Li, Yuliang Liu, Guojie Luo 等（小红书 Dots-Infra × 北大）。V（论文 bibtex 原文）
  • 代码：Dots-Infra/UltraEP（MIT），2026-07-15 发布 v1.0.0，News 原文：“has been deployed in our production MoE training”。V 配套 Megatron-LM 参考集成 Megatron-LM-UltraEP（含 8×Hopper 可跑 demo 与 Qwen3-235B 配方）；官方博客 dots-infra.github.io/UltraEP。SGLang 推理集成“experimental，production-ready 后发布”。V
  • 定位一句话（README 原文）：“rebalances on the exact post-gating load in real time … replicates hot experts and reroutes tokens within every layer of every microbatch, to achieve near-optimal end-to-end performance.”V

5.2 动机：从“预测 + 周期”到“精确 + 实时”

论文 §1 的论证链条（全部原文可引）：

  1. large-EP（32/64 路）把失衡放大为 straggler / All-to-All 瓶颈 / 激活显存尖峰，EP 度数越高实际-理想差距越大；
  2. 既有方案（EPLB 等）预测负载并调整放置，但生产负载非平稳——论文实测“专家热度在 microbatch、层、数据域之间剧烈漂移”（Qwen3-235B top-8/128 专家、EP64 采样），陈旧预测 → 残差失衡；
  3. 精确负载只有 gating 之后才可知 → 均衡被迫上关键路径（hot path）→ 需要“规划求解 + 专家状态重排”都足够快；
  4. 机柜级 RSN（scale-up 域从单台 4/8-GPU 扩到整柜 64+ GPU）让“整组 EP 处于一个高带宽域、热路径搬专家状态”在物理上可行——但 RSN 只是必要条件：控制面要在 gating→dispatch 的窗口内算好方案，数据面要用 RSN 带宽执行“不规则、易变的专家状态传输”。V

因此 UltraEP 的落点明确为 训练（贯穿所有阶段）与服务 prefill（论文：“practical balancing target is prefill, where throughput is prioritized to reduce TTFT”）；decode 不在其服务范围（decode 为 memory-bound，后续 TEMPO 论文另作分析）。V

5.3 方案设计：两大创新

创新一：配额驱动规划器（Quota-driven Planner，联合优化复制与 reroute）

  • 每个 quota 定义一个专家物理实例的最终 token 负载；quota 把“副本创建”与“token reroute”耦合成一个优化问题：“副本只在携带有效负载时才被物化；reroute 按 locality 实现解出的 quota 切分”。V
  • 求解用高效的阈值二分（threshold-based binary search），直接优化 reroute 后的负载而非中间放置；对比原话：“Unlike EPLB, which rebalances on stale load and leaves reroute to a separate heuristic (e.g., round-robin), UltraEP directly optimizes the post-reroute load”。V
  • GPU-resident 内核：update_placement 每 microbatch×层根据精确负载算方案（README 实测 0.067–0.078 ms），产出“实例上的累积配额”（prefix scan）供 reroute 使用。V

创新二：RSN 原生专家状态通信（tile 流式 + 中继树扇出缓解）

  • 权重/梯度按固定大小 tile切分，编译为 GPU 常驻的传输任务（persistent kernel），避免 host 往返与静态集合通信的带宽浪费；weight_sync（主专家权重 → 副本）与 grad_reduce（副本梯度 → 主专家）共用同一执行单元。V
  • Chunk-streaming relay（分块流式中继）：对副本数 > 4 的热专家构建两阶段中继树：源 rank 先播种少量 relay，relay 再转发到叶子；中继前沿约取 √(|ℋ(e)|−1) 以均衡两阶段；按 tile 块流水（relay 收到一块即可转发，per-chunk ready flag 驱动 stage-II）。V
  • Load-Aware Relay Scheduling 内核：按“各 rank 待发字节量”贪心选择 relay 与叶子，均衡所有 rank 的出口流量（README 的 weight_sync 三模式 direct / adaptive / force_relay 与 ULTRA_EP_WEIGHT_SYNC_RELAY_* 旋钮即此实现）。V
  • 显存集约：冗余专家槽位跨层复用权重/梯度缓冲、无优化器状态（优化器只作用于主专家）。以 Qwen3-235B-A22B（94 MoE 层 × 128 专家）为例：单个冗余槽由 3.3GB 权重 + 6.6GB 梯度降到每 rank 36MB/72MB。V
  • 训练等价性：backward 先重物化副本权重（restore）再做专家 Dgrad，副本 Wgrad 经 grad_reduce 异步归约回主专家并与后续算子重叠；PP/VPP 用 microbatch 槽位管理。V

5.4 实现与调优面

  • 独立 Python/CUDA 运行时（非框架插件）：ultra_ep.Manager(group, num_layers, num_local_master_experts, num_local_redundant_experts=R, …)；注册各层主专家指针池，暴露每 rank 冗余槽缓冲。V
  • 要求：SM90/SM100、PyTorch ≥ 2.10、CUDA ≥ 12.3/12.9、节点内 NVLink；唯一第三方依赖 NVSHMEM（nvidia-nvshmem-cu13==3.4.5，计划未来切换 NCCL GIN）。V
  • 兼容 DP/PP/VPP、激活检查点、低精度（FP8 专家含 scale）、CUDA graph。V
  • 可观测性：ULTRA_EP_LOAD_PROFILING 逐 microbatch×专家记录均衡前后负载，配套 HTML load viewer 可视化。V

5.5 验证（论文 + README，全部一手数字）

论文实验设置

  • 公有云 RSN 集群：每 rack 64 GPU（16 台服务器），scale-up 带宽为 scale-out RDMA 的 8–10×；prefill 用 1 rack，训练用 2–4 rack，最大 256 GPU。V
  • 模型：训练 GLM4.5-106B-A12B（128 GPU）、Qwen3-235B-A22B 与 DeepSeek-V3-671B-A37B（各 256 GPU）；服务 prefill Qwen3-235B 与 GLM4.7-358B（EP64/EP40 + DP attention）；生产训练为内部模型 RefMoE-288B-A16B（EP32）。bf16。V
  • 指标：训练用 TFLOPS/GPU（续跑晚期 checkpoint 的短窗口）；服务用 RPS–平均 TTFT；负载均衡质量用逐层逐批 max/mean 失衡比；为保证负载公平，服务评测记录 SGLang 满载路由轨迹并在其他方案上回放。V
  • 基线：无均衡、force-balanced ideal、Megatron-LM、SGLang、EPLB、LPLB、EPLB++（喂给 EPLB 精确负载的加强版静态方案）。V

核心结果

  • 摘要口径：训练 + 服务平均达到 94.3% 的 force-balanced ideal 吞吐，相对无均衡 1.49×；失衡比从 1.30–4.01 降到 1.01–1.04。V
  • 分模式：训练 94.6%、服务 prefill 93.9%（106B–671B 模型、≤256 GPU）；训练相对 Megatron-LM 平均 1.42×、prefill 相对 SGLang 平均 1.56×；相对 EPLB 1.29×、相对 EPLB++ 5%–24%；专家复制通信相对主流通信后端 3.1×–5.5×。V
  • 训练对比：3 模型平均相对 Megatron-LM——EPLB +20%、LPLB +12%、EPLB++ +29%、UltraEP +42%；DeepSeek-V3（路由补偿放大短期摆动）上 EPLB/LPLB 与 Megatron-LM 相当或更差，UltraEP 仍 >96% ideal。V
  • 开销分解（Qwen3-235B-A22B 训练，per MoE 层平均）：相对 ideal 的额外前向时延 0.33ms、仅占总时延 1.8%，后向可忽略；暴露开销 README 口径为大规模 EP 下 <300µs、通常占 step 1%–2%。V
  • 显存：无均衡时 MoE 激活峰值比 ideal 高 2×（训练）/ 11×（服务）；UltraEP 压回近 ideal。V
  • 生产：RefMoE-288B 多 rack 生产训练持续 >92% ideal、相对无均衡平均 +9.6%，收敛不受影响。V
  • README 自带 EP64 单测表（256 专家、每 rank 4 master + 2 冗余、topk=8、8k token/rank、bf16）：初始失衡 1.51/2.01/3.03 → 终值均 1.01；update_placement 0.067–0.078ms、reroute ~0.04ms、weight_sync（direct）0.21–0.32ms /（adaptive relay）~0.19ms、关键路径带宽 ~706–715 GB/s、grad_reduce（overlap）1.9–2.4ms、副本数最高 6/专家、合计 ≤51。V

5.6 局限与第三方评述

  • 范围：训练 + 服务 prefill；decode 迭代（memory-bound）不在其目标（§5.2）。V
  • 硬件前提：方法依赖 RSN 级 scale-up 域（NVLink 域 ≥ EP 组）；README 自陈“当 NVLink 域小于 EP 组时，可达失衡下限略高于理想 1.0”。V
  • TEMPO 评述：2608.13057 相关工作把 UltraEP 与 LLEP/TAOT 并列为训练侧均衡器，称其“无法在服务栈端到端复现——它们利用了权重/训练侧特性”（原文片段 “Training-side balancers (LLEP, TAOT, UltraEP) cannot be reproduced end-to-end on a serving stack — they exploit wei…”）；其摘要亦把 EPLB/LPLB/UltraEP 归入“按 token 数做均衡”的一类，指出 decode 受限域该模型失效（§9）。V/U
  • 继承关系：README 致谢——低层通信内核借鉴 DeepEP 与 HybridEP；均衡设计受 EPLB/LPLB 启发。V

6方案三：MoonEP —— 动态冗余专家 + S×K 完美均衡的 EP 通信库

6.1 身份与定位（README 一手）

  • 仓库：MoonshotAI/MoonEP；标题：“MoonEP: A Perfectly Balanced Expert Parallelism Library via Dynamic Redundant Experts”；引用信息：Yutian Chen, Cong Li, Yucheng Wang, Ming Wei, 2026。V
  • 自述定位：“MoonEP is an Expert Parallelism communication library that keeps token loads perfectly balanced across ranks via dynamic redundant experts.”——注意它是通信库（与 DeepEP 同类、可被引擎调用），而非完整引擎；其「完美均衡」指每个 rank 恰好收到 S×K 个 token，与路由倾斜无关。V
  • 时间：媒体集中 2026-07-28~08-02（Kimi K3 开放日 2026-07-28 同期，K3 技术报告 arXiv:2607.24653）；“MoonEP 是否为 K3 三大 Infra 技术之一”未证实。U
  • 设备：NVIDIA GPU；真武 PPU“under review, coming soon”。V

6.2 与 vLLM 的集成（进行中）

vLLM 侧三条证据：RFC #52095（Kimi K3 MoonEP integration roadmap）、PR #52101（BF16 PoC：MoonEP 作为 “balanced EP backend”）、PR #54147（Pin and build MoonEP in tools/ep_kernels，与 DeepEP/NIXL 同通道）。当前处于 PoC/路线图阶段，是否合入未核实。V/U（链接见 §11）

6.3 设计要点（README 一手，三条承诺）

Notation：S = 每 rank 输入 token 数，K = 每 token 的 top-k 数。① Perfect balance：无论路由多倾斜，每 rank 恰好收到 S×K token；一小批冗余专家由在线规划从当前 router 输出决定并在专家计算前预取，其梯度在 backward 归约回“家 rank”。② Online planning：近最优 GPU 规划内核、开销可忽略。③ Zero copy & static shapes：融合 permute/unpermute——token 直接写入远端专家分组位置、把缓冲视图交给计算；只需固定 S×K 缓冲，静态形状消除逐层 MoE 的 host 同步。

6.3.1 内存模型：NVLink 对称内存上的统一权重张量

  • 与框架的契约（README 原文要点）：每个专家投影（gate/up/down）每层一个连续对称内存权重张量 [E+B, H, H']，各 rank 布局相同；行 [0,E) = 各 rank 本地主专家（每 rank E/R 行，物理上就是主 rank 的参数内存，经对称内存在全局可见）；行 [E,E+B) = 本 rank 的预取槽，由 prefetch_weight 填充，规划器经 cu_seqlens 把“被复制专家的 token 段”指向这些槽。V
  • 物理内存来自跨层共享的进程级池：额外成本是每个投影总共 B 份专家权重，而非每层 B 份（跨层复用，与 UltraEP 同思路）。V
  • B（预取槽数）怎么设：训练必须 B = E/R（规划器最多从每个 rank 的一个远端主组复制 ≤E/R 个专家，保证 group GEMM 触碰的专家全部本地）；推理（只预取、无梯度）允许 B < E/R，推荐 B = 3–4——槽不够时 group GEMM 通过对称内存映射直接读主 rank 权重（稍慢、不影响正确性）。V
  • 梯度缓冲（训练）：fp32 [E+B,H,H']；预取槽梯度放在独立 reduce buffer（每 rank 一组，全局拼成 [R,B,H,H'] 视图），reduce_grad 让每个主 rank 经 NVLink 远端读回自己专家的梯度、累加并清零槽位。V

6.3.2 API 与数据流（dispatch / combine / prefetch / reduce）

buf = moonep.Buffer(S=4096, H=7168, K=8, E=256, num_ep_ranks=8, num_sms=32, token_padding=128)
hidden_nvsh, route_w, cu_seqlens, plan = buf.dispatch(hidden_sh, route_weights_sk, topk_experts_sk, tokens_per_expert,
                                                       zero_copy=True)   # plan = MoonEPCommPlan（前后向复用）
buf.prefetch_weight(plan, full_gate_weight, full_up_weight, full_down_weight)  # 行[E,E+B)为预取槽
…  # 框架侧按 cu_seqlens 选中的 VM 组行做 group GEMM（FFN）
output_sh, _, _ = buf.combine(plan, expert_output_nvsh, zero_copy=True)  # 反 permute + 按路由权重加权
# backward: combine bwd 用保存的 plan 重新 dispatch（跳过规划、无需预取）；reduce_grad 归约副本梯度

VM 组（VM group）GEMM 通过单一 [E+B,H,H'] 张量按行寻址专家（“contiguity is a hard requirement”），这是它与常规“每专家独立张量”框架不兼容的原因（也正是 vLLM 侧需专门适配的点）。V

6.4 性能主张：与 DeepEP v2（elastic）的对拍（README 一手）

基准均跑在 H20、EP=8，扫路由失衡度 maxvio = max_e(T_e/T̄) − 1（0 = 完美均衡）：V

  • 通信单点：MoonEP 的 comm 时间在每个失衡水平都低于 DeepEP v2；且随 maxvio 增大几乎持平，而 DeepEP v2（时延由最热 rank 决定）持续恶化——“perfect balance makes it immune to imbalance”。V
  • 对比口径公平性：MoonEP 的规划 + 权重预取内核（DeepEP 没有）已计入柱状图；即便如此，“总 dispatch 时间 ≈ DeepEP v2 的 dispatch 单独耗时，失衡下领先；combine 在各水平显著更快”。V
  • 端到端训练：DeepEP 随失衡 iteration 时间攀升，且动态激活形状导致显存碎片化、高失衡下训练 OOM；MoonEP 每 rank 恒定计算 S×K token、形状完全静态，时间持平且从不 OOM。V
  • 绝对数值在仓库 figure 图片中（comm_vs_deepep.png / e2e_vs_deepep.png），README 正文未给表——引用绝对吞吐前需看图。U
  • 基准公平性细节（bench docstring）：唯一 apples-to-apples 对照是 DeepEP v2 elastic、do_expand=True（expanded dispatch）+ reduced combine——因为 MoonEP 把 expert permute 熔进 comm（fused permute），DeepEP v1 的 recv_x 按源 rank 分组、permute 在外层未熔，故不比 v1。双方共享同一路由矩阵（seed 1234）、同一 hidden/权重张量、同一计时框架（warmup=20 iters=50）、同一 SM 预算（32）与 token_padding（128）；带宽公式 S×K×H×2/t。V

6.5 验证与复现

  • 官方测试：torchrun --nproc_per_node=8 -m pytest tests/test_{planning,dispatch,combine,e2e,grad_reduce,prefetch}.py（需多卡 + NVLink）；对拍基准 torchrun --nproc_per_node=8 benchmarks/bench_vs_deepep.py [--out r.csv]。V
  • 第三方复现：Saipien（Planner-Enforced S×K Token Balance + Zero-Copy Buffers）、ThakiCloud（busiest rank sets step time）等已实际运行其规划代码并撰文。V
  • 血缘：README Acknowledgments——启发自 DeepEP、Echo、UltraEP、AcclEP（阿里 EP 通信库）。V 即 MoonEP 与 UltraEP 同源共振，但分工不同：UltraEP 是「规划+复制+通信」全栈独立运行时，MoonEP 是「以均衡为卖点」的通信库（dispatch/combine 由自身提供、planning 内嵌）。

生态集成SGLang / vLLM / vLLM-Ascend / CloudMatrix384 已用Megatron-LM fork 参考集成；SGLang 推理集成 experimentalvLLM “balanced EP backend” RFC/BF16 PoC（进行中）；自对拍 DeepEP v2
公开量化结果官方无表；作为基线被第三方测：训练 +20%（vs Megatron）、prefill 被 UltraEP 超 1.29×94.3% ideal（训练+prefill 平均）、训练 1.42×/prefill 1.56× vs 主流引擎基线、失衡 1.01–1.04、热路径 +0.33ms（1.8%）H20/EP8：comm 全程低于 DeepEP v2 且对失衡免疫；训练高失衡不 OOM（数值在仓库图中）
主要局限依赖平稳性；与 reroute 解耦；次优启发式需 RSN 级 NVLink 域；decode 不覆盖；服务栈可移植性受 TEMPO 质疑对称内存/VM 组内存契约与现有引擎深度耦合；合入 vLLM 尚在 PoC
许可证MITMIT以仓库 LICENSE 为准（引用为 GitHub 收录）

7.1 一句话选型视角（v2 更新）

  • 想在现有推理引擎上快速止血（热度相对稳定）：EPLB 路线仍是零模型改动、生态最全（SGLang/vLLM 现成）。
  • 在做整柜级 MoE 训练（或 prefill 优先的服务）、能接受新运行时：UltraEP 是目前唯一有生产训练背书 + 开源代码的“精确实时”方案（先看 Megatron-LM fork 的 8×Hopper demo）。
  • 要的是均衡的通信原语（自研引擎/框架集成）：MoonEP 提供 dispatch/combine/prefetch/reduce 全套均衡通信 API，并可直接与 DeepEP v2 对拍评估。

8.3 严谨性要点（重要）

  • 控制变量：同负载同模型同集群，只切均衡策略；服务对比最好像 UltraEP 那样回放同一路由轨迹。
  • prefill 与 decode 分开测：EPLB 两策略分别服务两者；TEMPO 指出 decode 内存受限域与 prefill 的最优目标不同（§9）。
  • 明确“理想”分母：报 relative-to-ideal 时必须说明 ideal = 强制均衡实测（force-balanced），不是理论峰值。
  • 数字横比无效：EPLB 的 +20%（vs Megatron-LM 训练）、UltraEP 的 1.56×（vs SGLang prefill）、MoonEP 的 comm 曲线（vs DeepEP v2）分母各不相同，不要跨表直接相除。
  • 测量热路径开销：实时方案要单独报 planning/weight_sync/reroute 的时延与重叠情况（UltraEP 给了 0.33ms/1.8% 的可比口径）。

9.2 TEMPO 的批判：token 计数式均衡在 decode 受限域的局限（对三方案都适用）

TEMPO（arXiv:2608.13057，2026-08）摘要的核心论证：V

EP 服务中每层以最慢 GPU 同步。现有 dispatcher（EPLB、LPLB、UltraEP）均衡 token 数（或 METRO 均衡激活专家数），假设专家耗时与其中一个线性相关；但两代数据中心 GPU 实测表明两者都不是：token 数低于 n*≈156–168 时 HBM 权重流占主导——成本挂在“被激活的副本”而非 token；高于 n* 时 grouped GEMM 把 token 圆整到 128-tile 的 M-tile，拆分专家会产生 padding 计算。作者用 max-affine 模型 t=max(a+bG, c+βN) 拟合两域，给出 phase diagram，并主张这是预测性结论而非普适胜利：Qwen3-235B 在其胜区内端到端 +4–6% 吞吐、p99 −15.6%；DeepSeek-V3 在区外（通信受限）只有机制成本。

对三方案的直接含义：“均衡 token 数”只在计算受限/线性域是最优代理；decode 的 memory-bound 域应均衡“被激活的副本数”，而拆分副本引入的 GEMM padding 又改变了成本形态——EPLB/UltraEP/MoonEP 的“token 完美均衡”主张在纯 decode 大 batch 场景需按 TEMPO 的 phase 图重新检验（EPLB 的 Global 策略服务于 decode，尤其值得对照）。V

9.3 血缘与竞争小结

  • UltraEP ← 思想继承 EPLB/LPLB（README 致谢），← 内核借鉴 DeepEP/HybridEP；MoonEP ← 借鉴 DeepEP/Echo/UltraEP/AcclEP；三者的共同地基是 DeepEP 开创的低延迟 EP 通信。
  • MoonEP 与 UltraEP 最接近“同题异构”：UltraEP = 独立全栈运行时（规划+复制+通信），MoonEP = 通信库内置均衡规划；两者都押注 NVLink 对称内存/共享地址空间做零拷贝。
  • 学术界邻域（待细读，交叉引用未逐一核实）：LLEP、TAOT、FEPLB（2604.19654）、ScalpeLB、UBEP（2607.06202，EP 通信重构）、HCRMap（2607.11586）、RoutePack（2608.12146）、Echo（2603.07685）；厂商侧 TensorRT-LLM Wide-EP、vLLM eplb 模块、vLLM-Ascend SWIFT balancer。U

9.4 给深入研究者的建议

  1. 先分清你要均衡的阶段（prefill/decode/训练）与成本域（计算受限 vs HBM 受限），再选代理指标（token 数 / 激活副本数 / makespan）——TEMPO 的 phase 图是现成的判据。
  2. 把“副本数”当资源变量：显存预算内最大化调度自由度（跨层复用、动态 B/R）是三家的共同竞争点。
  3. 复现时以“相对理想/相对无均衡”的控制实验为准，警惕宣传数字的分母差异；生产选型看引擎合入状态（EPLB 已合、MoonEP PoC、UltraEP 走 Megatron fork）。
