MoE EP 系列 · 昇腾工程案例复盘（Qwen3.5 · NPU）· 2026-09-28

从 All-to-All 到 MegaKernel —— 昇腾 MoE 专家层四方案深度对比

阅读对象：Qwen3.5 27B/35B 在昇腾 NPU 上的推理优化项目中，MoE 专家层的四条并行方案——ALLGATHER（DP 复制专家）、ALLTOALL（标准 EP 基线）、MC2（通算融合）、FUSED_MC2（整链 MegaKernel）——的处理逻辑、优化点与 trade-off。素材来自项目案例材料（复盘口径），本篇按系列笔记体例重排并配图。

口径说明：算子计数（10 / 7 / 7 / 3）与算子命名（distribute_dispatch / distribute_combine / mega_moe / ZercMoe 等）沿用案例材料；与昇腾 CANN 官方文档的命名可能有出入，引用具体算子名时以官方文档为准。U 性能量级（如「8 卡下 all-to-all 约占 30%」）为案例口径，非公开论文数据。R

系列定位：与 MoonEP、METRO、LPLB、EPLB 等负载均衡笔记互补——均衡系列回答「token / 专家怎么摆才公平」，本篇回答「摆定之后，这一层怎么跑得最快」：通信与计算的边界如何一步步被算子融合压缩。同目录另见 MoE 与 FFN 前馈融合算子（vLLM / vLLM-Ascend 视角）。

1. 一页结论

  • 瓶颈定位：MoE 推理的主要瓶颈不在 GEMM 算力，而在 all-to-all 跨卡通信与多次数据重排带来的中间张量 HBM 往返；优化的本质是通过算子融合逐步压缩通信与计算之间的边界。
  • ALLTOALL：无融合的标准 EP 基线，10 个算子串行（两次 all-to-all、四次 permute/unpermute），通信与计算严格串行——所有方案的对比原点。
  • MC2：用 distribute_dispatch / distribute_combine 两个通算融合算子把「重排 + 通信 + 重排」各三段并为一段，算子数 10 → 7，融合算子内部片上流转、通信与重排流水重叠——当前主力方案（已现场验证、风险可控）。
  • FUSED_MC2：把 dispatch、专家 FFN、combine 整链融进单个 mega_moe kernel，算子数压至 3（核心 1 个），中间结果驻留片上、通信计算重叠最大——融合粒度的终极形态与长期目标；案例增强实现 ZercMoe 再加三件事：零冗余去重、aclshmem P2P 绕过 HCCL、单 kernel 内 AIC/AIV 专家组粒度流水。
  • ALLGATHER：独立思路——DP 复制全部专家绕过 all-to-all，通信换成规则的 all_gather + reduce_scatter（可量化降流量），代价是显存 ×N、计算冗余 ×N——小专家数场景的备选 / 对比基线。
  • 选型建议（Qwen3.5 27B/35B，512 专家）：MC2 为当前主力、FUSED_MC2 为长期目标，配套 alltoallv_gmm / gmm_alltoallv 通信—计算融合、decode 注意力链融合与权重预取，形成优化闭环。

2. MoE 推理为什么难：五大痛点

MoE 的稀疏特性带来训练效率与模型容量的双重收益，但推理部署必须引入专家并行（Expert Parallelism，EP）：专家数量远大于单卡可承载范围，权重分布到多张加速卡上，每个 token 按路由结果跨卡分发到目标专家所在的卡、计算完成后再聚合回源卡。一层 MoE 的输出为：

\[ y = \sum_{i \in \operatorname{TopK}(g(x))} g_i(x) \cdot E_i(x) \]

「分发—计算—聚合」这一流程使 MoE 层性能高度依赖跨卡通信效率与数据重排开销，而非单纯依赖 GEMM 算力。案例材料把难点归为五条，它们正好对应四方案各自的发力点：

痛点机理对应优化方向
① 通信开销大all-to-all 要求每卡向其他每卡发送不同的数据，模式复杂、带宽利用率低；与 all_gather（每卡收齐所有数据）/ reduce_scatter（每卡取自己的分片）相比最昂贵。动态路由下各卡收发量不等（AllToAllV），进一步拉低效率MC2 通算融合 / FUSED_MC2 重叠隐藏；ALLGATHER 直接换掉原语
② 数据重排频繁同一专家的 token 要在内存中连续排列才能适配 grouped GEMM：分发前按专家 ID permute；all-to-all 后收到的数据按源卡排列，需再 permute 按专家分组；聚合侧反向 unpermute。纯内存搬运不产生计算价值，却吃 HBM 带宽与 kernel 启动时间MC2 把重排融进通信算子；FUSED_MC2 全链片上流转
③ 中间张量多、HBM 往返频繁标准 ALLTOALL 共 10 个算子，每个算子的输出都要写 HBM 再由下一个算子读入；MoE 中间激活大，HBM 带宽往往先于算力成为瓶颈算子融合，消中间落盘
④ 通信与计算串行必须等分发通信完成才能开始 GEMM、等 GEMM 完成才能开始聚合通信，通信等待直接累加在端到端时延上；通信占比高达 30% 的场景下，近三分之一时间算力空闲MC2 部分重叠；FUSED_MC2 单 kernel 内深度流水
⑤ 动态路由与负载均衡路由动态：不同 batch / step 各专家 token 负载差异大，all-to-all 数据量分布不均、grouped GEMM 各专家 batch size 差异大，tiling 与负载均衡难度高；大融合算子要在单 kernel 内消化这种动态性，工程复杂度显著上升FUSED_MC2 的攻坚点（也是与 均衡系列的交界）

场景：Qwen3.5 27B/35B 昇腾 NPU 推理优化项目中，MoE 与 GDN（Gated Delta Net，线性注意力）并列为两大性能 gap。团队围绕 MoE 层系统试验了四条技术路线，并配套推进 alltoallv_gmm / gmm_alltoallv 通信—计算融合算子、decode 阶段注意力算子链融合、权重预取等手段，形成「基线 → 通算融合 → 整链大融合」的完整优化谱系。

3. ALLTOALL：标准 EP 基线

ALLTOALL 是最标准、最通用的专家并行实现，也是其他方案的性能基线。它用 TP 切分专家权重（每卡只存部分专家），通过显式 all-to-all 通信完成 token 跨卡分发与结果聚合，流水线共 10 个算子：

pad + TP split → permute → all_to_all → permute → gmm(gate_up) → SiLU → gmm(down)
→ unpermute → all_to_all → unpermute + weighted sum → all_gather(TP)
  • pad + TP split：对输入做填充并按 TP 组切分；
  • 第一个 permute：按专家 ID 重排 token，使发往同一目标卡的 token 连续；
  • all_to_all：token 跨卡发送到目标专家所在的卡；
  • 第二个 permute：收到的数据再次重排，使同一专家的 token 连续以适配 grouped GEMM；
  • gmm(gate_up) / SiLU / gmm(down)：本地专家的 FFN 计算；
  • unpermute：恢复 token 顺序；
  • 第二个 all_to_all：计算结果发回源卡；
  • unpermute + weighted sum：反重排与路由加权求和；
  • all_gather(TP)：TP 组内收集输出。

三大痛点（即 MC2 / FUSED_MC2 的优化对象）：① 通信重——两次 all-to-all 跨卡传输，8 卡下可占推理时间约 30%；② 中间张量多——10 算子串行，每段输出都写 HBM 再读入；③ 通信计算串行——分发通信 → FFN → 聚合通信严格串行，等待无法隐藏。

方案价值：ALLTOALL 本身不做融合，胜在通用性强（不依赖特定硬件融合算子，任意支持 all-to-all 的平台可跑）、实现简单风险低（全部是标准库成熟算子）、以及作为优化基线——MC2 与 FUSED_MC2 的收益均以它为参照。

4. ALLGATHER：DP 复制专家，绕过 all-to-all

ALLGATHER 不用 EP，改用数据并行（DP）处理 MoE 层：每张卡都存全部专家权重的完整副本，token 无需跨卡分发——每卡本地就有所有专家。流水线共 7 个算子：

quant + all_gather(DP) → init_routing → gmm(gate_up) → SiLU → gmm(down)
→ unpermute + weighted sum → reduce_scatter(DP)
  • quant：对输入量化，降低通信数据量；
  • all_gather：收集 DP 组内所有卡的 token，使每卡拥有完整 batch；
  • init_routing：本地计算路由（专家都在本地，路由只决定选哪些专家，不涉及跨卡分发）；
  • gmm(gate_up) / SiLU / gmm(down)：所有专家均在本地计算；
  • unpermute + weighted sum：恢复原序并按路由权重加权求和；
  • reduce_scatter：结果切回各卡，每卡只保留自己负责的输出分片。

图 2 · ALLGATHER 数据流（2 卡示例）：每卡都存全部专家 E0~E3，all_gather 让每卡拿到全量 token，本地算完后 reduce_scatter 各取一片输出。drawio 源文件：assets/ascend-moe-parallel-deep-reading.drawio（ALLGATHER DP 复制 sheet）。

关键：两卡做的是完全相同的计算（都算 t0~t3 的全部专家），存在 N 倍计算冗余（N = DP 卡数）。好处是没有 all-to-all 的复杂通信和 token 重排；代价是每卡都存全部专家权重 + 算全 batch，显存和算力都翻倍。

优化点：① 彻底绕过 all-to-all——通信原语换成更规则、带宽利用率更高的 all_gather + reduce_scatter；② 量化传输——all_gather 前先 quant 压流量；③ 无跨卡分发延迟——token 不等跨卡传输即可开算，路由与计算全在本地。

代价与局限：每卡存全部专家权重，显存开销高（512 专家全复制对大模型不现实）；每卡计算完整 batch，存在计算冗余。适用于专家数较少、显存充裕、追求快速上线或作对比基线的场景。

5. MC2：TP + 通算融合（distribute_dispatch / distribute_combine）

MC2 在 TP 切分专家的基础上引入昇腾 MC2 通算融合算子，把「通信 + 数据重排」融合为单个算子：用 distribute_dispatch 替代「permute + all_to_all + permute」分发侧三段，用 distribute_combine 替代「unpermute + all_to_all + unpermute」聚合侧三段。算子数 10 → 7：

pad + TP split → distribute_dispatch → gmm(gate_up) → SiLU → gmm(down)
→ distribute_combine → all_gather(TP)
  • distribute_dispatch 在一个算子内完成：按专家 ID 重排 token、发起 all-to-all 跨卡分发、接收后再次重排为 grouped GEMM 所需布局；
  • distribute_combine 反向完成：计算结果反重排、all-to-all 聚合、恢复原始顺序。

两个融合算子内部实现了通信与重排的流水重叠，消除了中间的 HBM 往返。

优化点：

  • 通算融合：分发侧 / 聚合侧各 3 个算子融合为 1 个，算子总数 10 → 7；
  • 消除中间张量 HBM 往返：融合算子内部数据直接在片上 buffer 流转，permute 结果、all-to-all 结果不再分别写回 HBM 再读入；
  • 通信—计算重叠：融合算子内部通信与重排计算流水化，部分隐藏通信延迟；
  • 减少 kernel 启动与 Host 下发：3 个算子的启动开销合并为 1 个，降低 Host 侧调度延迟；
  • 显存低：仍 TP 切分专家，每卡只存部分专家权重，远低于 ALLGATHER。

定位：当前昇腾平台 MoE 优化的主力方案——相比 ALLTOALL 收益明确（算子减少、HBM 往返消除、通信计算重叠），相比 FUSED_MC2 工程复杂度适中、风险可控，已现场验证有效并进入主链路。

6. FUSED_MC2：TP + 整链 MegaKernel

6.1 处理逻辑与优化点

FUSED_MC2 是融合粒度最大的方案：把 distribute_dispatch（分发）、专家 FFN（gmm gate_up + SiLU + gmm down）、distribute_combine（聚合）全部融进一个名为 mega_moe 的 MegaKernel，算子内部完成 dispatch_ffn_combine 全流程。流水线简化为 3 个算子：

pad + TP split → mega_moe(dispatch_ffn_combine) → all_gather(TP)

在 mega_moe 单个 kernel 内，token 的分发通信、专家 FFN 计算、结果聚合通信被组织为高度流水的执行流：分发通信与部分专家的 FFN 计算重叠、FFN 计算与聚合通信重叠，中间结果全部驻留片上缓冲或寄存器，最大限度减少 HBM 访问。

优化点：① 最大粒度融合——核心计算从 10 算子（ALLTOALL）/ 7 算子（MC2）压缩为 1 个 kernel，启动开销最低；② 中间张量 HBM 往返最少——dispatch、FFN、combine 之间数据全在片上流转；③ 通信—计算重叠最大——三类工作在同一 kernel 内深度流水，通信等待被最大程度隐藏；④ 显存低——仍 TP 切分专家。

定位：融合粒度的终极形态，对应会议中「路线 A（全链路大融合）」。潜在收益最高，工程复杂度也最高：需在单 kernel 内处理动态路由导致的 token 不均、grouped GEMM tiling 与负载均衡、通信 buffer 与计算的并发调度、动态 shape 适配等。作为长期优化目标持续攻坚，预计需多轮迭代达到生产可用。

6.2 ZercMoe：FUSED_MC2 的案例增强实现

ZercMoe 是 FUSED_MC2 的具体实现之一——架构模式与整链大融合完全一致，区别在实现细节：token 跨卡传输按「卡」去重，卡内分发靠本地内存拷贝；combine 侧反过来：卡内先把多个专家的结果加权累加好，再写一次回源卡。相对基础 MegaMoe 有三个增强：

  • 增强 ① 零冗余通信去重（Zero-Redundant）：同一 token 路由到本 rank 多个专家时，基础 MegaMoe 会重复发送多次；ZercMoe 用 distTokenFirstPos / distTokenLastPos 去重，每（token, dstRank）只传一次。
  • 增强 ② aclshmem 对称堆 + kernel 内 P2P 直连，绕过 HCCL：不用 HCCL all_to_all 集合通信，改用 aclshmem 对称堆，kernel 内通过 shmem(offset, rank) + MTE 搬运直接 peer 访问。收益：不经 HCCL 调度器；无 ccl_buffer 公式约束；大 batch（m ≥ 512）不炸；与去重后的不规则 P2P 流量天然适配。
  • 增强 ③ 单 MIX kernel 内 AIC/AIV 专家组粒度流水：单次发射完成全流程（sort → dispatch → GMM1 → SiLU → GMM2 → combine → unpermute），AIC : AIV = 1 : 2，按专家组做通信 / 计算重叠。同步机制：AIV 每完成一组 token 拷贝 → CrossCoreSetFlag（SYNCFLAGC2V，IsSyncTask 按 2 的幂次分批）→ AIC 开算该组 GMM1；epilogue 按 gmDequantSum 分批提前启动，不等全部专家算完。

图 3 · ZercMoe 单 kernel 内部：顶部为单次发射覆盖的七段流程，中部为 AIC/AIV 专家组粒度流水（AIV 拷贝组 1 时 AIC 已在算组 0 的 GMM，flag 同步），底部为三个增强点的完整表述。drawio 源文件：assets/ascend-moe-parallel-deep-reading.drawio（ZercMoe 单 kernel 流水 sheet）。

10 算子 · all_to_all ×2 · 低显存 · 无融合（优化基线）

② ALLGATHER｜DP · 专家全复制

7 算子 · all_gather + reduce_scatter · 高显存 · 无 all-to-all

③ MC2｜TP · 通算融合

7 算子 · dispatch / combine 融合 · 低显存 · 通信计算重叠 · 当前主力

3 算子（核心 1 个）· mega_moe 整链融合 · 低显存 · 重叠最大 · 长期目标

在 MC2 基础上把 FFN 也融进同一 kernel，dispatch / FFN / combine 整链大融合，中间数据全驻留片上、通信计算重叠最大、工程复杂度最高。

图 4 · 四方案关系：TP 路线三级融合递进（路线 1），ALLGATHER 独立换原语（路线 2）。

路线 1（融合递进）：ALLTOALL、MC2、FUSED_MC2 同属 TP 专家并行路线，三者不是互斥替代，而是融合粒度逐级加深的递进关系——

  • 第一步（ALLTOALL → MC2）：分发侧「permute + all_to_all + permute」融合为 distribute_dispatch，聚合侧「unpermute + all_to_all + unpermute」融合为 distribute_combine。核心是通算融合——把通信与数据重排合并，消除中间张量，实现通信与重排的流水重叠；算子数 10 → 7。
  • 第二步（MC2 → FUSED_MC2）：在通算融合基础上，把中间的专家 FFN（gmm gate_up + SiLU + gmm down）也融入同一个 kernel，形成 dispatch_ffn_combine 整链大融合。核心是计算也融进去——FFN 与两侧通信在同一 kernel 内深度流水，中间结果完全驻留片上；算子数 7 → 3（核心 1 个）。

路线 2（换通信原语）：ALLGATHER 不在递进链上。它的思路是「既然 all-to-all 这么难优化，那就不用它」——通过 DP 复制专家，把通信模式从复杂的 all-to-all 替换为更规则的 all_gather + reduce_scatter。这是换问题的思路，在特定条件下（专家数少、显存充裕、all-to-all 效率极低）可能有效；但在大模型、多专家的主流场景下受限于显存，更多作为对比基线或特定场景备选。

总结：四方案共同揭示了 MoE 推理优化的核心方法论——在 TP 专家并行框架内，通过逐级加深算子融合，不断压缩通信与计算之间的边界：从「减少算子数」到「消除 HBM 往返」再到「最大化通信计算重叠」，最终实现端到端时延的持续下降。对 Qwen3.5 27B/35B 这类 512 专家的大模型，建议以 MC2 为当前主力、FUSED_MC2 为长期目标，配套推进通信—计算融合与权重预取等手段，形成完整的优化闭环。

10. 快问快答

Q1：为什么不直接上 FUSED_MC2，先停在 MC2？

MC2 已经拿到大头收益（算子 10→7、HBM 往返消除、通信与重排重叠），且风险可控、已现场验证进入主链路；FUSED_MC2 要在单 kernel 内处理动态路由 token 不均、grouped GEMM tiling、通信 buffer 与计算并发调度、动态 shape，工程复杂度最高，需多轮迭代才能生产可用——按「先落袋、再攻坚」推进。R

Q2：MC2 与 FUSED_MC2 是替代关系吗？

不是，是同一 TP 框架内融合粒度的递进：MC2 融合「通信 + 重排」，FUSED_MC2 在其上再把 FFN 融进去。FUSED_MC2 成熟后自然覆盖 MC2 的能力，但落地前 MC2 是主力。V（案例口径）

Q3：ALLGATHER 什么时候真的可用？

专家数少（案例建议 ≤16）、单卡显存装得下全量专家、追求快速上线，或需要一条无 all-to-all 的对比基线时。512 专家规模的全复制不现实。V（案例口径）

Q4：本篇和负载均衡系列（EPLB / LPLB / METRO / MoonEP）什么关系？

正交且可叠加：均衡系列解决「token / 专家在各卡间怎么摆才公平」（放置、分流、重分组），本篇解决「给定路由后这一层怎么执行得最快」（融合、重叠、片上流转）。均衡做得好，融合算子内的 grouped GEMM 负载也更均匀——FUSED_MC2 的痛点⑤正是两者的交界。R

Q5：ZercMoe 为什么坚持绕开 HCCL？

案例材料给了四个理由：不经 HCCL 调度器、无 ccl_buffer 公式约束、大 batch（m≥512）不炸、与去重后的不规则 P2P 流量天然适配——去重后每（token, dstRank）只传一次，流量本就不规则，对称堆上的显式 peer 读写（shmem(offset, rank) + MTE）比集合通信更贴合。V（案例口径）
