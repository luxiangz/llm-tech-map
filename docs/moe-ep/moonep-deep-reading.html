MoE EP 负载均衡系列 · 深度阅读之六（MoonEP）· 2026-09-23

MoonEP 深度阅读笔记 —— 动态冗余专家与「构造性完美均衡」的 EP 通信库

阅读对象：Moonshot AI 开源的 MoonEP（“A Perfectly Balanced Expert Parallelism Library via Dynamic Redundant Experts”，Yutian Chen 等，2026）：一个EP 通信库（与 DeepEP 同类、被引擎调用，而非完整引擎），用「每步在线规划 + 动态冗余专家」做到无论路由多倾斜、每个 rank 恰好收到 $S \times K$ 个 token——均衡不是优化目标，是布局的构造性质。内核全部用 CUTLASS Python DSL（CuTe）编写。

证据标注：V = 一手核对（本地仓库源码逐文件精读 + README + 仓库基准图 + GitHub API）；R = 合理推断/图读数；U = 待核实。静态精读（需 SM90/100 + NVLink 集群，未运行）。

系列定位：与 EPLB（放置）、UltraEP（全栈运行时）、LPLB（训练 LP 分流）、METRO（decode 激活均衡）并列——token 均衡问题的第三条路线：不预测、不分摊、不选副本，而是重新分组。

1. 一页结论

  • MoonEP 是什么：EP 通信库（dispatch / combine / prefetch / grad_reduce 四个算子 + 内置在线规划器），用动态冗余专家保证每 rank 恒定计算 $S \times K$ token、形状完全静态——把「容忍不均衡」变成「布局上消灭不均衡」。V
  • 均衡怎么来的：每步前向跑一个 cooperative 规划内核：汇聚各 rank 真实路由 → 以 CAP = S×K 做组间贪心互填（超载组 → 最空组，受方一次补满）→ 专家级过户 → 挑 B 个迁入专家预取权重到本 rank 槽位 → 广播规划表。「每 rank 恰好 S×K」由构造保证（每源恰 S×K 条目 + 列容量 ≤ CAP + 贪心终态），无需迭代求解。V
  • 代价与回报：代价是迁入专家在本 rank 没有权重（预取槽复制 / 对称内存直读兜底，梯度独立 buffer 归约回 home）；回报是静态形状——消除每层 host 同步、无动态分配器、高失衡下不 OOM。V
  • 实测（8×H20，vs DeepEP v2 elastic）：通信时间随失衡（maxvio 0.2→20）几乎不变而 DeepEP 持续恶化；combine 各水平显著更快（高失衡约 21%）；dispatch 含规划+预取在低失衡下略慢、maxvio≥10 反超；端到端（9 层 MoE）maxvio=5 起领先 3.9–11.1%，maxvio=20 时 DeepEP OOM 而 MoonEP 正常跑完。R（图读数）
  • 生态：vLLM 已合入（PR #52101 “BF16 integration of MoonEP balanced EP backend”，2026-09-18 merge）；与 Kimi K3 的关系（开放日同期开源）官方未直接背书，U。V/U
  • 边界：单节点 NVLink 域（EP = 节点内 world size）、依赖 NVSwitch multicast、bf16 + H/H′ 需 128 倍数、权重必须是连续 $[E{+}B, H, H']$ 对称张量（与现有引擎布局深度耦合）、rank0 规划是串行热点。V

2. 身份与定位：通信库，不是引擎

README 自述：“keeps token loads perfectly balanced across ranks via dynamic redundant experts”。三个容易误读的点先钉死：V

  1. 它是通信库（对标 DeepEP 的位置）：提供 dispatch/combine/prefetch/reduce_grad 四个算子，group GEMM 由框架做——但「均衡」内嵌在通信库里（规划器是库的一部分），这与 DeepEP「给什么路由搬什么货」根本不同。
  2. 「完美均衡」是精确含义：每个 rank 恰好收到 $S \times K$ 个实 token（S = 每 rank 输入 token 数，K = top-k），与路由倾斜无关——不是「尽量均衡」的启发式目标。
  3. 动态冗余专家是手段：迁入的 token 要用本 rank 没有的专家 → 每步把少量远端专家权重预取进 B 个槽（推理可越界直读）。冗余是每步动态变化的，与 EPLB/UltraEP 的「分钟级/每 microbatch 复制」都不同粒度。

时间线：开源于 2026-07 末（媒体集中 2026-07-28~08-02，与 Kimi K3 开放日同期；“是否为 K3 三大 Infra 技术之一”无一手出处，U）；vLLM 集成三步走（RFC #52095 → PR #52101 BF16 backend 已合入 2026-09-18 → PR #54147 tools/ep_kernels 构建链，open）。真武 PPU 支持“under review”。V

3. 核心思想：构造性均衡 —— token 均衡的第三条路线

把本系列四条路线并排放，MoonEP 的独特性才看得清：

路线代表均衡动作改变什么
慢环放置EPLB分钟级重排 + 复制专家放哪（权重搬一次管很久）
比例分流LPLB每 batch 解 LP 定 0/1 之间的比例token 在既有副本间的比例
激活选副本METRO每 batch 贪心选单一副本decode 的激活专家集合
重新分组MoonEP每步重算「谁给谁多少」+ 预取权重token 的目的地 + 少量权重的临时位置

关键差别：EPLB/LPLB/METRO 都接受「专家→rank」的映射是给定的，只在 token 侧做文章；MoonEP 每步重排分组本身——超载组的 token 连同（预取的）专家权重一起挪到空 rank。所以它不需要负载预测（用本步真实路由），也不需要 aux-loss 配合，代价是每步多一次规划 + 权重预取的通信。V

「每 rank 恰好 S×K」为什么能白拿：每个源 rank 产出恰 $N = S \times K$ 条目（每 token 恰 K 个路由）；组间贪心以 CAP = N 为容量互填（各源总和 = 各容量总和，Σbal = 0），受方一次补满的终态即「每列恰好 N」——性质由构造保证，测试只验守恒/容量不变量而不需要断言它。V

图 2 · 完美均衡的构造：CAP=S×K 的贪心互填——左为路由自然倾斜（DeepEP 式「最热 rank 定步时」），右为规划后每 rank 恒 S×K；下方为 A1 伪码与构造性性质。drawio 源文件同上（完美均衡的构造 sheet）。

4. 在线规划内核：一个 cooperative grid 的 Phase A–D

planning.py，入口 launch_planning(ctx, topk_experts_flat, tokens_per_expert, cu_seqlens, plan)，输入是本 rank 的真实路由；单内核 num_sms×CTA、512 线程/CTA，分阶段：V

cap = S*K
gt[h] = Σ_{e ∈ home group h} tpe_all_ranks[e]        # A0：multimem 多播汇聚，rank0 算前缀和
bal[h] = gt[h] - cap                                  # Σbal = 0
while (h = argmax bal) > 0:                           # A1：组间贪心互填
    u = argmin bal; z[h,u] = -bal[u]                  #   超载组 → 最空组
    bal[h] += bal[u]; bal[u] = 0                      #   受方一次补满 ⇒ 每 rank 恰收 cap
for each home group h:                                # A2：专家级过户
    while (d = argmax z[h]) > 0:
        e = 本组剩余最多的专家; take = min(rem, quota)
        alloc[e,d] += take; alloc[e,h] -= take        #   ⇒ 迁移专家数最少（整组整组地搬）
for each dest rank d:                                 # A3：选预取专家 + 铺 VM 布局
    experts_to_copy[d] = alloc 中 token 最多的 B 个远端专家
    for g in [0, E+B): cu_seqlens[d,g] = pad 到 token_padding 倍数的累积段末
rank0 一次多播整张规划表
每 rank：C1 本地 topk 按 expert 排序（直方图 + 段前缀 + match_any）
         C2 对每条目在 alloc_cumsum 上固定趟二分 → dst = rank·NvS + 段内偏移
            同 token 命中同 dest 的后续项编码为 -(raw)-1（dedup）  D 本地化输出 + 设备端 barrier

四点值得注意：① 贪心目标是「最小化迁移」（受方一次补满 → 尽量整专家过户），冗余专家只在「某组溢出需要远端接盘」时出现；② 每个 dest 至多从一个远端 home 组接收 ⇒ B = E/R 个预取槽即够训练全本地化；③ rank0 承担汇聚/贪心/广播（单 warp 贪心循环是串行段）；④ NvS = S×K + (token_padding−1)·2·epn 是 padding 上界的闭式解——shape 仍然全静态。V

5. 端到端数据流：融合 permute 的通信

图 1 · MoonEP 端到端：前向（规划 → 预取/直写 dispatch → 静态 group GEMM → 融合 unpermute 的 combine）与反向（plan 复用 + 梯度归约）。drawio 源文件：assets/moonep-deep-reading.drawio（MoonEP 端到端数据流 sheet）。

两个「融合」是理解 MoonEP 通信的钥匙：V

  • permute 融进 dispatch：没有独立 permute 内核——token 行用 cp.async.bulk 直接写到远端 rank 的 expert-grouped 槽位（dst 编码的偏移处）；同一 token 命中同 dest 的 K 项被规划器 dedup 成 1 次传输，epilogue 再本地扇出到副本槽。group GEMM 拿到的 buffer 天然按专家分组。
  • unpermute 融进 combine：combine_prologue 先把重复行 fp32 预规约回 primary；combine 只拉 primary 行、按路由权重求和回 token-major。route weight 全程按 int32 视图在 meta 区 scatter/gather，从不 dedup。
  • zero_copy：dispatch 返回 NVL shard 的视图，专家 FFN 原地读写（combine 端用 data_ptr() 断言同一块）——消灭 comm→用户缓冲的边界拷贝；代价是视图生命周期约束（autograd 反向须 zero_copy=False）。

6. 内存模型：统一权重张量与 B 槽

与框架的契约是全库最「硬」的部分：每个投影（gate/up/down）每层一个连续对称内存张量 $[E{+}B, H, H']$，各 rank 布局相同（“contiguity is a hard requirement”——VM 组 GEMM 靠行寻址专家，这是与「每专家独立张量」框架不兼容、vLLM 需专门适配的原因）：V

行区间内容说明
$[0, E)$各 home rank 的主专家参数物理上就是主 rank 参数内存经对称映射全局可见
$[E, E{+}B)$本 rank 预取槽prefetch 按 experts_to_copy 填充；物理内存来自跨层共享的进程级池（额外成本 = 全模型 B 份专家权重，非每层 B 份）
  • 训练 B = E/R（规划器保证 GEMM 只摸本地行）；推理推荐 B = 3–4，槽不够时 group GEMM 按对称映射直读 home 行（稍慢、正确）。
  • 梯度侧：预取槽的梯度不是参数梯度，放独立 fp32 reduce buffer $[R,B,H,H']$（同池）；reduce_grad 让每个 home rank 经 NVLink 远端读回自己专家的槽梯度、fp32 累加，barrier 后只本地清槽（注释：曾试远端清零被否——同向 NVLink 读写共享带宽）。

7. 工程底座：CuTe DSL + 对称内存 + 无 host 同步

  • 全部内核用 CUTLASS Python DSL（CuTe）写，JIT + host LRU 缓存，shape 全 constexpr 特化；不是 Triton 也不是手写 .cu。csrc/ 仅 478 行：VMM 对称内存（cuMemCreate/Map/Export fd）+ NVSwitch multicast（BindMem）驱动封装。唯一 pip 依赖 nvidia-cutlass-dsl==4.4.2。
  • 对称内存全 RW：各 rank 的 chunk 按 rank 序 map 进一段连续 VA，dispatch 直写远端区；multicast VA 上的 multimem.st = 硬件扇出广播（规划表一次广播）。fd 经 AF_UNIX SOCK_DGRAM + SCM_RIGHTS 传递；对齐是血泪教训集中地（chunk 字节数必须对齐 VMM/multicast 粒度的 max）。
  • 无 host 同步：cooperative launch + 自复位 grid/cross-rank barrier（DeepGEMM 血统，fence.proxy.alias/async.global 桥接 multicast 与 TMA）+ PDL + 设备端读 dup_counts + 全静态 shape——「静态形状消除逐层 host 同步」的完整含义。
  • 位宽契约：RANK_BITS=7（R≤128）、KIDX_BITS=7；跨 2^31 地址运算显式 i64；bf16 payload 需 H%8==0，H/H′ 需 128 倍数（2D TMA tile）。

10. 局限（代码级可见）

  • 单节点 NVLink 域：EP = 节点内 world size（bench 即 8 卡）；跨节点 EP 需上层再切（与 UltraEP 的 RSN 域约束同型）；
  • 依赖 NVSwitch multicast（规划广播路径硬依赖）；bf16 + H/H′ 128 对齐、token_padding 上界约束；
  • 布局契约深度耦合：连续 [E+B,H,H′] 对称张量 + cu_seqlens 寻址，与「每专家独立张量」的现有框架不兼容——vLLM 走专用 backend 适配，其他引擎移植成本高；
  • rank0 串行规划热点：汇聚 + 单 warp 贪心 + 广播集中在 rank0（靠组数少/B 小摊薄），规模上去后的伸缩性未验证；
  • S 静态：每 rank 输入 token 数固定（静态 shape 的另一面）——变长 batch 需 padding 到 S，浪费随流量波动增大；
  • 无第三方大规模复现：README 之外只有小型博客级复现；「K3 在用」无一手出处。U

12. 快问快答

Q1：「完美均衡」真的完美吗？

它均衡的是每 rank 的 token 计数量（恒 S×K），不建模每专家计算时间差异与 group GEMM 的非线性——与 LPLB/METRO 的 token-only 目标同源的盲区（TEMPO 方向）。但在「token 数就是一阶瓶颈」的场景（通信量 ∝ token 数）它是构造性的最强保证。R

Q2：和 DeepEP 的本质区别一句话？

DeepEP 是「忠实搬运工」：路由给什么搬什么，最热 rank 决定步时；MoonEP 是「调度型通信库」：每步先算一个均衡的目的地分配（连权重预取一起规划），再按计划直写。代价 = 规划 + 预取开销（低失衡 ≈2% 端到端），收益 = 失衡免疫 + 静态形状。V

Q3：推理能用吗？

能，且已进 vLLM（BF16 balanced EP backend，2026-09-18 合入）。推理路径 B=3–4 预取槽 + 越界对称直读兜底，无梯度归约负担；静态形状对 CUDA Graph 友好。V

Q4：为什么要「连续统一权重张量」这么苛刻？

group GEMM 按 cu_seqlens 的行段寻址专家，要求 [E+B,H,H′] 一整块连续内存（本地行 + 预取槽同张量）；这也让预取 = 行拷贝、越界读 = 对称映射直读。换来的是零拷贝视图与 fused permute——契约苛刻但机制简单。V

Q5：规划每步都跑，开销真的可忽略吗？

单 cooperative kernel、无 host 往返、rank0 广播一次；对拍中 MoonEP 已把 plan 单独计时并计入总账——低失衡下端到端 ≈2% 的落后就是这个开销的显影。规模大（组多、专家多）时 rank0 单 warp 贪心是串行段，宣称「negligible」在你的规模上要自己量。R

Q6：它和 EPLB 们互斥吗？

分层可叠：放置层（EPLB 类）决定主专家基座分布，MoonEP 每步在其上重分组 + 预取；但 MoonEP 的预取槽已经承担了「冗余」角色，再叠 EPLB 复制的边际收益取决于基座是否长期偏斜。R
