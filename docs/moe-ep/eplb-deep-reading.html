EPLB 深度阅读笔记 —— 冗余专家、三步放置算法与不停服重排

阅读对象：DeepSeek 开源的 Expert Parallelism Load Balancer（EPLB）——一个只有 eplb.py（约 170 行 PyTorch）的专家放置与复制算法，以及它在 vLLM / SGLang 中的工程化集成。本文按「原理 → 算法流程（含逐位验证的实例推演）→ 代码 → 实测效果与局限」展开。

证据标注：V = 一手核对（官方源码 / 文档 / 论文原文，2026-09-18 抓取 main 分支）；R = 合理推断；U = 待核实。

系列定位：方案级对比见 MoE EP 方案深度解析 §4，逐行笔记见 源码级对比分析 §3；本文是 EPLB 单独的完整深读（含 vLLM/SGLang 集成与真实部署数据），可独立阅读。

1. 一页结论

  • EPLB 是什么：给定每个逻辑专家的负载统计 $w_i$，计算一份「复制 + 放置」方案——复制热专家（冗余专家）、再把所有物理副本均衡地装进各 GPU，输出三件套映射 phy2log / log2phy / logcnt。它只做放置计算，不改路由分数、不碰权重数值、不做负载预测（预测方法留给使用方）。V
  • 算法核心两招：① replicate_experts——每轮贪心复制 $\operatorname{argmax}_i (w_i / c_i)$ 的专家，让有效负载 $\mathrm{eff}_i = w_i/c_i$ 趋于平整；② balanced_packing——按权重降序把对象放进「当前最轻且未满」的包（先用于组→节点，再用于专家→GPU）。层次化策略利用 V3 的组限定路由让同组专家同节点，省跨节点 IB 流量。V
  • 工程闭环三步：在线统计（recorder 环形窗口）→ 周期触发计算新布局（V3 ≈ 每 10 分钟；SGLang 默认每 1000 次迭代）→ 权重按新布局 P2P 迁移 + 元数据原子切换，全程不停服。V
  • 实测收益：官方站数据：负载不均最多降 85%、吞吐最多 +40%、GPU 利用率 95%+；LMSYS 96×H100 PD 分离部署（DeepSeek-R1，256+32=288 专家）：prefill 1.49×、decode 2.54×。V
  • 边界与代价：开环控制——负载预测「尽力而为」，分布漂移会削弱效果；token 均衡 ≠ 延迟均衡；冗余专家吃显存（vLLM 文档：DeepSeek-V3 每个冗余专家每 rank 约 2.4 GB）；重排本身有权重搬运开销。训练期同族问题另由 DeepSeek LPLB（LP 求解）承接。V

2. 问题背景：为什么推理期需要专门的负载均衡

2.1 训练期的均衡保证不了推理期

DeepSeek-V3 训练用 auxiliary-loss-free 均衡（router 分数加偏置），保证的是训练分布上的长期期望均匀。到了推理侧，V3 报告明确指出两个残余挑战（§4.5.3）：V

  • 序列/小 batch 内不均：单条序列或小 batch 里，token 集中涌向少数专家，统计涨落来不及平均；
  • 域偏移（domain shift）：线上流量与训练分布不同（例如某领域请求占比骤增），专家热度整体迁移。

再加上 EP 部署的硬约束——all-to-all 的完成时间由最重的那张卡决定（makespan = straggler 的完工时间），任何不均都直接变成整层气泡。解决办法不是改路由（会伤模型质量），而是改放置：把热专家多放几份、把冷热专家搭配着装卡，让每张卡的期望负载拉平。

2.2 V3 的部署形态（EPLB 的设计前提）

阶段最小部署单元MoE 并行冗余专家
prefill4 节点 × 8 卡EP3232 个（每卡 8 常驻 + 1 冗余位）

通信不对称是层次化设计的根源：NVLink 域内 160 GB/s，跨节点 IB 约 50 GB/s（约 3.2 倍差距）。V V3 的组限定路由（node-limited routing，$M=4$：每个 token 最多被送往 4 个节点）让「专家组」成为天然的节点级打包单位——EPLB 的层次化策略直接利用这一点：组不跨节点 ⇒ 同组专家的 token 只需送到一个节点，跨节点 IB 流量最小。V

2.3 形式化目标

记逻辑专家数 $N_{\mathrm{log}}$、物理副本数 $N_{\mathrm{phy}} = N_{\mathrm{log}} + R$、专家 $i$ 的负载统计 $w_i$、副本数 $c_i$（$\sum_i c_i = N_{\mathrm{phy}}$）。EPLB 要近似求解：R

\[ \min_{\text{放置},\, c}\ \ \max_{g \in \mathrm{GPUs}}\ \sum_{i \in \mathrm{GPU}_g} \mathrm{eff}_i, \qquad \mathrm{eff}_i = \frac{w_i}{c_i}, \qquad \text{s.t. } |\mathrm{GPU}_g| = \frac{N_{\mathrm{phy}}}{G}\ \ \forall g \]

两个硬约束保证可部署：每卡槽位数相等（显存/参数均衡，$N_{\mathrm{phy}} \bmod G = 0$），层次化模式下再加组不跨节点（通信均衡）。这是一个带整数约束的 min-max 装箱问题（NP-hard），EPLB 用两步贪心求近似解——这正是它只有 170 行的原因，也是后来 LPLB 用线性规划求精解的动机。R

下面把这一个优化式拆成四步解释：为什么是负载最重卡，而不是总负载；$\mathrm{eff}_i = w_i/c_i$ 是怎么出现的；两个约束分别对应什么工程事实；它为什么确实是一个“装箱”问题。

2.3.1 第一步：优化目标为什么是 $\max_g L_g$，而不是 $\sum_g L_g$

MoE 层在专家并行下的延迟不是所有卡的总计算量，而是最慢那张卡的完工时间。all-to-all dispatch/combine 之后，整层必须等所有卡都完成 expert FFN 才能进入下一层，因此每层完成时间近似为

\[ T_{\mathrm{layer}} \approx \max_{g}\ \mathrm{Work}_g \;\propto\; \max_{g}\ \sum_{i \in \mathrm{GPU}_g} \mathrm{load}_i \]

若定义卡 $g$ 的负载 $L_g = \sum_{i \in \mathrm{GPU}_g} \mathrm{load}_i$，那么优化目标是 $\min \max_g L_g$。把总负载 $\sum_g L_g$ 做平均是没有意义的：哪怕总负载完全一样，只要一个专家把某一卡顶爆，那一卡就是 straggler。这正是 V3 §4.5.3 里“某个领域的请求集中于某专家、导致它所在 rank 过载”的直接形式化。

2.3.2 第二步：$\mathrm{eff}_i = w_i / c_i$ 不是新定义，是“复制后的每副本负载”

初始时每个逻辑专家只有一个物理副本，$c_i=1$，卡负载就是放在该卡上的专家负载之和。冗余专家机制允许把专家 $i$ 复制到 $c_i$ 张卡上。若 dispatch 时把属于 $i$ 的 token 在 $c_i$ 个副本之间均匀分流，则每个副本平均只承接 $w_i/c_i$ 的 token 流；这个量才是参与装箱的“物品重量”。

所以 $\mathrm{eff}_i$ 的语义应读作：

\[ \mathrm{eff}_i = \frac{\text{逻辑专家 } i \text{ 的总负载}}{\text{其物理副本数}} = \text{每个物理槽位平均分担的负载} \]

副本数 $c_i$ 是整数，并受物理槽位总数约束 $\sum_i c_i = N_{\mathrm{phy}}$。增加 $c_i$ 会摊薄 $\mathrm{eff}_i$，但也会占用更多槽位，这就是“用显存换负载均衡”的量化表达。

2.3.3 第三步：两个约束从哪来

  • 每卡槽位数相等：$|GPU_g| = N_{\mathrm{phy}}/G$。专家参数在 EP 下按卡存放，每张卡能放多少专家由显存上限决定；若某卡多放专家，另一卡必然少放，这会造成显存不均衡、内存容量成为新的 straggler。因此可部署的放置必须保证每卡专家数相同，也要求 $N_{\mathrm{phy}} \bmod G = 0$。
  • 层次化模式下的“组不跨节点”：V3 的 node-limited routing（$M=4$）把一组专家固定在一个节点内，组内走 NVLink，跨节点才走 IB。若一个专家组被打散到多个节点，token dispatch 就不得不跨 IB，通信开销显著上升。因此层次化版本把“组”作为节点级装箱单位，等价于每个节点内的槽位打包满足容量约束，组不拆散。

2.3.4 第四步：为什么这是装箱问题，且 NP-hard

把问题收缩到一个特例就看得最清楚：先冻结副本数 $c$（即每个专家的“物品重量” $w_i/c_i$ 已确定），只做放置。此时我们面对的是：把 $N_{\mathrm{phy}}$ 个重量各异的物品装进 $G$ 个容量均为 $C$ 的箱子，每个箱子恰好装 $K = N_{\mathrm{phy}}/G$ 个物品，目标是最小化箱子中重量之和的最大值。

\[ \min_{\pi}\ \max_{g}\ \sum_{i \in B_g} a_i, \qquad a_i=\frac{w_i}{c_i},\quad |B_g|=K,\quad \bigsqcup_g B_g = \{1,\dots,N_{\mathrm{phy}}\} \]

“恰好 $K$ 个物品”可等价化为经典 multiprocessor scheduling 问题：$G$ 台同构机器、$N_{\mathrm{phy}}$ 个任务、每个任务必须完整放到一台机器，目标是最小化 makespan（最长机器完成时间）。这个问题是 NP-hard；若再把副本数 $c_i$ 也作为整数变量一起优化，只是额外增加“通过复制把一个重量拆成多个更轻物品”的选择维度，并不会变简单。所以 EPLB 的完整问题也是 NP-hard。

把复制也放进来后，装箱问题的“物品”与“箱子容量”还有一层特殊关系：

总“物品重量”会随复制而下降，但“物品个数”却从 $N_{\mathrm{log}}$ 增到 $N_{\mathrm{phy}}$：

\[ \sum_i \mathrm{eff}_i = \sum_i \frac{w_i}{c_i} \le \sum_i w_i \]

这正是 EPLB 不用精确求解、而用两层贪心的原因：

  1. 先决定每个专家复制几份（连续视角近似：让热专家的 $w_i/c_i$ 尽量贴近某个目标负载）；
  2. 再把 $N_{\mathrm{phy}}$ 个已定重量的物品按降序装入当前最轻的箱子（`balanced_packing`，对应 4.1 节）。

这样就把一个 NP-hard 的 min-max 装箱问题，降成了一个可解释、可增量执行的近似解。后续 LPLB 用线性规划把这个目标转成可精确优化的 LP 形式，也是为了解决同一套不等式约束下贪心解可能偏离最优的问题。

3. 核心思想：冗余专家（Redundant Experts）

只做置换（permutation）的均衡有个天花板：当某单个专家的负载超过每卡平均负载时，无论怎么排列，装下它的那张卡必然超载。冗余专家补上这块短板——复制是连续可调的负载分担旋钮：副本数 $c_i$ 每加一，该专家的有效负载减半式下降。V3 论文原文："we introduce a deployment strategy of redundant experts, which duplicates high-load experts and deploys them redundantly"，且高负载专家由在线统计检测、周期性调整（约每 10 分钟）。V

副本怎么被使用？路由仍按逻辑专家算（TopK 得到逻辑 id），dispatch 时查 log2phy 表把 token 送到某个物理副本（按 rank 取模等方式分流），副本输出再按 phy2log 归并。路由分数与模型行为完全不变——变的是「同一个逻辑专家住在哪里、住几份」。

3.1 三件套的语义

张量形状语义
phy2log$[L,\ N_{\mathrm{phy}}]$每个物理槽位装的是哪个逻辑专家（dispatch/combine 的真值表）
log2phy$[L,\ N_{\mathrm{log}},\ \max c_i]$每个逻辑专家的物理副本槽位列表（不足补 $-1$）
logcnt$[L,\ N_{\mathrm{log}}]$每个逻辑专家的副本数 $c_i$（权重迁移量 = 副本数）

注意三个映射都是逐层的：不同 MoE 层的专家热度不同，各自独立计算放置。V

4. 算法详解（eplb.py 逐函数）

入口只有一个：rebalance_experts(weight, num_replicas, num_groups, num_nodes, num_gpus)。若 num_groups % num_nodes == 0 走层次化，否则退化为全局（把组数、节点数都置 1）。V

4.1 balanced_packing：降序 + 最轻未满包

把 $n$ 个带权对象装进 $m$ 个包，每包恰好 $n/m$ 个（容量硬约束，保证每卡槽位相等）：

  1. 按权重降序排序；
  2. 逐个取出，放进「当前总重最小且未满」的包。

这是经典的 LPT（longest processing time first）贪心：大件先放，小件填缝。它只保证「像样的」均衡——例如 $L_0$ 的组打包结果 $446 / 587$ 并不完美（见 §4.5 推演），因为容量约束先于完美均衡。R

4.2 replicate_experts：贪心复制 $\operatorname{argmax}(w_i / c_i)$

从 $c_i = 1$ 出发，逐个填充冗余槽位：每轮选当前有效负载最大的逻辑专家加一副本。

\[ i^{*} = \operatorname*{argmax}_{i}\ \frac{w_i}{c_i}, \qquad c_{i^{*}} \leftarrow c_{i^{*}} + 1 \]

为什么除以 $c_i$：复制一份就是让该专家的负载由两份均摊，$w_i / c_i$ 正是每个副本的期望负载——反复选它，等价于用水位线把最高的「副本负载」往下压，$R$ 轮后所有副本的有效负载尽量平整。函数注释直言目标："such that the maximum load of all replicas is minimized"。V

4.3 rebalance_experts_hierarchical：三步流水

步做什么用什么权重通信动机
Step 1 组→节点把专家组均衡打包到节点组内负载和 $w_{G}$组不跨节点 ⇒ token 少过 IB（配合 V3 组限定路由）
Step 2 节点内复制每节点独立做 replicate_experts节点内逻辑专家 $w_i$复制发生在 NVLink 域内，副本间同步/迁移便宜

实现上有两个纯技巧性的映射变换：Step 1 后把专家重编号为「节点主序」（log2mlog），Step 3 后再经两级逆映射换回全局逻辑 id（mlog2log、pphy2phy）——张量下标的花式搬运，逻辑仍是三步打包。V

4.4 全局策略与选择依据

README 的表述：层次化「适用于 prefill 阶段、专家并行度较小的场景」，全局「适用于 decode 阶段、专家并行度较大的场景」。V 直觉：R decode 的 EP 度极大（V3 达 EP320、每卡 1 专家），组约束此时反而限制复制自由度；且 decode 通信走低延迟内核、对组聚集收益不敏感。全局策略 = 跳过 Step 1，全局复制 + 全局打包（2025-03-21 的 commit e1100fe 还为全局策略补上了 GPU 级均衡）。V

4.6 算法性质小结

  • 复杂度：每层 $O(N \log N)$（排序）+ $O(N \cdot R)$（贪心），纯 CPU 上的小张量计算，毫秒级——重排的瓶颈永远在权重搬运，不在布局计算。R
  • 贪心无最优保证：两步贪心（先定副本数、再打包）解耦了本应联合优化的变量，是速度与质量的折中；LPLB（DeepSeek 2026）用 LP 在训练期求更优分配。V
  • 负载定义留给使用方：README 明确 "the exact method to predict the loads is out of the scope of this repo"——统计口径（token 计数 / 计算时间 / 滑动平均）由集成方决定。V

5.1 统计收集

  • SGLang：ExpertDistributionRecorder 在 forward 中旁路记录每逻辑专家 token 数，环形 buffer（--expert-distribution-recorder-buffer-size）；可 dump 累积统计（喂给 EPLB 实时优化）或逐 batch 数据（离线分析与模拟）。触发条件还要求 eplb_rebalance_num_iterations ≥ buffer_size，防止用到陈旧统计。V
  • vLLM：开启 EPLB 后每次 forward 收集负载统计，以 window_size（默认 1000 步）为决策窗口。V
  • 为什么能统计到：EP dispatch（DeepEP / DeepGEMM masked grouped GEMM）按物理专家收发 token，天然知道每专家的 token 量——统计是通信内核的免费副产品。R

5.2 触发与执行（LMSYS 的三阶段迁移）

SGLang 的 EPLB 部署（LMSYS 博客）把重排拆成三阶段，保证高效且不中断服务：V

  1. 系统加载阶段：权重可预取进主存加速重排，或 mmap 留在磁盘省内存；
  2. 准备阶段：所需权重后台异步传入显存，利用空闲 DMA 引擎，不打断 GPU 计算；
  3. 执行阶段：device-to-device 拷贝落位，可用物理内存重绑定进一步优化。

重排频率的实践经验：定期重排（利用负载的时间局部性），前提是尽量压低权重重载成本；增大 batch size（扩集群或 MTP）也能减少专家使用的随机波动、改善均衡。V

5.3 元数据切换与路由

权重落位后，physical_to_logical_map 原子替换，dispatch 按 log2phy 把同一逻辑专家的 token 分流到多个副本。SGLang 的 ExpertLocationUpdater 还为「rank 故障导致专家缺失」留了恢复路径（DRAM backup / 磁盘 reload，见 §6.3）。V

6.1 官方 eplb.py 的灵魂片段

复制贪心的核心只有五行（完整源码见 eplb.py，MIT 许可）：

for i in range(num_log, num_phy):
    redundant_indices = (weight / logcnt).max(dim=-1).indices   # 贪心：选有效负载最大的专家
    phy2log[:, i] = redundant_indices                            # 新物理槽位 ← 该逻辑专家
    rank[:, i] = logcnt[arangen, redundant_indices]              # 这是它的第几份副本
    logcnt[arangen, redundant_indices] += 1

打包贪心同样短（balanced_packing 内层）：按降序遍历，放入「未满包里总重最小」的那个：

for group in indices[i]:                       # indices 按权重降序
    pack = min((i for i in range(num_packs) if pack_items[i] < groups_per_pack),
               key=pack_weights.__getitem__)    # 最轻且未满
    pack_index[i, group] = pack
    ...
    pack_weights[pack] += weight[i, group]

7. 实测效果与代价

7.1 官方与社区数据

  • DeepEP 官网：负载不均最多降 85%、吞吐最多 +40%、平均 GPU 利用率 95% 以上、多 GPU 扩展接近线性。V
  • LMSYS 96×H100（PD 分离，DeepSeek-R1）：256 逻辑 + 32 冗余 = 288 物理；EPLB 带来 prefill 1.49×、decode 2.54× 加速。prefill profile：DeepSeek 实测 62,713 tokens/s/节点，SGLang 默认布局 50,302（慢约 20%），模拟完美 EPLB 达 59,337（差距缩至约 6%）——默认随机布局到 EPLB 的差距远大于 EPLB 到完美均衡的差距。均衡度（平均/最大每卡 token 数）与吞吐强相关。V
  • 专家分布观察：多数专家很少被使用、少数专家高频使用（天然不均）；prefill 与 decode 的分布相似但不相同——支持 PD 分离各用一套放置。V

7.2 代价清单

  • 显存：冗余专家是纯增量参数。vLLM 文档量化：DeepSeek-V3 每个冗余专家每 rank 约 2.4 GB——内存紧张时不可用。V
  • 重排开销：权重搬运（同卡拷贝 / P2P 通信）+ 短暂的统计-执行窗口；SGLang 用分片 yield、vLLM 用 async worker 压感知。
  • 开环风险：LMSYS 实验因缺线上真实统计，用 in-distribution 数据喂 EPLB（作者自认局限）；分布漂移时收益打折。V

9. 快问快答

Q1：EPLB 会改变模型的输出吗？

不会。路由分数、专家权重数值都不动；它只改变「专家住哪、住几份」。同一逻辑专家的多副本输出按 phy2log 归并，数学上等价于原模型。V

Q2：为什么用贪心而不是最优解？

问题是 NP-hard 的 min-max 装箱；贪心毫秒级出「像样」的解，而重排的真实瓶颈在权重搬运。追求最优分配的场景（训练期）后来有了 LPLB 的 LP 求解。R

Q3：冗余专家数 $R$ 怎么选？

约束：$N_{\mathrm{phy}} \bmod G = 0$（每卡槽位整数）。V3 prefill 用 32（每卡 8+1）；vLLM 大规模部署同样建议 32。$R$ 越大均衡自由度越高，但显存线性增长（V3 每 rank 每Expert ≈ 2.4 GB）。附带收益：$N_{\mathrm{phy}}$ 不必是 2 的幂，EP 度可选 12、72 等灵活规模（LMSYS）。V

Q4：层次化和全局策略怎么选？

代码只看一个条件：num_groups % num_nodes == 0 走层次化，否则全局。工程直觉是 prefill / 小 EP 用层次化（组聚集省 IB），decode / 大 EP 用全局（复制自由度优先）。V

Q5：重排期间服务会停吗？

不会。SGLang：层分块 + generator yield 分片执行 + temp buffer 双阶段写；vLLM：async worker 异步执行；LMSYS：三阶段（主存预载 → DMA 异步传输 → D2D 拷贝）。V

Q6：每层都独立重排吗？

是。三件套形状都是 $[L, \cdot]$——不同层的专家热度分布不同，各自计算放置；SGLang 还可按层分块执行迁移。V

Q7：EPLB 和 DeepEP 什么关系？

分工：DeepEP 负责 token 的 all-to-all 通信（normal / low-latency 内核），EPLB 决定「专家怎么摆」。EPLB 均衡了负载，DeepEP 的 dispatch/combine kernel 等待时间与方差随之下降——LMSYS 的 profile 里两者是配套出现的。V

Q8：训练期也能用 EPLB 吗？

EPLB 面向推理/部署的静态重排（论文语境是 redundant experts 部署策略）。训练期同族问题由 LPLB（LP-based load balancer，DeepSeek 2026 开源）处理。训练期的持续重均衡另见 负载均衡综述 §4.2 的系统级方案。V
