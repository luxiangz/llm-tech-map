LPLB 深度阅读笔记 —— 冗余边上的线性规划与单 SM 内点法

阅读对象：DeepSeek 开源的 LPLB（Linear-Programming-Based Load Balancer）——面向 MoE 训练期的逐 micro-batch 负载均衡器：在冗余专家构成的图上解一个小型线性规划，把每个热专家的 token 按最优比例分流到两个副本，求解器是一个跑在单个 SM 上的 5 次迭代内点法（~100 µs）。

证据标注：V = 一手核对（2026-09-23 抓取的仓库源码/README：初始提交 2025-11-19，仅此一 commit）；R = 合理推断；U = 待核实。

系列定位：与 EPLB 深读（推理期静态放置）、METRO 深读（decode 激活专家均衡）构成三部曲；LPLB 官方自述 "early research stage"，性能仍在评估，本文以源码一手核对为主。

1. 一页结论

  • LPLB 是什么：训练期（也可用于推理）的动态负载均衡器。EPLB 用历史统计做低频静态重排，对付「持续偏热」；LPLB 在每个 micro-batch 上解一个 LP，对付「小批次随机波动」——两层互补，且 LPLB 内部直接 import EPLB 算法打底。V
  • 建模：把冗余专家看成图的边（每条边恰好连接 2 个 GPU：原件所在卡 + 副本所在卡）。LP 的自由度只有一件事：每条边上的分流比 $o_{k,d} + r_{k,d} = 1$（该专家的 token 两端各承担多少）；目标是最小化 8 卡组内的最大负载 $\min t$。变量数仅 $2GD + G + 2$（$G=8, D=2$ 时 36 个）。V
  • 求解器：不用 CPU/GPU 通用求解器，而是在单个 SM 上手写原始仿射尺度内点法（Dikin 类乘性更新，固定 5 次迭代），线性代数用 cuBLASDx 矩阵乘 + cusolverdx 块高斯消元在共享内存里完成；不可行则回退 0.5/0.5 均分。V
  • 本文独立验证：用 numpy 复刻其 LP 构造与 5 次迭代求解（assets/lplb_lp_verify.py），两种合成实例把组内 imbalance 从 1.18 / 1.22 压到 1.002，距理论下界 $\max(\text{组均值}, \text{最大固定负载})$ 不到 0.004——5 次迭代即实质最优。V
  • 边界：只均衡 token 数（不建模 grouped GEMM 的非线性耗时）；节点内求解 ~100 µs、每层每 batch 都要解，小 batch 下开销占比不可忽略；极端全局不均时可能比 EPLB 更差（每专家最多 1 个副本，分流自由度有限）。官方明确 early research stage。V

2. 问题背景：EPLB 管不到的那部分不均

EPLB 的输入是统计窗口内的平均负载，重排周期以分钟计（V3 ≈ 10 min）。但 MoE 训练的单个 micro-batch 里，专家热度是随机涨落的：某个 batch 恰好集中一堆代码 token，第 37 层的 e112 瞬间被挤爆，下个 batch 又换别人。这类波动有两个特点：周期太短（来不及搬权重）、幅度可控（涨落围绕均值）。LPLB 的解法：权重不动，让已经放在两处的副本按需分流——「重排太贵，那就只调路由比例」。R

注意分工：训练期主损失里的 aux-loss-free bias 保证长期期望均匀（防坍缩），EPLB 保证静态放置均衡，LPLB 兜住逐 batch 涨落——三层各管一个时间尺度。V

3. 核心思想：冗余专家 = 图上的边

LPLB 的冗余结构由矩阵 $\mathrm{r2o} \in \mathbb{Z}^{G \times D}$ 描述（$G$ = 组内 rank 数，$D$ = 每 rank 冗余槽数）：rank $k$ 的第 $d$ 个冗余槽，是 rank $\mathrm{r2o}[k][d]$ 的第 $d$ 个专家的副本。planner 的 docstring 强调约束：每个冗余专家恰好被 2 个 rank 共享（原件方 + 副本方）。V

把 rank 当节点、每个冗余专家当一条边，就得到一张「token 可以沿边流动」的图。README 给出三种拓扑：V

拓扑规模边结构特点
Cube8 GPU/组，$D=2$立方体 + 对角边节点内 NVLink 高效
Hypercube16 GPU，$D=2$无对角边更大组
Torus任意 $m \times n$节点内邻居 + 跨节点邻居全局均衡好，跨节点流量高

关键限制：每个逻辑专家最多 2 份（planner 断言 max_logcnt == 2）——分流自由度被有意控制在「二选一按比例」上，这是 LP 能做小的前提，也是它在极端不均下不如 EPLB 自由（可多副本）的原因。V

4. LP 建模：最小化组内最大负载

对每个 8 卡组、每层独立解一个小 LP。决策变量：每条冗余边两端的承担比例 $o_{k,d}$（原件方留存）与 $r_{k,d}$（副本方接收）：

\[ \min\ t \qquad \text{s.t.}\quad b_g + \sum_d w_{g,d}\, o_{g,d} + \sum_{(k,d):\, \mathrm{r2o}[k,d]=g} w_{k,d}\, r_{k,d} \le t \ \ \forall g, \qquad o_{k,d} + r_{k,d} = 1, \quad o, r \in [0,1] \]

其中 $b_g$ 是 rank $g$ 的固定负载（未被复制专家的 token），$w_{k,d}$ 是第 $(k,d)$ 条边（被复制专家）本 batch 的 token 数——即 README 说的「边容量 = 该冗余专家当前 batch 的 token 数」。变量布局（minilp.cu 的 kernel_build 逐行核对）：V

变量段数量含义
$o[g,d]$$GD$ = 16边 $(g,d)$ 的负载留存在原件方的比例
$r[g,d]$$GD$ = 16流向副本方（$\mathrm{r2o}[g][d]$ 那张卡）的比例
$s[g]$$G$ = 8负载行松弛（$\mathrm{load}_g \le t$ 化为等式）
$t$1组内最大负载（目标函数唯一系数 1）
Big-M 列1人工列（目标系数 1000），让 $\mathbf{1}$ 向量初始可行

约束 $NC = G + GD = 24$ 行：8 条负载行（$b_g$ 为右端）+ 16 条比例行（$o + r = 1$）。理论下界：任何分流比都有 $\max_g \mathrm{load}_g \ge \max(\text{组均值},\ \max_g b_g)$——固定负载是搬不走的，LP 的全部本事就是把「可流动的部分」抹平到这条线。R

图 2 · LP 模型结构（左）与 README 示例 r2o 的 16 条冗余边（右）。绿实边 = 第 0 列（两个四元环），红虚边 = 第 1 列（对角）。drawio 源文件：assets/lplb-deep-reading.drawio（LP 模型与 CUBE 拓扑 sheet）。

5. 求解器：单 SM 上的 5 次迭代内点法

为什么不用现成求解器：这个 LP 每个 micro-batch、每层、每个 8 卡组都要解一次，延迟预算是微秒级；CPU 上的 SciPy/HiGHS 来回搬运就要数百 µs 起，GPU 通用路径则 launch 开销都盖过求解本身。DeepSeek 的答案：把整个 LP 装进一个线程块（单 SM），矩阵小（$24 \times 36$）到共享内存里放得下。V

算法是原始仿射尺度内点法（Dikin，与 EPLB 的两步贪心形成有趣对照——同一个问题的两种「预算化求解」）。固定 5 次迭代，每次：V

工程细节：cuBLASDx 做块内矩阵乘、cusolverdx 做块高斯消元（CUDA ≥ 12.6.3 + MathDx 组件）；跨节点组走 NVSHMEM（IBRC putmem_signal 做 allgather 求和 + 节点内 combine），延迟比节点内长。V

6. 端到端流程：内环逐 batch，外环换布局

图 1 · LPLB 端到端：内环（每 batch 每层）计数 → LP → 加权分流；外环（低频）用 EPLB 无冗余版打底 + 按 r2o 加冗余边。drawio 源文件：assets/lplb-deep-reading.drawio（LPLB 端到端流程 sheet）。

6.1 外环：update_redundancy_mapping

三步，全部在 planner.py 核对：V

  1. 调 EPLB 的 rebalance_experts（仓内 vendored 副本 lplb/eplb.py）但不带冗余（nored：物理数=逻辑数）——只做静态均衡重排；
  2. 每个 rank 把本地专家按历史负载降序排序，取 top（combined_redundant × D）个标记为待复制；
  3. 按 r2o 拓扑把这些专家复制到邻居的冗余槽 → 输出三件套 phy2log / log2phy / logcnt（max=2）。

即「EPLB 管静态放置，LPLB 在其上叠一层拓扑化的冗余边」——两个项目的关系是复用而非替代。

6.2 内环：run(idx, avail_counter, n_sms)

  1. 计数：kernel_count_idx 多 SM atomicAdd 统计本 batch 每个逻辑专家的 token 数（附带每 SM 前缀和，供加权映射用）；
  2. 求解：view 成 [组, 8, 本地专家数]，跨卡 all_reduce（或走 DeepEP buffer 通信子），每组建 LP 解出 o_weight；
  3. 映射：kernel_map_idx 把每个 token 的逻辑专家号翻译成物理槽位——对被复制专家，用确定性伪随机数 $(\text{count} \times 499 + 41) \bmod \text{total}$ 对照期望配额 $\mathrm{o\_weight} \times \text{total}$ 决定发原件还是副本，实现按比例分流且负载在 SM 间均匀。

输出 redirected_indices 直接喂给 DeepEP dispatch。整个过程 GPU 上完成、不搬任何权重。V

两种场景下 5 次迭代都把 8 个 rank 拉到几乎同一负载线，距下界 $\max(\text{组均值}, \max b_g)$ 不到千分之四——DeepSeek 的 5 次迭代预算在中小规模实例上就是实质最优。反例也有教育意义：若某个 rank 的固定负载远超组均值（LP 搬不动它），最优解就是撞在下界上一动不动——这种情况该找外环（EPLB 换放置）而不是内环硬解。

10. 局限与开放问题

  • token-only 目标：不建模 grouped GEMM 的非线性耗时（冷热专家同 token 数不同时延），官方自认可能次优；V
  • 求解频率即开销：每层每 batch 一次 ~100 µs，小 batch 下占比不可忽略；跨节点组（NVSHMEM 同步）更贵；V
  • 极端不均退化：每专家 ≤ 1 副本（max_logcnt=2），全局严重倾斜时可调自由度不如 EPLB 的多副本——README 直言「极端全局不平衡时可能比 EPLB 更差」；V
  • early research stage：单 commit、性能仍在评估、无论文背书，生产采用需自担验证。

11. 快问快答

Q1：LPLB 和 EPLB 是竞争关系吗？

不是，是叠层：外环直接 import EPLB 算法做无冗余静态放置，再叠 r2o 冗余边；内环 LP 只管逐 batch 分流。EPLB 管分钟级静态，LPLB 管 batch 级动态。V

Q2：为什么限制每条边只连 2 个 rank？

把 LP 压到 24×36 的规模才能单 SM 微秒级求解；多副本会同时放大变量数和约束（且 README 说明 LPLB 有意不让同一专家多副本，留自由度给放置层）。代价见 Q4。R

Q3：为什么选内点法而不是单纯形？

单纯形迭代次数不确定、分支多，不适合固定预算的 GPU kernel；仿射尺度内点法迭代次数固定、每轮同一组矩阵运算（matmul + GE），正好映射到 cuBLASDx/cusolverdx 两个块级原语。5 次迭代在实测规模下已到下界（§8）。R

Q4：LP 解不可行时会怎样？

kernel 做三重检查（d_max、人工列、残差），不可行则该组回退 0.5/0.5 均分并把 avail_counter 减一——均衡降级但不阻塞训练。V

Q5：分流比怎么落到每个 token？

kernel_map_idx 用确定性伪随机序列 $(c \times 499 + 41) \bmod \text{total}$ 把 token 按期望配额分到原件/副本两端——比例精确、分布打散、可复现。V

Q6：推理能用吗？

机制上不排斥（SGLang 已把 lplb_solver 接为可选 dispatch 算法），但设计动机是训练期的 batch 涨落；推理侧的同类需求更多由 METRO（激活专家）等服务期方案承接。R
