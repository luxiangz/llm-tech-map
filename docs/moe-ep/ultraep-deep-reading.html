1. 问题：大规模 EP 的负载失衡

1.1 失衡的因果链

专家并行（EP）把 $N$ 个专家分散到 $G$ 个 rank 上，token 经门控后通过 all-to-all 通信发往各专家。路由是动态的，因此每个 rank 实际接收的 token 数 $L_r$ 天然不等。大规模 EP 下，这个不等被放大为三类系统瓶颈V（论文摘要 + 博客）：

瓶颈机理
计算滞后（straggler）MoE 前向是同步集合通信，每层都要等最慢的 rank；热点 rank 拖慢全局
token all-to-all 通信瓶颈失衡使部分链路 token 交换量激增，偏斜（skew）造成热点拥塞
激活显存峰值热点专家所在 rank 激活堆积，逼近 OOM

失衡的度量（博客原话口径为「rank 间负载不均衡（最大值 : 平均值）」V）：

$$ \mathcal{I} \;=\; \frac{\max_r L_r}{\bar{L}}, \qquad \bar{L} = \frac{1}{G}\sum_{r=1}^{G} L_r $$

由于每层步时 $\propto \max_r L_r$、理想计算量 $\propto \bar{L}$，吞吐损失 $\approx 1 - 1/\mathcal{I}$：$\mathcal{I}=1.3$ 即丢 23%，$\mathcal{I}=4$ 即丢 75%（MoE 段内）。UltraEP 论文与博客报告的实测原始 $\mathcal{I}$ 在 1.30–4.01，理想与现实训推吞吐的端到端偏差最多可达 2 倍V。

1.2 为什么既有方案失效

  • EPLB（DeepSeek, 2025）：按前一时间窗口的路由统计周期性重排专家放置，隐含假设「历史负载可预测未来负载」。但细粒度 MoE（数百个小专家）的专家热度在 microbatch / 层 / 数据域间剧烈漂移，预测失准后重排甚至负优化V（博客动机节）。
  • LPLB（DeepSeek, 2025）：在 EPLB 放置之上用线性规划在线调整 token 重路由，但被「可解性约束 + EPLB 放置偏差」削弱V（博客 §3.1）。
  • 算法侧均衡（auxiliary loss / routing bias）只保证统计意义上的均衡，管不到单个 microbatch 的偏斜V。博客的分工表述：算法侧负责训练稳定性与专家特化，系统侧负责把每个 microbatch 已经发生的偏斜重新摊平，二者自然叠加。

UltraEP 的回应：门控一结束就拿到精确负载（exact post-gating load），在每个 microbatch 的每层实时重均衡——复制热专家到冗余槽位、按配额把 token 重路由到副本（§5–§8）。代价是均衡操作暴露在关键路径上、以 microbatch 为最小粒度高频执行，因此必须把决策与通信都压到百微秒级——这是全部设计的出发点。

2. 硬件前提：RSN 与 NVLink 域

机架级节点（Rack-Scale Node, RSN）把整个机架当作一台计算机：机架内数十个 GPU 用 scale-up 网络（NVLink/NVSwitch、UALink、灵衢总线等）紧耦合为全对等高速域；机架之间走 scale-out（以太网 / InfiniBand）。当前参考值：NVIDIA NVL72 提供 260 TB/s 级 GPU 间带宽、72 GPU 为主流机架规模；华为 CloudMatrix 384 把 scale-up 域扩到 384 NPUV（详见问答 Q1–Q5）。

UltraEP 的硬边界（README 原文V）：专家复制被限制在 scale-up（NVLink）域内；当 NVL 域小于 EP 组时，可达均衡下限略高于 1.0。代码落点：

  • csrc/utils/nvshmem.cuh:36：nvshmem_ptr() 对 NVL 域外的 PE 直接返回 nullptr——副本通信半径被通信层硬性截断在域内V；
  • csrc/kernels/config.cuh 与规划 kernel 的维度常量 MAX_GPUS_PER_NVL / kMaxNvlDomainSizeV；
  • ultra_ep/manager.py:114–122：NVL 域 ≤ 8 时强制 weight_sync 退化为 direct 模式（关闭中继：机内 8 卡直发已无扇出压力）并打印提示V。

推论：EP64 在 NVL72 级 RSN 上可整组进 scale-up 域，理想均衡可达；在传统 8 卡服务器上副本只能在本机摆放，均衡下限被抬高——仓库的 8×Hopper demo（§10）是缩小版验证，论文的生产叙事依赖 RSNR。扩大 NVL 域（如 CloudMatrix 384）降低的是均衡下限，机制本身不变R。

4. 初始化与状态布局（manager.py）

4.1 固有专家与冗余槽位

每个 EP rank 持有 $m$ 个固有专家（master，参数与优化器状态的属主）+ $R$ 个冗余槽位（replica，只存权重/梯度 buffer）。构造 Manager 时声明两者数目与专家尺寸（expert_fc1_numel = 2·hidden·ffn、expert_fc2_numel = hidden·ffn，支持 FP8 的 scale buffer）V。框架随后用 construct_local_master_ptr_pool(layer_id, ...) 把每层固有专家的权重/梯度指针注册进来（manager.py:359）——UltraEP 不搬运优化器状态，冗余专家的梯度在反传中实时归约回 master（§9），优化器只更新 masterV。

4.2 虚拟层号：PP/VPP 下的多 microbatch 并存

流水线（PP/VPP）会让同一层有多个 microbatch 同时在飞。UltraEP 用虚拟层号隔离它们（manager.py:309–330V）：

$$ \text{vid} \;=\; \text{real\_layer} \times \text{max\_microbatches} \;+\; \big(\text{counter} \bmod \text{max\_microbatches}\big) $$

放置表、配额表、reroute buffer 都按 vid 索引，slot 用完即循环复用；纯 DDP（max_microbatches=1）时 vid 退化为真实层号。master 指针池按真实层号索引，C++ 侧由 vid 反解V。

4.3 设备驻留的放置与配额张量

规划的全部输入输出都是 CUDA int32 张量（manager.py:162–179V）：physical_to_logical_map、logical_to_physical_map [L, N, G]、logical_replica_counts [L, N]、logical_instance_quota [L, N, G]（即 $q_{r,e,t}$ 表）、logical_instance_quota_prefix、rank_quota_prefix（reroute 分流用，§8）。规划结果各 rank 确定性一致，无需广播V（update_placement 文档串）。

4.4 显存账：跨层复用

冗余槽位的权重/梯度 buffer 全部层共享一套（每 rank $R$ 份），运行时零动态分配V。博客口径：Qwen3-235B 上单个冗余槽位的额外显存从 9.9 GB（不复用）降到 108 MBV。算术复核R：Qwen3-235B 隐藏 4096、专家中间维 1536，单专家 $3\times4096\times1536 \approx 18.9\text{M}$ 参数；bf16 权重 37.7 MB + fp32 梯度 75.5 MB ≈ 113 MB/槽；94 层各留一份 ≈ 10.6 GB、复用一份 ≈ 113 MB——与官方数字差 <8%，量级吻合。

5. 控制面第 1 步：精确负载采集（load_compute.cu）

规划器的输入是门控后的精确负载 $L_e$。三个 kernel 完成采集（load_compute.cuV）：

  1. 本地直方图：稠密路径 rmap_local_sum_kernel 把 $[T, N]$ 布尔路由图按列求和（warp 合并读 + 共享内存块内归约 + 全局 atomicAdd）；稀疏路径 sparse_topk_histogram_kernel 直接对 topk_ids [T,k] 做共享内存直方图——框架可走 update_placement_sparse 避免物化稠密路由图。
  2. 跨 rank 可见性：每 rank 的直方图写入 NVSHMEM 对称堆（代码注释「alloc by nvshmem」），域内各 rank 直接可读，无需集合通信搬运V。
  3. 全局归约：reduce_per_rank_loads_kernel 把 $G$ 份每 rank 负载合成全局 $L_e$。随后 profiler 的 stage_pre 钩子把「均衡前」负转载走（manager.py:547）。

6. 控制面第 2 步：quota 规划器（placement.cu）

6.1 问题形式化

给定精确负载，求副本放置（每个冗余槽放哪个专家的副本）与配额 $q_{r,e,t}$，使重路由后的 $\mathcal{I}$ 最小。约束：每 rank 冗余实例数 $\le R$、副本与 master 同 NVL 域、master 位置固定（update_placement 文档串描述 legacy 路径：masters 固定、按 NVL 域贪心复制最热专家、LPT 装箱且副本不与 master 同卡；quota 路径把放置与配额耦合求解，语义等价）V。

6.2 算法：阈值二分 + 耦合求解

博客 §3.1 的定义V：quota 是每个专家实例在重路由后会接收的负载——直接解 quota，使「实例化新副本」与「更新负载分布」发生在同一探索步骤（这正是对 EPLB「先放置」/ LPLB「再路由」两阶段割裂的回应）；整体框架对最优全局均衡阈值 $\tau$ 做二分搜索。

代码级证据（placement.cuV）：

  • 可行性谓词 warp_capacity_feasible()（placement.cu:76）：给定 $\tau$，每 rank 算 $\text{excess}_r = (L_r - \tau)^+$（超载量）、$\text{slack}_r = (\tau - L_r)^+$（可吸收量），warp 归约判定 $\sum_r \text{excess}_r \le \sum_r \text{slack}_r$ 且逐源可安置。该谓词对 $\tau$ 单调，二分成立R。
  • 导出循环（placement.cu:340–478）：超载 rank 遍历本 rank 专家（按负载降序的 sorted_experts），把过剩负载逐专家导出到有 slack 的 rank；共享内存数组 smem_warp_slots_used[QUOTA_SOLVER_WARPS][MAX_GPUS_PER_NVL] 实时记账目标 rank 的槽位占用——放置与配额在同一个循环里同时确定。
  • quota oracle：QUOTA_ORACLE_MAX_BATCH_K 与 sel_quota[]（placement.cu:250–332）处理 top-k 整数量化——配额必须能被真实 token 路由凑出来，不是任意实数R；精度由 ULTRA_EP_QUOTA_ORACLE_EPS（默认 0.01）控制V。
  • 寄存器化：use_register_state = (G ≤ 64)——EP64 以内每个 lane 用 2 个寄存器跟踪 2 个 rank 的状态，配 warp shuffle 归约；规划在 EP64 下 <100 µsV（<100 µs 来自博客，寄存器化来自代码）。

7. 数据面前向：weight_sync（weight_sync.cu）

7.1 任务模型与 tile 流水线

规划输出转化为「单源多目的」的传输任务：一个 task = 把某专家的一份权重分片（fc1 或 fc2）从 master rank 发到它的若干副本 rank。设计注释（weight_sync.cu:577–598V）：

每 tile：TMA Load tile → SMEM（仅一次）→ 向 N 个副本地址发 N 路 TMA Store；双缓冲使 Load[i+1] 与 Store[i] 重叠。

持久化 kernel：CTA 通过 stage1/2_global_tile_counter 原子抢 tile，多 CTA 并行处理同一 task 的不同 tile，over-launch 由持久 kernel 自消化。通信走 NVSHMEM 对称堆（内存语义 put），权重或梯度切 tile、共享内存 double-buffering、TMA 异步搬运V（博客 §3.2）。

7.2 三档分发计划与中继决策

weight_sync 有三档计划（manager.py:506V）：direct（源直发所有副本）、adaptive（默认，按扇出收益自动选择中继）、force_relay（强制中继）；NVL 域 ≤ 8 强制 direct（§2）。中继决策的精确启发式（weight_sync.cu:129–190V）：

  • 中继数 relay_count = ⌊√num_replicas⌋，受 MAX_RELAYS=8 封顶，且 ≤ 副本数 − 1；
  • 启用条件（扇出收益判定）：副本数 − max(直发扇出, 子节点扇出) ≥ 2，其中子节点扇出 = ⌈(副本数 − 中继数) / 中继数⌉；副本数 < 4 不开中继；
  • 中继树每次 weight_sync 按当前流量重建，由低流量 rank（恰好是没被选作副本的）分摊中转V（博客）。

8. reroute：逻辑路由 → 物理路由（reroute.cu）

规划改变了「哪个专家在哪些 rank 有实例」，token 的路由表必须相应展开。reroute 有两套输入形态V：

  • 稠密（reroute(vid, probs, routing_map)）：两遍 kernel——先 reroute_forward_count_kernel 按 (expert, tile) 用 __ballot_sync + __popc 数活跃 token，再 dense_{rr,quota}_reroute_scatter_kernel 做 tile 计数前缀和 + 散射，输出物理版的 probs 与 routing_map；反向由 reroute_backward_gather_kernel 按展开表把梯度聚合回逻辑空间。
  • 稀疏（reroute_sparse(vid, topk_ids)，就地改写）：每个 topk 条目经每专家原子计数器拿到本 rank 内序号 local_ordinal，然后选副本——
    • round-robin 模式：副本序号 = ordinal mod C（C 为该专家副本数）；
    • quota 模式（默认）：sparse_quota_replica_index（reroute.cu:441）用 rank_quota_prefix 前缀数组线性扫描——序号落在第 $j$ 个前缀区间就发第 $j$ 个副本。这逐 token 实现了规划器的配额切分：前 $q_{r,e,t_1}$ 个 token 发副本 1，其后 $q_{r,e,t_2}-q_{r,e,t_1}$ 个发副本 2……V

时序上 reroute 与 weight_sync 并发（QUOTA_REROUTE_INTERLEAVE=true），基本被权重传输掩盖V。profiler 的 record_post 钩子随后用 Triton kernel 从配额表重建「均衡后」物理负载，供前后对比（manager.py:332–357）。

9. 反向与确定性梯度归约（grad_reduce.cu）

副本的 Wgrad 必须归约回 master 的 fp32 梯度 buffer（grad_dtype 仅支持 fp32，manager.py:66V）。两条路径（grad_reduce.cuV）：

  • 快速路径：grad_reduce_kernel 直接对 master 梯度做 atomicAdd——无序浮点累加，快但每次运行的求和顺序不同、结果可能有浮点差异；
  • 确定性路径（默认开启，ULTRA_EP_GRAD_REDUCE_DETERMINISTIC=1）：grad_reduce_deterministic_kernel 把 tile 再切半为 subtile，在共享内存中按固定顺序累加后写回，保证浮点确定性——生产训练可复现性的硬要求；代价由精细的 SM 占用与共享内存 footprint 控制（必须偶数个驻留 SM，默认 42）V。

归约与 router/attention 反向重叠（§3.3）；注意开源 Megatron patch 中，控制权重分发与 Wgrad 计算重叠需要侵入 grouped GEMM 引入同步，因此被放在 Wgrad 之前满 SM 执行（博客脚注 1V）。

概念组：RSN 与超节点

Q1 机架级节点（rack-scale nodes）是什么？

一种架构理念：把整个机架当作一台计算机，而不是一群独立服务器的集合。传统数据中心以单台服务器（如 8 卡 GPU 机）为扩容单元，RSN 以整个机架为单元。关键在机架内部的 scale-up 互联：数十个 GPU 通过 NVLink/NVSwitch（NVIDIA）、UALink（AMD）、灵衢总线（华为）等技术组成全对等的高速域，带宽比机架间的 scale-out 网络（以太网/InfiniBand）高 1–2 个数量级——例如 NVL72 机架提供 260 TB/s 级 GPU 间带宽，而跨机链路通常为数百 GB/s 级V。对 MoE 的意义：专家并行的 token all-to-all 与 UltraEP 的专家复制通信都发生在机架内部的高速域里，通信瓶颈大幅降低。

Q3 华为的 384 节点是啥？

指 CloudMatrix 384 超节点（硬件产品名 Atlas 900 A3 SuperPoD）V：由 12 个计算柜 + 4 个总线设备柜共 16 个机柜组成，用自研灵衢（UnifiedBus）总线把 384 颗昇腾 NPU（配 192 颗鲲鹏 920 CPU）连成全对等域——统一编址内存 48 TB、BF16 算力约 300 PFLOPS、NPU 间 D2D 带宽双向 784 GB/s、总线单跳时延约 200 ns。对标 NVL72：算力约为其 1.7 倍，功耗约 559 kW（NVL72 约 120 kW 的 4 倍多）——「用规模换性能」路线。

Q4 384 不是 scale-up + scale-out 吗？

CloudMatrix 384 本身是两层架构系统，但两层分界不在「384 内部」V：

  • 超节点内（384 卡）= scale-up：灵衢/UB 总线、全对等、统一编址、内存语义，带宽比传统以太网高 15 倍、时延低 10 倍；
  • 超节点之间 = scale-out：参数面 RDMA 交换机互联，最大可扩展到 16 万卡集群。

设计逻辑：scale-up 域扛「快」（通信密集、延迟敏感的 MoE EP、token all-to-all），scale-out 域管「大」（数据并行、流水线并行等）。

Q5 超节点内相当于 scale-up 吗？

相当于，但更准确的说法是「scale-up 域的跨机柜扩展」。超节点内互联具备 scale-up 的全部特征：极高带宽、微秒级以下时延、全对等拓扑、统一编址/内存直接访问、逻辑上像一台计算机、不经传统网络V。区别仅在物理形态：传统 scale-up 指单机箱内（8 卡服务器 NVLink）或单机架内（NVL72 NVSwitch 域），华为把它推到了跨 12+4 机柜。对 UltraEP 的意义：更大的 NVL 域 = 更低的均衡下限（见 Q15 的第三环）。

论文语句组

Q6 「UltraEP 通过高效的配额驱动规划器主动响应门控后的负载，并利用 RSN 原生的持久化 Tile 流传输和基于中继的扇出缓解技术，来执行由此产生的不规则专家状态迁移」——这句话怎么理解？

逐词拆解（机制详见正文 §5–§7）：

  • 主动响应门控后的负载：门控（gating/router）完成后，每个 token 选了哪些专家已确定，系统立刻统计出精确负载 $L_e$（$e$ 遍历所有专家）——不等历史统计、不靠预测。「主动（eagerly）」强调这在关键路径上即时发生。
  • 配额驱动规划器（quota-driven planner）：直接求解「每个专家实例将接收多少 token」（配额 $q_{r,e,t}$），把「在哪放副本」与「token 怎么分流」耦合进同一次阈值二分求解（§6）。注意两个常见误读：quota 不是「给 rank 设处理上限」，而是实例级的接收量；规划输出的是复制方案而非迁移方案。
  • 不规则专家状态迁移：「不规则」指传输模式每层每 microbatch 都变（哪些专家要复制、复制几份、发往哪些 rank 都不同），无法用规则的集合通信表达。「迁移」实为复制物化——把 master 权重分发到各 rank 预留的冗余槽位（跨层复用的 buffer），反向再恢复与归约（§4、§9）。
  • RSN 原生持久化 Tile 流传输：把权重切成 tile，用持久化 kernel + TMA + 共享内存双缓冲 + NVSHMEM 内存语义流式搬运，吃满 scale-up 域带宽（§7.1）。
  • 基于中继的扇出缓解：热专家副本很多时，源 rank 直发会成为出口瓶颈；用按流量实时构建的两阶段中继树分摊（§7.2）。

Q7 「跨秩（inter-rank）不均衡度」是什么意思？

「秩」即 rank——分布式框架里每个参与计算进程的编号（0, 1, 2, …，通常一卡一进程），与数学里的矩阵秩无关。跨秩不均衡度衡量不同 rank 之间负载差异：

$$ \mathcal{I} = \frac{\max_r L_r}{\bar{L}}, \qquad \bar{L} = \frac{1}{G}\sum_r L_r $$

其中 $r$ 遍历 EP 组内所有 rank，$L_r$ 是 rank $r$ 实际接收的 token 数，$G$ 是 rank 总数，$\bar{L}$ 是均值。$\mathcal{I}=1$ 为完美均衡，越大越失衡。UltraEP 把它从 1.30–4.01（最忙 rank 最多扛 4 倍于平均的负载）压到 1.01–1.04（只多 1–4%）。它重要是因为同步语义：每层要等所有 rank 算完，$\mathcal{I}$ 直接决定吞吐损失 $\approx 1 - 1/\mathcal{I}$（Q11 详解）。

通信组：all-to-all、dispatch/combine 与元数据

Q8 论文里的 all-to-all 实际上是不是 dispatch + combine？

是（在 MoE EP 语境下）。Token all-to-all 由一对方向相反的通信组成：

  • Dispatch：门控后，每个 rank 把 token 按 routing map 发往目标专家所在的 rank——每个 rank 都可能向任意其他 rank 发送，构成 all-to-all；
  • Combine：专家算完后，把输出送回 token 原始所在的 rank——同样构成 all-to-all。

两点补充：① 失衡会让 dispatch 的「接收热点」和 combine 的「发送热点」落在同一批 rank 上，这就是均衡与通信瓶颈的耦合（§1.1）；② UltraEP 不实现这对通信——它与 token 通信库解耦，集成中用 DeepEP/HybridEP（§10.1），均衡的作用是间接的：token 分布摊平后 all-to-all 的偏斜自然下降。

Q9 dispatch/combine 是同步通信吗？直接用 alltoallv 不行吗？

是同步集合通信：每个 rank 必须等所有 rank 的收发都完成才能进入专家计算（dispatch 后）或下一层（combine 后）——正因为如此，任何一个慢 rank 都会让全体空等，这是 straggler 问题的通信侧根源。

alltoallv 理论上可行，朴素用法不行，病灶有四R（口径综合自 DeepEP 仓库与昇腾社区文章）：

  1. 元数据 host 往返：alltoallv 需要先知道每对 (源, 目标) 的收发量；朴素实现把计数搬到 CPU（allgather → host 算偏移 → 分配接收缓冲），引入设备↔主机内存往返与流同步；
  2. 动态形状破坏 CUDA graph：接收张量按实际计数分配，形状每步都变，无法捕获；
  3. 不感知非对称域：通用集合通信库不理解「NVLink 域内 + RDMA 域间」的带宽差异，不能做域间转发；
  4. 偏斜拥塞：失衡流量让热点链路饱和，其他链路空闲（生产中 all-to-all 可占步时 20–60%R）。

注意分工：这些是 token 线的问题，由 DeepEP 一类通信库解决；UltraEP 的数据面在权重/梯度线（§7、§9），但用了同族技术（设备驻留、单侧通信、无 host 同步）。

Q10 dispatch/combine 具体怎么做，才能避免 alltoallv 那样提前 allgather 全量的元数据？

先厘清一个前提：变长 all-to-all 逻辑上只需要每对（源，目标）的计数（$G\times G$ 个整数，$G$ 为 rank 数），不需要全量路由表（规模正比于 token 数 × top-k）。「allgather 全量元数据」是朴素实现把充分统计量做坏了。先看两者差多少——以 DeepEP README 的 DeepSeek-V3 预训练口径为参数V（每 rank 每 microbatch $T_{\text{loc}}$=4096 个 token、top-$k$=8、$N$=256 个 routed experts，设 $G$=64），下表数字为算术演示R：

交换内容单份大小全网交换量（allgather，$G$=64）
稠密路由表 $[T_{\text{loc}}, N]$ 布尔（朴素「全量元数据」）4096 × 256 B = 1 MB64 MB
稀疏 topk_ids $[T_{\text{loc}}, k]$ int644096 × 8 × 8 B = 256 KB16 MB
计数向量（充分统计量） int32 × $G$64 × 4 B = 256 B16 KB

表：元数据的三种形态，充分统计量比全量路由表小 4 个数量级。对照 token 本体（$T_{\text{loc}} \times k \approx 3.3\times10^4$ 个 token 副本 × 7168 维 ≈ 百 MB 级），16 KB 的计数才配称「零头」。

关键认识：接收端要开工，只需要知道「每个源 rank 给我发多少」，不需要知道「哪个 token 去哪个专家」——后者在发送端本地就已经确定，专家分段可以在数据到位后按到达顺序在设备上现算。把这个认识落成协议，就是 DeepEP 的两条路径（API 事实一手核对V；逐步语义为合理推断R）：

normal 模式（训练 / prefill）的五步协议：

  1. 门控不出卡：router 在本 rank GPU 上完成，得到 topk_ids [T_loc, k]——它从此不再跨 rank 移动；
  2. 设备侧计数交换：get_dispatch_layout(topk_idx) 在设备上把 topk_ids 归约成「发给每个目标 rank 多少 token」的计数向量（一个 $G$ 维直方图），并把计数直接写到各对端（NVLink 域内 put / RDMA 域间写），全程无 CPU 参与；
  3. 设备上算接收布局：每个 rank 用收到的计数（谁给我发多少）做前缀和，得到接收缓冲里按源 rank 排列的分段偏移——num_tokens_per_rank / num_tokens_per_rdma_rank / num_tokens_per_expert 全是设备张量；
  4. 数据搬运：dispatch() 按布局搬 token 本体：机内走 NVLink，跨机走 RDMA，并支持从 NVLink 域向 RDMA 域转发（非对称域带宽转发），SM 数量可配；
  5. 唯一一次 host 交互：normal 模式的输出张量按实际接收数分配，CPU 要等一次 GPU 信号才知道尺寸（README 原话 "the CPU will wait for GPU's signal to arrive"）。训练不用 CUDA graph，这次等待无妨；机内场景传 num_worst_tokens 改最坏尺寸分配即可消掉它。

low-latency 模式（decode）的槽位协议——干脆没有独立的元数据阶段：

  1. 初始化即固定：每对（源，目标）预注册固定容量缓冲（容量 = num_max_dispatch_tokens_per_rank），且每专家一对 QP（num_qps_per_rank = num_experts // group.size()）；
  2. 数据即元数据：dispatch 时发送端把 token（FP8 + scale）直接写进对端对应槽位；recv_expert_count 是数据落位后自然更新的设备张量——计数是传输的副产物，不是前置条件；
  3. 零同步：没有计数交换、没有 barrier、没有 CPU 参与；缓冲形状恒定，CUDA graph 捕获后 replay 只需恢复 buffer 状态（README："compatible with CUDA graph (but you may restore some buffer status once you replay)"）；
  4. 零 SM 重叠：return_recv_hook=True 时实际接收推迟到 hook() 调用那一刻，通信在 RDMA 引擎后台推进——供双批重叠（TBO）使用。

均衡与部署组：量化、激活与 EP 度

Q11 负载均衡程度如何评估？

分两级（正文 §1.1、§10）：

① 指标级——跨 rank 不均衡度：

$$ \mathcal{I} = \frac{\max_r L_r}{\bar{L}}, \qquad \bar{L} = \frac{1}{G}\sum_{r=1}^{G} L_r $$

$r$ 遍历 EP 组内 rank；$L_r$ 是 rank $r$ 按当前放置实际接收的 token 数；$G$ 是 rank 数；$\bar{L}$ 是平均负载；$\max_r$ 取最忙者。UltraEP 在每层每 microbatch 粒度、用门控后的精确 token 数统计，均衡前（post-gating）与均衡后（post-reroute）各测一次，内置 profiler 采集并可视化。选 max:mean 而非 max:min 的原因：同步语义下步时由 $\max_r L_r$ 决定、理想计算量是 $\bar{L}$，因此有效利用率 ≈ 1/𝓘，吞吐损失 ≈ 1 − 1/𝓘（𝓘=1.3 丢 23%；𝓘=4 丢 75%），指标可直接换算成吞吐。

② 端到端级——吞吐对 force-balanced 理想上界归一化（94.3% 类数字）。指标边界：𝓘 是 rank 级均衡；rank 摊平后与理想上界的残差来自专家级非一致性（§10.2 末行），不能混为一谈。

Q12 prefill 阶段序列越长、token 很多，大部分专家是不是都会被激活？

是，且可以定量。设 $N$ 为专家总数、$k$ 为 top-k、$T$ 为每步 token 总数（整个 EP 组）。均匀路由假设下，一个专家被至少一个 token 选中的概率与每专家平均 token 数为：

$$ P_{\text{act}} = 1-\Big(1-\frac{k}{N}\Big)^{T}, \qquad \lambda = \frac{T\,k}{N} $$

但激活全覆盖 ≠ 均衡：随机涨落随 $T$ 增大被摊薄（相对幅度 $\propto 1/\sqrt{T}$，即与 $\sqrt{T}$ 成反比），而专家热度的系统性偏斜不随 $T$ 消失，且同一序列内路由同域相关（同话题 → 同批专家热）R。证据：$G$=64、$T$=4096 时纯涨落只能解释 𝓘≈1.13（Q15 公式），实测原始 1.30–4.01——大头是系统偏斜，这正是「精确负载」路线的立论点。

Q13 decode 阶段是不是也存在「专家都被激活」？

大批量 decode 会，但「激活」的含金量完全不同。decode 每步的 token 数等于批大小 $B$（每序列产 1 个 token）。代入 Q12 公式：$B$=128、$N$=256、$k$=8 时 $P_{\text{act}}$=98.3%——专家大多被点亮；但每专家平均只有 $\lambda = Bk/N = 4$ 个 token。此时 grouped GEMM 完全被权重读取主导（读一遍专家权重的时间与只有 1 个 token 时几乎相同），单步耗时 ≈ 本 rank 被点亮的专家数 × 权重读时间。所以 decode 的失衡本质变了：均衡对象从「token 数」漂移为「每 rank 激活专家数 / 权重读次数」R。MoonEP「每 rank 恒载 S×K」的构造性保证正是针对这一层（见本目录源码级对比分析）。

图 7：EP 度放大实际性能差距的逻辑链。

①自平均：rank 负载是它 $m = N/G$ 个专家负载之和，$m$ 越小，和的相对波动越大；②极值统计：每层末尾是同步集合通信，所以该层耗时等于 $G$ 个 rank 中最慢一个的耗时（取 max，不是平均）；而「从更多样本里取最大值」这个动作本身就使最大值更极端——即使每个 rank 自身的波动程度不变，对近似高斯的波动有 max ≈ mean + σ·√(2 ln G)（σ 为单 rank 负载的标准差），随 $G$ 单调增大；③粒度下限：均衡的最小动作是搬一个专家或改一路 token，占该 rank 负载的 $1/m$，$m$ 小则任何动作都是大跳变（NVL 域 < EP 组时下限进一步抬高，§2）；④⑤失衡在同步与通信上双重放大并随层数复合。

①②可以合成解析下限（均匀路由、纯随机涨落近似R）：

$$ \mathcal{I}_{\text{noise}} \approx 1 + \sqrt{2\ln G}\cdot\sqrt{\frac{G}{T\cdot k}} $$

其中 $G$ 是 EP rank 数，$T$ 是每步 token 总数，$k$ 是 top-k；$\sqrt{2\ln G}$（$\ln$ 为自然对数）来自「$G$ 个独立同分布高斯样本最大值的期望偏移」，$\sqrt{G/(Tk)}$ 是均匀路由下 rank 负载的相对标准差。该式同时编码了「token 越少越糟」（decode）与「EP 度越大越糟」两个方向，是 Q15 与 Q16 的统一答案。注意它只是下限：真实路由的系统性偏斜叠加其上（所以实测能到 4.0）。
