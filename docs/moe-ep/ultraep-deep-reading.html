0. 一页结论

  • UltraEP 是"精确负载 + 实时"的专家均衡运行时：门控一结束就拿到本 microbatch 的真实负载，在每层每 microbatch 的关键路径上求解复制方案、把热专家权重复制到各 rank 预留的冗余槽位、并把 token 按配额重路由到副本。V
  • 它改的不是 token 通信，而是专家状态布局：token 的 dispatch/combine 仍由 DeepEP 等原有路径执行，UltraEP 与之解耦；均衡让各 rank 接收 token 数摊平，间接消除 all-to-all 偏斜与 straggler。V
  • 两条设计支柱：控制面 quota 驱动规划器（对全局均衡阈值做二分搜索，把「放置」与「重路由」耦合求解，EP64 下 <100 µs）；数据面 NVSHMEM + TMA 持久化 tile 流传输 + 两阶段中继树（关键路径总暴露开销 <300 µs，占步时 1–2%）。V
  • 硬边界：专家复制被限制在 scale-up（NVLink）域内；NVL 域小于 EP 组时，可达均衡下限略高于 1.0——这是 RSN（机架级节点）成为论文标题的真正原因。V
  • 数字：训练 + 推理 prefill 平均达 force-balanced 理想吞吐 94.3%（训练 94.6% / prefill 90–97%），相对无均衡基线提升 1.49×；跨 rank 不均衡度（最大:平均）从 1.30–4.01 压到 1.01–1.04；最大 256 GPU、106B–671B 模型；已在 288B 生产预训练中长期部署（≥92% 理想性能）。V

1. 问题与动机

1.1 失衡的因果链

大规模 EP 下，设备级专家负载不均衡被放大为三类系统瓶颈V（论文摘要 + 博客）：

瓶颈机理
计算滞后（straggler）同步集合通信下，每层都要等最慢的 rank；热点 rank 拖慢全局
token all-to-all 通信瓶颈失衡使部分链路 token 交换量激增，偏斜（skew）造成拥塞
激活显存峰值热点专家所在 rank 激活堆积，逼近 OOM

不均衡度指标的定义（博客原话为「rank 间负载不均衡（最大值 : 平均值」）V：

$$ \mathcal{I} \;=\; \frac{\max_r L_r}{\frac{1}{G}\sum_{r=1}^{G} L_r}, \qquad \mathcal{I} = 1 \text{ 为完美均衡} $$

其中 $L_r$ 是 rank $r$ 门控后接收的 token 总数，$G$ 为 EP 组内的 rank 数。论文实测原始 $\mathcal{I}$ 在 1.30–4.01V——即最忙 rank 最高扛着 4 倍于平均的负载。

1.2 为什么「基于历史负载」的方案失效

EPLB（DeepSeek, 2025）按前一时间窗口的路由统计周期性重排专家放置，其隐含假设是历史负载可预测未来负载。博客对细粒度 MoE（数百个小专家）的实测观察是：专家热度在 microbatch / 层 / 数据域间剧烈漂移，预测失准后重排反而可能负优化V。后继的 LPLB（DeepSeek, 2025）针对 EPLB 放置与实时负载的偏差，用线性规划在线调整 token 重路由，但效果被「可解性约束 + EPLB 放置偏差」削弱V（博客 3.1 节原述）。UltraEP 的回应是把两个阶段耦合进同一次求解（见 §4）。

值得强调的分工（博客总结）V：算法侧均衡（auxiliary loss / routing bias）负责训练稳定性与专家特化，只在统计意义上起作用；系统侧均衡（UltraEP）负责把每个 microbatch 已经发生的负载偏斜重新摊平。二者目标不同、自然叠加。

2. 硬件前提：RSN、scale-up 域与 NVL 域约束

2.1 RSN 与两层网络

机架级节点（Rack-Scale Node）把整个机架当作一个计算机：机架内数十个 GPU 通过 scale-up 网络（NVLink/NVSwitch、UALink、灵衢总线等）紧耦合为全对等高速域；机架之间走 scale-out（以太网 / InfiniBand）。对话中核实过的硬件参考值V：NVIDIA NVL72 提供 260 TB/s 级 GPU 间带宽、72 GPU 为当前主流机架规模（AMD Helios 同为 72），Dell 高密度配置可达 144；华为 CloudMatrix 384（Atlas 900 A3 SuperPoD）以 16 机柜（12 计算 + 4 总线）、灵衢总线把 scale-up 域扩到 384 NPU（48 TB 统一编址内存、约 300 PFLOPS BF16、功耗约 559 kW vs NVL72 约 120 kW——「用规模换性能」的路线）。

2.2 关键约束：复制半径 = NVLink 域

README 原文V：

"Confining expert replication to the scale-up fabric, UltraEP adapts to available NVLink domain size automatically. When the NVLink domain is smaller than the EP group, the achievable imbalance floor sits slightly above the ideal 1.0."

这条约束在代码里是硬边界：NVSHMEM 工具层对域外 PE 的 nvshmem_ptr() 直接返回 nullptr（csrc/utils/nvshmem.cuh:36），规划与通信 kernel 的维度常量是 MAX_GPUS_PER_NVL / kMaxNvlDomainSizeV。因此：

  • EP64 在 NVL72 级 RSN 上可以整组进 scale-up 域 → 理想均衡可达；
  • EP64 在传统 8 卡服务器（NVL 域 = 8）上，副本只能在本机 8 卡内摆放 → 均衡下限 >1.0。仓库的 8×Hopper demo 是最小化可复现验证，论文的生产叙事依赖 RSNR。

这也给「CloudMatrix 384 之类的超节点对 UltraEP 意味着什么」一个精确回答：扩大 NVL 域降低的是均衡下限（floor），机制本身不变R。

3. 系统总览：一次前向 + 反向的完整生命周期

先修正一个常见误读（也是所对齐对话中的最大偏差）：UltraEP 做的不是「专家迁移」，而是「热专家复制到预留冗余槽位 + token 重路由到副本 + 反向时恢复与归约」。初始化时每个 EP rank 预留 $R$ 个冗余专家 slot（权重 / 梯度 buffer 跨层复用），每个 layer 把固有专家（master expert）的指针注册给 ManagerV。

几个使「每层每 microbatch 一次」变得便宜的工程事实V：

  • 显存跨层复用：冗余 slot 的权重/梯度 buffer 全部 layer 共享一套，Qwen3-235B 上单个冗余 slot 的额外显存从 9.9 GB 降到 108 MB；冗余专家不维护优化器状态（梯度实时归约回 master，优化器只更新 master）。运行时零动态显存分配。
  • 确定性梯度归约：副本→master 的 Wgrad 归约用保序累加替代 atomicAdd，保证浮点确定性（生产训练可复现性要求），并尽量压缩确定性实现的性能损失。
  • 通信 SM 可控：驻留 SM 数可用环境变量调节，保证反向的通信被计算完全掩盖且不拖慢计算。

4. 控制面：quota 驱动的均衡规划器

4.1 形式化

记专家 $e$ 的物理副本所在 rank 集合为 $\mathcal{H}(e)$（master + 冗余副本），源 rank $r$ 发往「专家 $e$ 在 rank $t$ 上的实例」的 token 数为配额 $q_{r,e,t}$，满足R（论文记号，ar5iv 数学片段核对过 $q_{r,e,t}$ 与 $\mathcal{H}(e)$V）：

$$ \sum_{t \in \mathcal{H}(e)} q_{r,e,t} = L_{r,e}, \qquad L_r = \sum_{e} L_{r,e}, \qquad \text{slot 约束：每 rank 冗余实例数} \le R $$

目标是最小化 $\mathcal{I} = \max_r L^{\text{reroute}}_r / \overline{L^{\text{reroute}}}$，其中 $L^{\text{reroute}}_r$ 是按 $q$ 重路由后各 rank 的实际接收负载。

4.2 算法：阈值二分 + 耦合的配额求解

博客 3.1 的准确定义V：quota 是「每个专家实例在重路由后会接收的负载」——不是对话里理解的「给 rank 设处理上限」。直接解 quota 把「放置新副本」与「更新负载分布」耦合进同一探索步骤，避免了 EPLB（先放）/ LPLB（再路由）的两阶段割裂。整体框架是对最优全局均衡阈值 $\tau$ 做高效二分搜索。

代码级证据（csrc/kernels/placement.cu，共 1665 行）V：

  • 可行性谓词 warp_capacity_feasible()（placement.cu:76）：给定阈值 threshold，每个 rank 计算 $\text{excess}_r = (L_r - \tau)^+$、$\text{slack}_r = (\tau - L_r)^+$，warp 归约后判定 $\sum \text{excess} \le \sum \text{slack}$ 且逐源可安置——这是标准的「水量可平」条件，对 $\tau$ 单调，故二分成立。
  • 导出循环（placement.cu:340–478）：超载 rank 遍历 sorted_experts（本 rank 专家按负载降序），把过剩负载逐专家导出到有 slack 的 rank，同时用共享内存数组 smem_warp_slots_used[QUOTA_SOLVER_WARPS][MAX_GPUS_PER_NVL] 记账目标 rank 的 slot 占用——放置与配额在同一个循环里同时确定，这就是「耦合」的落地。
  • quota oracle：QUOTA_ORACLE_MAX_BATCH_K 与 sel_quota[]（placement.cu:250–332）处理 top-k 路由下的整数量化——配额必须能被真实 token 路由凑出来，不是任意实数R（标识符与逻辑推断）。
  • 比例切分：build_rank_quota_prefix()（placement.cu:669）按各副本 quota 占比对源 rank 的 token 做带余数处理的成比例分配，生成 reroute 用的前缀索引。
  • 寄存器化：use_register_state = (G <= 64)——EP64 以内每个 lane 用 2 个寄存器跟踪 2 个 rank 的 slack/slot 状态，配合 warp shuffle 归约，求解在 EP64 时仍 <100 µsV（<100 µs 数字来自博客；寄存器化来自代码）。

5. 数据面：persistent tile streaming 与两阶段中继

5.1 任务模型与 tile 流水线

weight_sync.cu（1037 行）的设计注释V：一个 task = 单源多目的的一份权重分片（某专家 fc1/fc2）传输；源可以是本地 master（stage 1 直发）或本地中继缓冲（stage 2 转发）。每个 tile 的执行节拍：

TMA Load tile → SMEM（仅一次）→ 向 N 个副本地址发 N 路 TMA Store；双缓冲使 Load[i+1] 与 Store[i] 重叠。

持久化 kernel + 原子计数：CTA 通过 stage1/2_global_tile_counter 抢 tile，多个 CTA 并行处理同一 task 的不同 tile，over-launch 由持久化 kernel 自行消化V。通信建立在 NVSHMEM 对称堆上（内存语义 put；nvshmem_ptr 域外返回 nullptr，跨域另有 RDMA teamV）。

5.2 两阶段中继树：精确的启发式

少数热专家可能有众多副本，master rank 的出口多播流量会成为新瓶颈（负载极不均衡时甚至抵消均衡收益）V（博客 3.2）。代码里的具体决策规则（weight_sync.cu:129–190）V：

  • 中继数 relay_count = ⌊√num_replicas⌋，受 weight_sync_relay_max_relays 封顶，且 relay_count ≤ num_replicas − 1；
  • 启用条件是扇出收益判定：num_replicas − max(直发扇出, 子节点扇出) ≥ min_fanout_gain，其中子节点扇出 = ⌈(num_replicas − relay_count) / relay_count⌉；副本数低于 min_replicas 不值得开中继；
  • 中继树每次 weight_sync 按当前流量重建，由低流量 rank（恰好是没被选作副本的）分摊中转V（博客）。

5.3 就绪通知：epoch ready-flag

task 完成时向各目标 rank 的 ready-flag（带 epoch 计数）发信号（finalize_completed_weight_sync_task，weight_sync.cu:644 起）V，接收端按专家粒度放行后续 token dispatch，不必等全部权重到位——没有全局 barrier。这与 §6 讨论的「元数据随数据内联」是同一设计哲学。

6. 专题：dispatch/combine 如何避免「全量元数据 allgather」

这是所对齐对话末尾的问题：token 的 dispatch/combine 具体怎么做，才能避免朴素 all-to-allv 路径里「提前 allgather 全量元数据」的开销？分四层回答。先说清楚：UltraEP 本身不实现 token 通信（与 DeepEP 解耦），本节以 DeepEP 为代表讲 token 线，UltraEP 的权重线用的是同族技术。

6.1 先厘清：all-to-allv 到底需要什么元数据

逻辑上，变长 all-to-all 只需要每对 (src, dst) 的计数矩阵（$G \times G$ 个整数）——接收端据此算各源段偏移。它不需要「全量元数据」（每 token 的路由表，$O(T \cdot k)$）。「提前 allgather 全量信息」是朴素实现把这件事做坏了的两种形态R：

  1. 全量复制型：早期框架的 allgather dispatcher 把 token 或路由表广播给所有 rank（$T \cdot k$ 规模），带宽和显存都被放大 $G$ 倍；
  2. host 往返型：用 allgather/小 all-to-all 把计数搬到 CPU → host 上算偏移并分配接收张量 → 再调 all_to_all_single / MPI_Alltoallv。代价：D2H/H2D 往返 + 流同步；接收形状动态 → CUDA graph 无法捕获；通用集合通信库不感知 NVLink/RDMA 非对称域拓扑；失衡偏斜下热点链路拥塞（生产中 all-to-all 可占步时 20–60%R，对话引昇腾社区文章的口径）。

6.2 DeepEP normal 模式（训练 / prefill）：计数设备驻留 + 域间转发

DeepEP 把「布局」与「数据」分成两个阶段，并把两者的元数据都留在设备上V（V1 README API）：

  • 布局阶段：get_dispatch_layout(topk_idx, num_experts) 在设备上产出 num_tokens_per_rank、num_tokens_per_rdma_rank、num_tokens_per_expert、is_token_in_rank——交换的是计数向量（充分统计量）而非路由表R（API 形态一手核对；「计数经 NVLink/RDMA buffer 设备侧交换」为对实现结构的推断）。
  • 数据阶段：dispatch() 按「NVLink 域内 put + RDMA 域间转发」执行非对称域带宽转发（README: "forwarding data from NVLink domain to RDMA domain"），buffer channel 队列 + 锁做流控，SM 数量可配（set_num_sms）V。
  • combine 零元数据：直接复用 dispatch 返回的 handle，反向搬运即可V。

诚实的代价：normal 模式仍有一次 host 同步——README 原文注释「the CPU will wait for GPU's signal to arrive, so this is not compatible with CUDA graph. Unless you specify num_worst_tokens, but this flag is for intranode only」V。原因：接收张量按实际计数动态分配，必须在 host 上拿到尺寸。训练/prefill 本来不用 CUDA graph，这个取舍成立；而 num_worst_tokens（最坏尺寸分配）就是消灭这次同步的开关。官方在 issue #39 还自评：队列式 buffer 省显存但复杂且可能死锁，固定最大容量 buffer 更简单更快V。

6.3 DeepEP low-latency 模式（decode）：元数据彻底并入数据面

解码模式把「同步」从协议里整体拿掉V（V1 README）：

  • 固定容量：low_latency_dispatch(hidden, topk_idx, num_max_dispatch_tokens_per_rank, ...) 的接收 buffer 按最坏 token 数预分配，形状恒定；返回的 recv_expert_count 是设备张量（供 grouped GEMM 在设备上消费）——注释明言「compatible with CUDA graph (but you may restore some buffer status once you replay)」。
  • 纯 RDMA + 每专家 QP：num_qps_per_rank = num_experts // group.size()，数据经预注册 buffer 直写对端。
  • 零 SM 重叠：return_recv_hook=True 时，数据接收由 RDMA 引擎在后台推进，调用 hook() 才真正可见——用于双批重叠（TBO）而不占用任何 SM。
  • 没有独立的元数据阶段：发送端把 token 连同必要头部直接写入对端固定槽位，接收端扫描/计数即得布局——「元数据随数据内联（in-band）」。

顺带一提 V2（当前 main）：decode 路径提供 cached_handle 模式，路由不变时复用布局、「avoiding redundant CPU synchronization」V——把「何时需要元数据」进一步压缩到「布局真变了才算数」。

② 元数据设备驻留 / 随数据内联计数往返 CPU，host 分配 + 流同步设备侧交换计数（normal）或头部随数据写入固定槽位（low-latency），零 host 参与
③ 最坏尺寸 + 固定地址按实际计数动态分配 → 不可捕获 CUDA graph固定容量 buffer + 设备张量计数 → graph 兼容；代价是预留显存（issue #39 讨论的取舍）

UltraEP 在权重线上是同族实现：NVSHMEM 单侧 put + epoch ready-flag（§5.3），无全局 barrier、无 host 同步、CUDA graph 兼容。并且两条线互相成就：UltraEP 把负载摊平后，「DeepEP token 接收 buffer 的 worst-case 分配」也随之下调V（博客设计原则一节）——均衡得越好，最坏尺寸浪费的显存越少。

8.2 批判性视角

  • TEMPO 的批评（arXiv:2608.13057）：把 UltraEP 与 LLEP、TAOT 归类为「training-side balancers」，认为其无法在 serving 栈上端到端复现——它们利用了训练特有的条件（如权重在推理侧不可即时复制的约束被绕开）R（片段截断，语义待核）。旁证：UltraEP 的 SGLang 集成目前标注 experimentalV（README）。
  • 为什么只覆盖 prefill 不覆盖 decode：论文与博客均未明说。合理解释R：解码每步 token 极少（百级），每层复制专家 + 重路由的相对开销会远超 300 µs 量级收益；且 DeepEP low-latency 模式本身用固定 slot + 最坏尺寸已部分消化失衡。留作待验证。
  • rank 级 vs 专家级均衡的边界：UltraEP 只把「各 rank 总负载」摊平，不解「各专家间」不均衡；与 force-balanced 上限的差距正来自通信/计算对负载的非一致性（§7 表末行）。把它误当专家级均衡会高期待。
  • 带宽账（为什么必须限定 scale-up 域）R：以 Qwen3-235B 单专家 ≈ 37.7 MB（bf16）计，EP64 下每层物化 R 个副本跨 rank 传输约在 GB/s×百微秒 = 数十 MB 量级，只有 NVLink 域（≥100 GB/s/rank）能装进 300 µs 预算；RDMA 域单卡 ~50 GB/s 且多 rank 共享，必然爆预算。这与「复制半径 = NVL 域」的硬约束互为因果。
  • 与 MoonEP 的叙事竞争：UltraEP 结尾把后训练（RL rollout 的强动态负载，引 ReLibra）列为下一个战场，主张做「MoE RL 基础设施的统一负载调节层」V（博客）；与 MoonEP 的 decode/推理叙事正面相遇，可回看本目录另两篇笔记的对比矩阵。

10. 增补讨论：失衡量化、专家激活覆盖与 prefill/decode × EP 度的定量关系

本章由四问引出：失衡怎么评估；prefill 序列长、token 多时是否全专家被激活；prefill 与 decode 的大 EP 部署差异；EP 度越大为何实际差距被拉大。统一用 $N$（专家总数）、$k$（top-k）、$T$（每步 token 总数）、$G$（EP rank 数）、$m = N/G$（每 rank 专家数）、$\lambda = Tk/N$（每专家平均 token 数）。

10.1 失衡的评估：为什么是 max : mean

UltraEP 的指标在每层、每 microbatch 粒度上、用门控后的精确 token 数统计，且均衡前（post-gating）与均衡后（post-reroute）各测一次，故能同时报告 1.30–4.01 → 1.01–1.04V：

$$ \mathcal{I} = \frac{\max_r L_r}{\frac{1}{G}\sum_r L_r}, \qquad L_r = \text{rank } r \text{ 接收的 token 数} $$

选 max : mean 而非 max : min 的理由：MoE 前向每层做同步集合通信，步时 ∝ 最慢 rank（max），理想计算量 ∝ 均值（mean），因此

$$ \text{有效利用率} \approx \frac{1}{\mathcal{I}}, \qquad \text{吞吐损失} \approx 1 - \frac{1}{\mathcal{I}} $$ $$ \mathcal{I} = 1.3 \Rightarrow 23\% \text{ 损失}; \quad \mathcal{I} = 4.0 \Rightarrow 75\% \text{ 损失（MoE 段内）} $$

评估分两级V：① 指标级——UltraEP 内置运行时 profiler（融合 metadata 算子 + 异步 D2H，开销近零），采集每层每 microbatch 重路由前后的全部专家负载，配 HTML 层次化可视化；② 端到端级——吞吐对 force-balanced 理想上界归一化（94.3% 类数字）。指标边界：$\mathcal{I}$ 是 rank 级均衡而非专家级；与理想上界的剩余差距来自实际路由下通信/计算对各专家负载的非一致性V（博客）。

10.2 「大部分专家被激活」的定量：覆盖率公式

均匀路由假设下，单个专家被至少一个 token 选中的概率与每专家平均负载R（解析推导；真实路由非均匀，见下）：

$$ P_{\text{act}} = 1-\Big(1-\frac{k}{N}\Big)^{T}, \qquad \lambda = \frac{T\,k}{N} $$

两个推论：

  • 激活全覆盖 ≠ 均衡。随机涨落随 $T$ 增大被摊薄（$\propto 1/\sqrt{T}$），但专家热度的系统性偏斜不随 $T$ 消失，且同一序列内路由同域相关（同话题 → 同批专家热）R。G=64、T=4096 时纯涨落只能解释 $\mathcal{I}\approx 1.13$，实测原始 1.30–4.01 说明系统偏斜是大头——这正是「精确负载」路线的立论点。
  • decode 也几乎全点亮，但负载极稀（$\lambda \approx 1\!\sim\!8$）：GEMM 被权重读取主导，单步耗时 ≈ 本 rank 被点亮的专家数 × 权重读时间。decode 的均衡对象从「token 数」漂移为「激活专家数 / 权重读次数」R——MoonEP「每 rank 恒载 S×K」的构造性保证正是针对这一层（见源码级对比分析）。
