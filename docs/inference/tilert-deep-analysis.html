TileRT 深度解构 —— 持久化引擎内核与 execution gap 的系统性消除

分析对象：tile-ai 组织（TileRT，v0.1.6）——TileLang 团队推出的超低时延 LLM 解码运行时，tagline 为 "Tile-Based Runtime for Ultra-Low-Latency LLM Inference"。已承载 Z.ai GLM-5.1-highspeed 生产流量，AgentX 榜单（2026-09-24）8×MI355X 跑 GLM-5.3 FP8 单用户 469 tok/s 居第一；与小米 MiMo 合作的 1T 参数模型在单节点 8 GPU 上实测约 1200 tok/s。

证据标注：V = 官方博客 / README / 合作方博客明确陈述；R = 合理推断；U = 待核实。本文为网络资料解构（未做源码精读——TileRT 内核本身以预编译 .so 黑盒交付，仓库无可读内核源码，这一点本身也是本文的重要发现）。

TL;DR

TileRT 的核心创新是把整个模型在编译期静态展开成一个常驻 GPU 的「持久化引擎内核」（Persistent Engine Kernel），将算子打碎为 tile 级任务、把调度下沉到 GPU 内部，从而消除 kernel launch、跨 kernel 同步、显存往返等「执行缝隙」（execution gap）开销。它不做通用 serving，专攻 batch-1 单流生成速度（TPOT），通过 vLLM KVConnector 插件以 PD 分离形态嵌入现有推理栈。

一句话定位：它是「解码极速能力」而非「推理平台」——前缀处理、并发调度、API 生态全部让渡给 vLLM，自己只把一件事做到硬件理论极限：单个 token 的生成延迟。

一、问题定义：Execution Gap（执行缝隙）

TileRT 全部设计源于一个数量级落差（官方博客给出的账）V：

  • 8×H200 聚合显存带宽约 38 TB/s，GLM-5.1 单步 decode 仅需激活约 42 GB 参数；
  • 由 decode 的访存墙（memory-bound roofline）可得理论下限：
$$\text{TPOT}_{\min} = \frac{B_{\text{active}}}{\text{BW}_{\text{agg}}} = \frac{42\ \text{GB}}{38\ \text{TB/s}} \approx 1.1\ \text{ms} \;\Rightarrow\; \text{约 900 tok/s 的理论上限}$$
  • 但传统引擎真实只能跑出几十 tok/s。Profiler 显示 GPU 利用率并不低——算力被「困在执行边界之间」。

作者把这之外的开销统称为 execution gap：kernel launch 延迟、kernel 间的全局同步、中间结果在 global memory 的往返、通信与计算之间的停顿、runtime 与 device 的调度握手。在百毫秒级的大 kernel 时代这些开销被打摊薄；而 decode 的微秒级 kernel 下，「kernel 还没热起来就已经结束了」，固定开销重新进入关键路径。TileRT 的全部技术，就是对这四个字的系统性围剿。

二、架构解构：五层技术栈

TileRT 的架构可以拆成自上而下的五层，每层都在回答「如何让 GPU 不停下来」。

2.1 执行模型层：Persistent Engine Kernel（持久化引擎内核）

  • 编译期把整个模型静态展开为 GPU 上一个常驻运行的引擎内核，host 侧只 launch 一次；
  • 没有逐算子的 kernel launch 序列，优化范围从「单个 kernel」扩大到「整个 forward pass」；
  • 中间结果停留在 register / shared memory / L2，不反复写回显存；
  • 调度不再由 host runtime 驱动，而是下沉到 GPU 内部持续自驱。

这是与 vLLM / SGLang 类「动态调度 + 逐算子执行」框架最根本的分野——前者为吞吐和通用性保留调度自由度，TileRT 用静态性换延迟。

2.2 流水线层：Tile 级流水线 + 持续预取

  • 数据搬运、张量计算、通信被切成细粒度的物理 tile 任务，在存储层级（global → shared → register）间持续流动；
  • 当前 tile 在计算核内处理时，后续数据已在多级预取路径上，实现深度的片上重叠；
  • 对比 NVIDIA 的 PDL（Programmatic Dependent Launch，只能让下一个 kernel 提前 launch）：TileRT 直接消除了 kernel 边界，可以精确控制预取时机、距离和搬运内容，重叠能力强于 PDL。

2.3 同步层：流式同步替代全局 barrier

  • 持久化内核失去了 kernel 边界隐式提供的全局同步，TileRT 改用流式 producer–consumer 握手：上游阶段产出部分数据即交给下游，阶段间持续重叠而非齐步走；
  • 官方明确说这项技术在 AMD 架构上「特别有效」。

2.4 通信层：one-shot push + 有序本地归约

TP8 下放弃 ring all-reduce / reduce-scatter + all-gather 的多轮通信模式：

  • 每个 rank 直接把数据单边写入所有 peer 的 symmetric buffer（one-shot push），然后各 rank 按固定顺序做本地归约；
  • 消除多轮传输和独立同步阶段；通信不再是一个独立 kernel，直接织入执行 pipeline 与计算持续重叠。

2.5 特化层：Warp → Block → GPU 的异构 Worker

从 warp specialization 一路扩展到整机异构。以 GLM-5.1 为例的分工：

  • GPU 0 = 稀疏索引 Worker：Top-K 选择、MoE 路由等动态稀疏阶段；
  • GPU 1–7 = MLA Worker：RMSNorm、GEMM、Flash Sparse Attention、AllReduce 等规整计算流。

动机：稀疏路由、Top-K、MTP 验证这类动态阶段不适合同构 TP 扩展，让「擅长的人干擅长的事」。GPU 在这个视角下从同构并行设备变成「持续流动、紧密编排的异构执行系统」。

2.6 编译底座（重要且需要注意的部分）

TileRT 的内核生成技术建立在 TileLang（tile 级 GPU kernel DSL，约 7.5k stars）之上，底层编译技术官方称会「逐步贡献」到 TileLang 和 TileScale 项目。但 TileRT 仓库本身只发布预编译的后端动态库（libtilert_dsv32.so / libtilert_glm5.so / libtilert_glm52_rocm.so），内核源码并未随仓库开放——它是 MIT 协议的开源项目，但内核实现目前是黑盒交付。

2.7 为什么在 AMD CDNA 4（MI350X / MI355X）上如鱼得水

官方博客给出三条硬件层面的理由，这也是它在 AgentX 榜上用 AMD 卡打赢 NVIDIA FP4 方案的底层解释V：

  1. 寄存器容量：每个 CU 更大的寄存器堆 → 同 occupancy 下更多 in-flight 数据常驻，支撑更深预取与更多阶段重叠；
  2. 分区 cache 与细粒度内存控制：CDNA 的 compute partition 各有本地 cache，内存指令可控可见范围 → 分区内跨 block 轻量交换数据，硬件分区成为软件可主动利用的 locality 层级；
  3. ISA 级控制：inline assembly + 开放可反汇编工具链，关键路径可做针对性手工优化。

3.2 推测解码：MTP 与 DFlash 两条腿

  • MTP（GLM-5.2/5.3 支持深度 1/3，NVIDIA 侧固定 3）：合成负载最高 590 tok/s，GLM-5.2/5.3 平均接受长度 3.2；
  • DFlash（arXiv:2602.06036，块级掩码并行预测）：草稿模型一次前向填充整个掩码块（块大小 8），草稿侧仅用滑动窗口注意力（SWA）使单次预测算力为常数，Muon 二阶优化器 + 自蒸馏训练；验证仍走拒绝采样保证无损。与小米联调后平均接受长度：Coding 6.30 / Math 5.56 / Agent 4.29（每轮 8 个草稿 token 接受 6–7 个）。

有效速度的账很简单：$v_{\text{eff}} = \bar{L}_{\text{accept}} / t_{\text{step}}$。DFlash 把 $\bar{L}_{\text{accept}}$ 从 MTP 的 ~3.2 拉到 ~6.3，等于在不动系统的情况下再翻一倍——这正是它能破 1000 TPS 的关键拼图之一。

3.3 PD 分离：不动 vLLM 一行源码的接入方式

v0.1.5 引入，这是 TileRT 从「benchmark 玩具」走向生产的关键一步：

  • 接口：完全基于 vLLM V1 官方扩展点 KVConnectorBase_V1，自定义 TileRTConnector（kv_producer 角色），零 fork / 零 patch；
  • 数据面：传输引擎支持 NIXL（多 NIC 主机推荐 UCX_NET_DEVICES 绑定 RDMA 网卡）与 Mooncake，协议与引擎解耦；RDMA 单边写直接落进 TileRT decode 节点预注册的显存，无序列化、不经主机内存；forward 窗口内只做快速状态提取到 staging buffer，实际传输由后台异步 sender 完成，不拖慢同批原生请求；
  • 交接：传输内容为压缩 KV、稀疏注意力索引缓存及元数据；接收侧转成 TileRT 原生内存布局后直接注入运行中的引擎实例——无冷启动、无调度空泡，MTP 从第一步就生效；
  • 路由：外部路由器把延迟敏感请求发给 vLLM 做 prefill（强制 max_tokens=1），带 tilert_host 标记的请求 KV 直送 TileRT 解码池，不带标记的走原生 vLLM 解码池；TileRT 池有独立的 gated-dispatch 背压（--queue-timeout 可排队而非 429），与 vLLM 池的无界队列完全隔离；
  • 约束：一个解码引擎同时只服务一条序列；KV cache dtype 两端必须匹配（如 fp8_ds_mla ↔ fp8）。

五、案例深挖：与小米 MiMo 的模型-系统协同设计

1000 TPS 不是纯系统优化的结果，而是「模型为流水线而改」的范本。官方的判断很直白：当性能逼近硬件边界，瓶颈从单个 kernel 变成结构性边界（memory hierarchy 与模型结构不匹配、通信拓扑与路由模式冲突、KV cache 增长与 locality 矛盾、动态稀疏破坏同构并行），模型→编译器→硬件的单向适配不再够用。MiMo-V2.5-Pro-UltraSpeed 的三个协同设计点：

  1. 选择性 MXFP4 量化：只把对量化容忍度最高的 MoE Experts（参数绝大部分）压到 FP4（OCP MX v1.0 规范，QAT 训练），其余网络保持高精度——直接针对商用 GPU 的带宽墙，$B_{\text{active}}$ 的下降线性转化为 TPOT 下降；
  2. DFlash 草稿架构对齐：草稿模型用 SWA 与 MiMo-V2 系列主模型对齐，单次预测算力为常数；块大小限 8 以压低验证开销；
  3. 高频瓶颈前置到模型侧：MTP 每层额外的 LM Head 在 1000 TPS 下引入数十微秒级开销，RMSNorm、RoPE、KV 写入等「FLOP 可忽略但反复切断执行流」的碎片操作成为主要矛盾——这些在模型设计阶段就要算进去。

官方配套的宏观论点是 「Speed 是新的 Scaling Law」：Chat 时代（2023–24）value < cost 拼质量，Agentic 时代（2025–）value ≈ cost 拼吞吐，Autonomous 时代（未来两年）value >> cost 拼速度——固定延迟预算内能做多少轮 rollout、多深的推理链、多少次自验证，速度本身就是新的扩展维度。

几个精确的判断：

  • 它不是 vLLM 的竞争者，是 vLLM 的「外挂变速箱」：PD 分离拓扑里两者是共生关系，vLLM 管 prefill、并发、prefix cache、标准 API，TileRT 只管把 decode 压到极限；
  • 与专用硬件的对比是它最强的叙事：1T 模型 1200 tok/s 出自单台标准 8-GPU 节点，而此前这个量级基本是 Cerebras / Groq 专属；
  • TileLang 是它的技术母体和生态位：tile-ai 组织以 TileLang（7.5k stars）为核心，TileOPs（LLM 算子库）、tilelang-ascend / metax（国产硬件适配）为枝干，TileRT 是这条技术路线在「完整推理引擎」层面的第一次产品化——用 DSL 生成整个持久化内核，这条路 Triton 系框架目前没有走到。

七、局限与风险（批判性视角）

  1. 内核黑盒：仓库只有 20 个 commit，交付物是预编译 .so，内核源码未开放（「逐步贡献到 TileLang / TileScale」目前更多是承诺）。想审计、二次开发、移植模型都做不到，实质上接近商业 SDK 的开源壳；
  2. 模型支持面极窄且扩展成本高：静态展开的执行模型意味着每支持一个新模型 / 新结构都要重新编译整套引擎，当前仅 DS-V3.2 与 GLM-5 系；
  3. batch-1 单流专注是双刃剑：吞吐型场景（高并发、大 batch）完全不适用；官方路线图里 batch 2/4 仍属「计划」。这决定了它必须以 PD 分离插件形态存在，无法独立承担通用服务；
  4. 单引擎单序列：一个解码引擎同时只服务一条序列，资源占用和弹性伸缩的经济学需要实际部署检验；
  5. 成绩多来自自家参与的合作与榜单R：AgentX 虽是 SemiAnalysis 主导的开源可复现基准，但 1000 TPS 等数字的复现依赖特定权重（MiMo FP4-DFlash 检查点已开源）与配置，独立第三方复现数据还很少；
  6. 项目很年轻：v0.1.x 阶段，CLI 有已知 bug，长上下文、复杂真实流量下的 tail latency 是官方自己承认的持续战场（「极致 benchmark 往往是脆弱的」）。

八、对低时延方向的启示

  • 「Execution Gap」是一个值得内化的分析框架：分析任何 decode 侧性能时，把开销分为 roofline 内（带宽 / FLOP）与 roofline 外（launch / 同步 / 往返 / 调度），后者在微秒级 kernel 时代是几十 tok/s 与几百 tok/s 的差距来源。相关技术谱系可对照：NVIDIA PDL（TileRT 的对照组）、DeepSeek DeepGEMM、SGLang 的 overlap scheduler、CUTLASS device-side GEMM——它们都在同一个方向上，TileRT 只是走得最远（直接消灭 kernel 边界）；
  • 低时延的终局是协同设计：系统侧榨干之后，下一步的空间在模型侧——量化精度分配（expert-only FP4）、投机解码架构（MTP → DFlash 的接受长度跃迁）、甚至 LM Head 的层数。做低时延研究不应只盯 kernel；
  • 对 RL / rollout 的直接意义：rollout 评测的 gate 本质上也是「固定时间预算内能产出多少合格 token」，TileRT 这类引擎（或它的技术思想）直接影响 rollout 吞吐上限与 test-time scaling 的可行预算；
  • AMD 路线值得跟踪：TileRT 在 CDNA 4 上的表现说明「低时延优化」未必绑定 NVIDIA 生态，寄存器容量和分区 cache 的设计差异在持久化内核范式下被放大。

理论 Decode 上限的计算原理

Decode 阶段为访存受限（memory-bound）：自回归每生成一个 token，至少要把激活的参数权重从显存完整读一遍。因此单步时延下限与吞吐上限由带宽而非算力决定：

\[ t_{\text{step}} \;\ge\; \frac{S_{\text{act}}}{B_{\text{agg}}}, \qquad T_{\text{upper}} = \frac{1}{t_{\text{step}}} = \frac{B_{\text{agg}}}{S_{\text{act}}} \]

其中 $B_{\text{agg}}$ 为节点聚合显存带宽，$S_{\text{act}}$ 为单 token 激活参数字节。按 TileRT 博客口径：GLM-5.1（MoE）单步激活 ≈42 GB（FP8/1 字节权重）；W8/INT8 权重同为 1 字节/权重，故 $S_{\text{act}}$ 同取 42 GB；MXFP4 则减半为 21 GB。假设：① 激活权重在 8 卡间理想切分、各卡带宽并行；② 只计权重流量（不含 KV Cache、通信、反量化）；③ 算力足够（memory-bound 成立）。这个上限与"传统引擎几十 tok/s"之间的 1~2 个数量级差，正是正文分析的 execution gap。

追问：实测 469 tok/s 距理论上限 1,524 tok/s 很远，怎么解释

AMD 官方技术文章《TileRT AgentX on AMD Instinct GPUs》给出的 469 tok/s（8×MI355X，GLM-5.3，TP8，FP8 权重 + BF16 KV，MTP K=3，单用户 AgentX 榜第一）与表 2 的 1,524 tok/s 之间差 ≈3.2 倍。这不是矛盾，而是口径差了四层——1,524 是"短上下文、只读权重、100% 峰值带宽、零通信"的白盒上限，469 是端到端 agent 会话回放的真实成绩。逐层剥离：

#开销来源量级与依据证据等级
1基准口径：AgentX 不是白盒 decodeAgentX（SemiAnalysis 开源可复现基准）回放真实编码 agent 会话：多轮、上下文持续增长、tool call、共享前缀，考的是 KV/路由/调度/尾时延。文章自给的标尺：同一配置（TP8 + MTP K=3）在 8×MI350X 上 1K ctx 648 → 1M ctx 425 tok/s——469（MI355X，会话平均上下文更长）正落在该区间，长上下文衰减本身就吃掉了约 1/3V
2KV Cache 流量不在 42 GB 账内账面 $S_{\text{act}}$ 只含激活权重（KV=0）；实际 KV 为 BF16（字节较 FP8 翻倍），每 token 的 KV 读取随上下文增长，长会话时进入与权重流量可比的量级——这是 648→425 衰减曲线的直接物理来源V（BF16 与曲线出自文章；"可比量级"为 R）
3峰值带宽 ≠ 实效带宽8 TB/s 是理想顺序读峰值。业界普遍实测：decode GEMV 稳态只能拿到峰值的 ~50–90%（KV 争用、专家权重非连续访存、launch 开销）；即便按 80% 计，上限立刻降为 ≈1,219 tok/sR（业界口径，见 InferenceX 词汇表等）
4TP8 通信轮数batch-1 的 all-reduce 是小消息、延迟主导——文章原话"通信轮数比峰值带宽更重要"。TileRT 用 one-shot 推送 + 本地归约把每层轮数压到 1，但乘以近百层后仍是每步的固定时间项，无法被带宽账覆盖V
5碎片算子与 MTP 开销LM Head（词表 ~15 万）、RMSNorm/RoPE/路由/KV 写入——FLOP 可忽略但反复切断执行流（正文五节已析）；MTP K=3 每 step 验证 4 个候选 token，各自 top-k 路由使每 step 激活专家并集扩大（可达单 token 的 2–3 倍），权重流量按 step 放大R
6模型口径校验（排除项）GLM-5.3 总参 ~753B、激活 ~40B/token（FP8 ≈ 40 GB，另有注意力 indexer 每 query 选 2,048 token），与账面 42 GB（GLM-5.1）基本一致——模型不是差距主因R（第三方汇总，非官方）

把账串起来：1,524（白盒）→ ×带宽实效 ≈1,219 → +KV/通信轮数/碎片算子 → 短上下文实测 648（MI350X 档，MI355X 略高）→ ×长上下文与 agent 会话混合 → 469。达成率 ≈31%——而这已是消灭了 kernel 边界的榜首引擎；传统引擎几十 tok/s 时达成率仅 2–5%。还要注意 469 已含 MTP 接受长度 ~3.2 的收益，若按"读一遍权重出 3.2 token"的投机感知口径衡量，实际达成率比 31% 更低——KV、通信轮数与碎片算子吃掉的比表面更多。理论上限的价值不在"可达"，而在提供一把尺：剩余 ~69% 里，KV 流量与通信是 roofline 内的物理开销（要靠 FP8 KV、更高带宽、更少通信轮数压缩），碎片算子与调度是 roofline 外的工程开销（TileRT 们继续消灭的对象）。
